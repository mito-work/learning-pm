# ステークホルダー管理 > 立ち上げ

## 正式見積：体制図作成

---

## 導入

### このスキルを身につけると、何が変わるか

「誰に連絡すればいいかわからない」とプロジェクト開始後に顧客から言われた。
「体制図には○○さんの名前があるのに、実際に出てくる人が違う」とクレームになった。
「ベンダー側のPMとPLの違いが顧客には伝わっておらず、同じ確認が二重に来た」——

体制図は「誰がプロジェクトにいるか」を示す地図です。
正式見積フェーズの体制図は、超概算フェーズの仮体制図（役割のみ）とは違い、
**実際の担当者名・連絡窓口・意思決定ラインを明示した、プロジェクト運営の設計図**です。

このスキルを学ぶことで：
- 顧客が「誰に・何を・どのルートで伝えるか」を迷わなくなる
- アサイン変更・体制変更時のリスクを事前に設計できる
- 連絡の二重化・抜け漏れを構造で防げる
- 体制図が提案書の「信頼性」を高めるツールになる

---

## 学習目標

このテキストを読み終えると、以下ができるようになります。

1. **仮体制図と正式体制図の違いと、それぞれの目的を説明できる**
2. **正式体制図に必要な要素（役割・人名・連絡窓口・意思決定ライン）を整理して作成できる**
3. **体制図に起きやすい問題（アサイン変更・窓口の重複）を設計段階で防ぐポイントを説明できる**

## 本編

---

### Section 1：仮体制図と正式体制図の違い

**一言でいうと：仮体制図は「役割の地図」、正式体制図は「人の地図＋コミュニケーション設計」。**

超概算フェーズで作った仮体制図と、正式見積フェーズの体制図は、目的が異なります。

| 項目 | 仮体制図（超概算） | 正式体制図（正式見積） |
|-----|--------------|-----------------|
| **作成タイミング** | 超概算・キーパーソン特定のため | 提案書・見積もりに添付するため |
| **記載内容** | 役割のみ（人名なし） | 役割＋担当者名＋連絡先 |
| **目的** | 「誰が入るか」を顧客と確認するツール | 「誰が何をするか」を顧客に提示する設計図 |
| **完成度** | 未確定あり（空欄OK） | 確定情報のみ（空欄NG） |

**正式体制図で伝えること：**
```
① 誰がプロジェクトを担当するか（ベンダー側の全メンバー）
② 誰がどの役割を担うか（PM・PL・各担当の役割定義）
③ 誰に連絡すればいいか（顧客から見た窓口の明確化）
④ 意思決定はどのラインで行うか（エスカレーションルート）
```

---

### Section 2：正式体制図に含める要素

**一言でいうと：体制図は「図」ではなく「情報の設計」。含める要素を先に決めてから描く。**

体制図に入れる情報は、大きく5つです。

#### ① 役割と担当者名

各メンバーの「役割（ロール）」と「担当者名」をセットで記載します。

```
記載例：
  プロジェクトマネージャー（PM）：山田 太郎
  プロジェクトリーダー（PL）：鈴木 花子
  設計担当：田中 一郎
  開発担当：佐藤 二郎、中村 三郎
  QA担当：伊藤 四郎
```

**役割の説明文を1行添える**ことで、顧客が「この人に何を聞けばいいか」を理解できます。

```
PM（山田）：プロジェクト全体の管理。顧客への報告・課題のエスカレーション窓口
PL（鈴木）：技術面のリード。設計・開発方針の判断。技術的な質問の窓口
```

#### ② 連絡窓口の明示

顧客が「誰に連絡すればいいか」を迷わないように、窓口を明確にします。

```
【ベンダーへの連絡先（窓口）】
  ・日常的な連絡・進捗確認：PL 鈴木（suzuki@example.com）
  ・契約・費用・エスカレーション：PM 山田（yamada@example.com）
  ・緊急時（障害・クリティカルな課題）：PM 山田（携帯：090-XXXX-XXXX）
```

窓口が複数ある場合は「何についてはどこ」を明示します。
「何かあればPMに」だけでは、全件PMに集中して機能しなくなります。

#### ③ 意思決定・エスカレーションライン

```
【意思決定ライン】
  通常の判断 → PL 鈴木が判断
  スコープ・費用に関わる判断 → PM 山田が判断
  契約変更・重大な課題 → PM 山田 → 弊社部長（○○）にエスカレーション
```

顧客は「このベンダーはどのレベルの問題まで現場で判断できるのか」を知りたいと思っています。
エスカレーションラインが見えることで、顧客は「困ったときに誰に言えばいいか」が明確になります。

#### ④ 顧客側の体制（確定分）

正式体制図はベンダー側だけでなく、顧客側の確定した体制も入れます。

```
【顧客側体制（確定済み）】
  プロジェクトオーナー：顧客 取締役 ○○様
  顧客側PM：顧客 ○○部 田中様（日常の窓口）
  業務担当者：顧客 ○○部 鈴木様（要件定義フェーズで参加予定）
```

未確定の役割は「調整中」と記載し、空欄にしません。
「空欄」は「考えていない」という印象を与えます。

#### ⑤ 協力ベンダー・外部連携先（あれば）

```
【協力ベンダー】
  インフラ構築：○○クラウド株式会社（担当：△△様）
  → インフラ設計・構築・運用設計を担当
```

### Section 3：体制図の「落とし穴」と防ぎ方

**一言でいうと：体制図は作って終わりではなく、「守れる設計かどうか」を最初に確認する。**

体制図でよく起きる問題と、設計段階での対処法を整理します。

#### ① 「書いた人と実際に動く人が違う」問題

```
よくある状況：
  提案書に「PM：山田」と書いたが、受注後にアサインが変わった
  → 顧客から「話が違う」とクレームになる
```

**対処法：**
提案書の体制図に、以下の一文を添えます。
```
「本体制図は現時点の予定です。プロジェクト開始後に担当者が変更になる場合は、
 事前に顧客様にご説明した上で変更させていただきます。」
```
また、体制図に「アサイン確定日」を記載し、いつまでに確定するかを明示します。

#### ② 「窓口が多すぎて混乱する」問題

```
よくある状況：
  顧客からの質問が、PMにもPLにも営業担当にも飛んでくる
  → 誰が回答するかが決まらず、二重回答・回答漏れが起きる
```

**対処法：**
顧客向けの窓口は「1つのトピックにつき1人」にします。
「技術的な質問はPL・事務的な連絡はPM」のように、トピックごとの窓口を体制図に明示します。

#### ③ 「体制図が古くなる」問題

```
よくある状況：
  プロジェクト途中でアサインが変わったが、体制図を更新しなかった
  → 顧客が古い体制図をもとに連絡してくる
```

**対処法：**
体制図には「版数・更新日」を入れます。
```
体制図 v1.0（2026年6月時点）
```
体制変更時は新しい版を作り、顧客に送付します。

### Section 4：体制図の描き方——構造のパターン

**一言でいうと：体制図の形は「何を伝えたいか」で決める。複雑にしない。**

体制図にはいくつかのパターンがあります。
プロジェクトの規模・顧客との関係に合わせて選びます。

#### パターン①：シンプルな階層型（小〜中規模）

```
【顧客側】               【ベンダー側】
PO（○○様）
 ↕ 報告・承認
顧客側PM（△△様） ←────→ PM（山田）
                              ↓
                         PL（鈴木）
                         ↙       ↘
                    設計担当    開発担当
                   （田中）    （佐藤・中村）
                                   ↓
                              QA担当（伊藤）
```

#### パターン②：コミュニケーションライン入り（顧客との連携を重視する場合）

```
【顧客側】                    【ベンダー側】
PO（○○様） ─────月次報告───→ PM（山田）
                                  │
顧客側PM（△△様）──週次連携──→ PL（鈴木）
                                  │
業務担当（鈴木様）──要件確認──→ 設計担当（田中）
IT担当（伊藤様） ──技術確認──→ 開発担当（佐藤）
```

コミュニケーションラインを矢印で示すことで、「誰がどのルートで話すか」が一目でわかります。

---

### Section 5：体制図を提案書で「使う」技術

**一言でいうと：体制図は「添付資料」ではなく、提案の中で説明する「信頼の根拠」にする。**

体制図を提案書に入れるだけでは不十分です。
**体制図を説明する場（提案プレゼン・打ち合わせ）で、PMが直接語ること**が重要です。

```
体制図の説明の仕方（例）：

「弊社のPM山田がプロジェクト全体を管理し、
 顧客の田中様との窓口を一本化します。

 技術面はPL鈴木が主担当となります。
 設計から実装まで一貫して鈴木が責任を持つことで、
 認識のズレが起きにくい体制にしています。

 万が一、重大な課題が発生した場合は、
 山田から弊社部長にエスカレーションし、
 速やかに顧客様に報告します。」
```

「誰が・どんな経験を持ち・どんな考えでプロジェクトに臨むか」を体制図に沿って語ることで、
単なる図が「このチームに任せられる」という安心感に変わります。

## まとめとネクストアクション

### 3つの重要ポイント

1. **正式体制図は「役割＋人名＋連絡窓口＋意思決定ライン」の4点セットで作る**
   仮体制図（役割のみ）から進化させ、「誰に何を頼むか」を顧客が判断できる設計図にする。
   顧客側の確定情報も入れ、未確定は「調整中」と明示する。

2. **窓口は「1トピックにつき1人」。複数の窓口は混乱を生む**
   技術質問・進捗確認・エスカレーションの連絡先を分けて明示する。
   「何でもPMへ」は機能しない。

3. **体制図は「添付資料」ではなく「説明するもの」。提案の場でPMが直接語る**
   「誰が担当し・どんな責任を持ち・問題が起きたらどうエスカレーションするか」を言葉で伝えることで、
   図が「信頼の根拠」に変わる。
