# ステークホルダー管理 > 立ち上げ

## 正式見積：【内部】決済者／上長の特定

---

## 導入

### このスキルを身につけると、何が変わるか

「見積もりを顧客に出したら、上司に『なぜ確認しなかったのか』と怒られた」
「金額は合っていたのに、リスクの説明が不十分だと差し戻された」
「誰に確認すれば社内OKが出るのか、毎回よくわからない」——

正式見積を提出する前には、社内にも「承認しなければならない人」がいます。
顧客への対応ばかりに意識が向きがちですが、**社内の決済者・上長を正確に特定することが、見積もり提出の前提条件**です。

このスキルを学ぶことで：
- 正式見積の社内承認ラインを、案件の規模や種類に応じて判断できる
- 上長への報告タイミングと報告内容を整理できる
- 「誰に・何を・いつ確認するか」を計画として立てられる
- 差し戻し・後戻りを防げる

---

## 学習目標

このテキストを読み終えると、以下ができるようになります。

1. **正式見積における社内の承認ラインを、案件規模・種類に応じて整理できる**
2. **決済者・上長への報告のタイミングと内容を判断できる**
3. **複数の上長が関与する案件で、確認漏れを防ぐ管理ができる**

## 本編

---

### Section 1：なぜ「内部の決済者・上長特定」が必要か

**一言でいうと：顧客への見積もり提出は、社内承認が終わった後に行う。順番を間違えると二度手間になる。**

「見積もりを顧客に出す」という行為には、2つの前提が必要です。

```
顧客に見積もりを出す前に必要なこと：
① 見積もりの金額・内容が正しいか（技術・工数の確認）
② その見積もりを出すことを、社内の誰かが承認しているか（社内承認）
```

②を飛ばして顧客に出してしまうと、こうなります。

```
よくある失敗パターン：
  ① PMが見積もりを作成して顧客に提出
  ② 上長に報告したら「このリスクは説明したのか？」「この金額は低すぎる」と指摘
  ③ 顧客に「一度見積もりを修正させてください」と連絡
  → 顧客からの信頼が落ちる。「出してから修正」は最悪の状況
```

**見積もり提出のゴールデンルール：社内承認 → 顧客提出。この順番は絶対に崩さない。**

---

### Section 2：社内承認ラインは「案件の規模」で変わる

**一言でいうと：小さい案件は現場判断、大きい案件は経営判断。規模に応じた承認ラインを把握する。**

会社によって承認ラインは異なりますが、一般的には案件の金額規模によって承認者が変わります。

| 案件規模 | 金額目安 | 承認者の例 | 承認に必要な時間の目安 |
|--------|--------|---------|-----------------|
| 小規模 | ～1,000万円 | PM・PL | 1〜2営業日 |
| 中規模 | 1,000万〜5,000万円 | 部長・部門責任者 | 3〜5営業日 |
| 大規模 | 5,000万円〜 | 役員・経営会議 | 1〜2週間 |
| 戦略案件・新規顧客 | 金額に関わらず | 営業責任者＋技術責任者 | 個別調整 |

**重要：承認ラインは会社・部門によって異なります。**
まず自社の承認ルールを確認してください。
「いくら以上は誰が承認するか」というルールが明文化されていない場合は、上長に直接確認します。

---

### Section 3：決済者・上長が複数いる案件の整理

**一言でいうと：承認が必要な人は1人とは限らない。全員を最初に特定する。**

正式見積には複数の観点が含まれます。
それぞれの観点ごとに「確認すべき上長」が異なることがあります。

#### 確認すべき上長の種類

| 確認観点 | 確認すべき上長 | 確認内容 |
|--------|------------|--------|
| **金額・利益率** | 営業責任者・部長 | この金額で受注してよいか。利益率は適切か |
| **技術的な実現可能性** | 技術責任者・PL | この内容で本当に作れるか。工数は適切か |
| **リスク・契約条件** | 法務・管理部門 | 契約条件に問題はないか。リスクが高い要件はないか |
| **リソース確保** | 部門責任者 | 受注した場合、人員を確保できるか |

特に見落としがちなのは**「リソース確保」の確認**です。
見積もりは通ったが「その時期に人員がいない」という状況は、プロジェクト開始後の炎上につながります。

#### 確認漏れを防ぐチェックリスト

```
正式見積の社内承認チェックリスト：

□ 金額・利益率：[確認者：___________] [確認予定日：___________]
□ 技術的実現可能性：[確認者：___________] [確認予定日：___________]
□ 契約条件・リスク：[確認者：___________] [確認予定日：___________]
□ リソース確保：[確認者：___________] [確認予定日：___________]
□ 最終承認者：[確認者：___________] [確認予定日：___________]
```

このリストを見積もり作成前に作ることで、「誰に・いつ・何を確認するか」が明確になります。

### Section 4：上長への報告タイミングと報告内容

**一言でいうと：上長への報告は「見積もり完成後」ではなく「作成前」から始める。**

見積もりを完成させてから上長に見せると、こんな問題が起きます。

```
「完成後に見せる」の問題：
  ・上長が「この方針で作るべきではなかった」と言い出す
  → 最初から作り直しになる（大きな手戻り）

  ・「この前提条件は入れるべきだった」と指摘される
  → 金額が大幅に変わる
```

上長への報告は、**見積もり作成の前・中・後の3段階**で行います。

#### ① 作成前：方針の合意

```
報告内容：
・案件の概要（顧客、規模、内容）
・見積もり作成の方針（どこまで含めるか・前提条件）
・懸念しているリスク
・顧客への提出予定日

上長への確認事項：
「この方針で見積もりを作成してよいですか？
 特に[○○の部分]についての判断をいただきたいです。」
```

#### ② 作成中：中間報告（大規模案件・リスクが高い案件）

```
報告内容：
・現時点での概算金額
・工数見積もりの前提
・新たに判明したリスク

上長への確認事項：
「現時点で○○万円前後になりそうです。
 [リスク]について方針を確認させてください。」
```

#### ③ 作成後：最終承認

```
報告内容：
・見積もりの最終金額
・前提条件の全体像
・対応できるリスクと対応できないリスク
・競合状況・受注確率（わかる範囲で）

上長への確認事項：
「この内容で顧客に提出してよいですか？
 [特にリスクが高い部分]についてご確認ください。」
```

---

### Section 5：「決済者・上長の特定」を最初にやるべき理由

**一言でいうと：誰が承認するかを知ることで、見積もり作成のスケジュールが決まる。**

承認には時間がかかります。
「承認者が誰か」を最初に特定しておくことで、「顧客への提出日から逆算した社内スケジュール」が立てられます。

```
スケジュール逆算の例：

顧客への提出希望日：6月30日

逆算：
・最終承認（役員）：1週間必要 → 6月23日までに申請
・技術レビュー：3日必要 → 6月20日までに完成
・見積もり作成：1週間必要 → 6月13日から開始

つまり：6月13日に作成開始しないと間に合わない
```

承認者を特定しないまま見積もりを作り始めると、「完成してから初めて承認者に渡す」という最悪のスケジュールになります。
「顧客の提出期限」だけを見て動くPMと、「社内承認期限から逆算して動くPM」では、余裕が全く違います。

## まとめとネクストアクション

### 3つの重要ポイント

1. **社内承認 → 顧客提出の順番は絶対に崩さない**
   顧客に出してから「社内に差し戻された」は最悪の状況。
   見積もりを作る前に「誰が承認するか」「何日かかるか」を確認する。

2. **承認者は金額規模・観点ごとに複数いる。全員を最初にリストアップする**
   営業・技術・リソース・法務——観点ごとに確認すべき上長が異なる。
   チェックリストで「誰に・いつ・何を確認するか」を見える化する。

3. **上長への報告は「作成前・作成中・作成後」の3段階で行う**
   完成後にだけ見せると手戻りのリスクが高い。
   作成前に方針を合意することで、「最初から作り直し」を防ぐ。
