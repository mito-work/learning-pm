# ステークホルダー管理 > 立ち上げ

## 超概算：【対客】超概算内容の打診

---

## 導入

### このスキルを身につけると、何が変わるか

「概算を伝えたら、あとから『そんな金額は聞いていない』と言われた」
「担当者はOKと言っていたのに、上司に通したら白紙になった」
「金額が上振れしたら『話が違う』とクレームになった」——

PMが超概算の打診を苦手とする理由は、「誰に・どう・何を伝えるか」が整理できていないからです。
超概算の打診は、金額を伝えることではありません。
「なぜその金額なのか」を、決める立場の人に納得してもらうことです。

このスキルを学ぶことで：

- 超概算を正しく伝え、決済担当者まで正確に届ける方法が身につく（直接・現場担当者経由のどちらも）
- 「高い」「聞いていない」というクレームを事前に防げる
- 超概算の限界を正直に伝えながら、信頼を得る方法がわかる
- 前提条件の変更が生じた場合に、追加見積もりの交渉がスムーズになる

---

## 学習目標

このテキストを読み終えると、以下ができるようになります。

1. **超概算を「上限」と「前提条件・精度」で伝えられる**
2. **「なぜこの金額か」を価値・比較・内訳で説明できる**
3. **クレームを防ぐための「記録・精度の説明・比較軸」を実践できる**

## 本編

---

### Section 1：超概算は「上限」で提示する

**一言でいうと：幅で伝えると顧客が下限で計画する。上限1点を明示する。**

超概算（プロジェクト初期段階の概算）は、精度が低い見積もりです。
一般的に、超概算の精度は **±30〜50%** と言われています。

超概算は「低く言って後から上げる」ことはできません。
金額が変動すると「話が違う」というクレームに直結します。
だからこそ、最初から「上限」を明示して提示することが重要です。

> **関連教材：** 超概算を提示する前に、顧客の予算上限を先に確認するステップがあります。
> 顧客の予算上限を把握したうえで、超概算の上限を予算内に収まるよう設定するためです。
> 詳しくは「超概算：【対客】決済担当者に予算の打診」を参照してください。

**悪い例①：1点の数字で伝える**

```
「このシステムは5,000万円です」
→ 後から7,000万円になったとき：「話が違う！5,000万円と言ったじゃないか！」
```

**悪い例②：幅（レンジ）で伝える**

```
「現時点では4,000万円〜7,000万円の範囲を想定しています」
→ 顧客は下限の4,000万円で計画を立てる
→ 後から6,500万円になったとき：「4,000万円で見てたのに…」
```

**良い例：上限で伝える**

```
「現時点の超概算として、上限7,000万円でご検討ください。
 精度は±40%程度のため、要件定義完了後により正確な数字をお出しします。」
→ 顧客は7,000万円以内で計画を立てる
→ 要件定義後に6,500万円になっても：「上限内に収まっている」
```

### Section 2：「なぜこの金額か」を説明する

**一言でいうと：金額だけ伝えると「高い」になる。価値と比較軸を一緒に伝える。**

決済担当者が「高い」と感じるのは、金額の大きさだけが原因ではありません。
「この金額に見合う価値があるのか」が見えないことが原因です。

#### ① 金額が高い理由の説明

```
・要件の詳細がまだ確定していない
・外部連携先の仕様が未確認
・非機能要件（セキュリティ・性能・運用）の詳細が未定
```

これらの不確定要素があるため、現時点の見積もりは
「確認できていない部分をリスクとして上乗せした金額」になります。

顧客への伝え方：
「現時点では仕様が確定していない部分があるため、
 上限を多めに見た金額でお伝えしています。
 要件定義が進むにつれて、より正確な数字に絞り込んでいきます。」

#### ② 内訳を大まかに示す

 └ 【補足】「高い」と言われたときは機能を絞るかフェーズを分ける

細かい内訳は不要ですが、「何にお金がかかるか」の構造を示すと納得感が上がります。

| 費用区分 | 概算割合 | 補足 |
|--------|--------|------|
| 開発費（設計・実装・テスト） | 約60% | エンジニア人件費が中心 |
| プロジェクト管理費 | 約15% | PMおよびPLの稼働費 |
| インフラ・ライセンス費 | 約15% | サーバー・ソフトウェア費用 |
| 導入支援・教育費 | 約10% | マニュアル作成・研修など |

内訳を示したことで「ここは削れないか」という話になった場合、
以下の2つのアプローチで選択肢を提示します。

| アプローチ | 内容 | 使う場面 |
|---------|-----|--------|
| **機能を絞る** | 優先度の低い機能を今回のスコープから外す | 「全部は要らないかも」という反応のとき |
| **フェーズを分ける** | 全機能を複数フェーズに分割し、初期投資を抑える | 「一度に全額は出しにくい」という反応のとき |

「削る」のではなく「後回しにする」という提示が、
顧客が受け入れやすい選択肢になります。

#### ③ 比較軸を示す

金額だけを提示すると「高いか安いか」の判断ができません。
何かと比べることで、顧客が「この金額感は妥当だ」と判断できるようになります。

**比較軸の例：**

| 比較の切り口 | 伝え方の例 |
|-----------|---------|
| **現状のコストと比べる** | 「現在、手作業で月○時間かかっている業務が自動化されます。人件費換算で年間○百万円の削減効果が見込めます」 |
| **導入しない場合のリスクと比べる** | 「このまま現行システムを使い続けた場合、○年後には保守コストが現在の2倍になる見込みです」 |
| **代替手段と比べる** | 「パッケージソフトでの代替も検討しましたが、カスタマイズ費用を含めると今回のスクラッチ開発と同程度になります」 |

### Section 3：クレームを防ぐ——書面（メール・議事録）に残す

**一言でいうと：口約束は後で覚えていない。記録に残すことが最大のクレーム防止策。**

> **前提条件の定義・精度の設定・スコープ外の明示・前提変更の予告** は、超概算を作成する段階の作業です。
> 詳しくは「超概算：【対客】見積作成」で確認してください。

超概算に関するクレームの多くは「言った・言わない」の水掛け論です。
打ち合わせ後に書面を残すだけで、この水掛け論のほぼ全てを防げます。

口頭だけの金額提示は、後から「そんな金額は聞いていない」という水掛け論になります。
打ち合わせ後には必ず、議事録かメールで「本日ご説明した金額と前提条件」を文章で送ります。

```
メールの例：
「本日ご説明した超概算の内容を下記の通りご確認いただけますか。
 ・概算金額（上限）：○千万円（前提：○○○の場合）
 ・精度：現時点で±40%程度
 ・次のステップ：要件定義完了後に概算見積もりをご提示」
```

「ご確認ください」と送ることで、顧客が黙認した時点で合意記録になります。

書面に残した内容は、クレームを防ぐだけでなく、**前提が変わった際の追加見積もり交渉の根拠**にもなります。
「最初にこの前提でご合意いただいていましたが、〇〇が変わったため追加が発生します」と伝えられるのは、書面で合意を取っているからです。
口頭だけで終わらせていると、前提変更の交渉は水掛け論になります。

### Section 4：決済担当者への伝え方——言葉を選ぶ

**一言でいうと：直接伝える場合も現場担当者経由の場合も、「経営の言葉」に整理して渡す。**

超概算の打診には2つのルートがあります。

| ルート | 状況 | 対応方針 |
|------|-----|---------|
| **直接打診** | 決済担当者に同席・面会できる | 自分で経営言語に変換して伝える |
| **現場担当者経由** | 現場担当者が決済担当者に説明する | 現場担当者が「伝えやすい形」で渡す |

このセクションでは、特に**現場担当者経由**のルートを中心に解説します。

---

#### 現場担当者経由の場合：まず現場担当者に理解・共感してもらう

「上司に話しておきます」と現場担当者に言われたとき、任せきりにするのは危険です。
現場担当者が金額の意味を正確に理解していなければ、誤った情報が決済担当者に届きます。

> **前提：現場担当者との信頼関係**
> 現場担当者が「この情報を正確に・好意的に伝えよう」と思ってくれるかどうかは、
> それまでの関係性にかかっています。
> 信頼関係の作り方は「超概算：【対客】担当者予算打診不可時の決済者確認」を参照してください。

信頼関係があるうえで、現場担当者が自分で説明できるよう以下の3点を整理して渡します。

```
① なぜこの金額なのか（1文で）
  「要件がまだ確定していないため、リスクを上乗せした上限金額です」

② 上限であることの意味（誤解を防ぐ）
  「この金額で確定ではなく、要件定義後に正確な数字をお出しします」

③ 次のステップ（担当者が質問されたときに答えられるよう）
  「要件定義に○ヶ月かかり、そこで正式見積もりを出せます」
```

この3点を口頭で説明したうえで、書面（メールや1枚の要約）として渡すと伝言しやすくなります。

---

#### 決済担当者に届く言葉の選び方

直接打診でも現場担当者経由でも、決済担当者に届く言葉は「経営言語」である必要があります。
決済担当者（役員・経営者）は技術的な詳細には興味がなく、「この投資は正しいか」だけを判断します。

| 避けるべき言葉 | 使うべき言葉 |
|------------|------------|
| 「APIを使って連携します」 | 「既存システムと自動でデータ連携します」 |
| 「サーバーの冗長化が必要です」 | 「障害時でもサービスが止まらない構成にします」 |
| 「工数が多いので高くなります」 | 「複雑な要件のため、開発に時間がかかります」 |
| 「要件定義が終わらないと出せません」 | 「今は上限でお伝えする超概算で、詳細確定後に正式な数字をお出しします」 |

現場担当者経由の場合は、この変換を**担当者自身がやりやすいよう**書面に落としておくことがポイントです。

## まとめとネクストアクション

### 3つの重要ポイント

1. **超概算は「上限」で提示する。幅（レンジ）では伝えない**
   幅で伝えると顧客は下限で計画を立てる。上限を明示することで「この金額以内で進める」という合意になる。

2. **超概算は「上限＋前提条件＋精度」の3点セットで伝える**
   1点の数字は後から必ずトラブルになる。「上限○○万円、前提は○○、精度は±40%」
   という形で伝えることで、後の変動を「想定内」に変えられる。

3. **必ず書面に残す。口頭だけで終わらせない**
   打ち合わせ後のメール1通が、最大のクレーム防止策になる。
   「本日ご説明した金額と前提条件です、ご確認ください」と送るだけでよい。
