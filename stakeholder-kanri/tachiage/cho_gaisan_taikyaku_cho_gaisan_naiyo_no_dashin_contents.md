# ステークホルダー管理 > 立ち上げ

## 超概算：【対客】超概算内容の打診

---

## 導入

### このスキルを身につけると、何が変わるか

「概算を伝えたら、あとから『そんな金額は聞いていない』と言われた」
「担当者はOKと言っていたのに、上司に通したら白紙になった」
「予算が増えたら『話が違う』とクレームになった」——

PMが予算の話を苦手とする理由は、「誰に・どう・何を伝えるか」が整理できていないからです。
超概算の予算打診は、金額を伝えることではありません。
「なぜその金額なのか」を、決める立場の人に納得してもらうことです。

このスキルを学ぶことで：
- 決済担当者（予算を持つ上位者）への伝え方が身につく
- 「高い」「聞いていない」というクレームを事前に防げる
- 超概算の限界を正直に伝えながら、信頼を得る方法がわかる
- 後から予算が増えたときの摩擦を最小化できる

---

## 学習目標

このテキストを読み終えると、以下ができるようになります。

1. **決済担当者と現場担当者の違いを説明し、両者への対応を使い分けられる**
2. **超概算を「幅（レンジ）」と「前提条件」で伝えられる**
3. **クレームを防ぐための「記録・精度の説明・比較軸」を実践できる**

## 本編

---

### Section 1：「決済担当者」とは誰か

**一言でいうと：お金の判断ができる人に、直接伝える必要がある。**

プロジェクトの窓口になる「現場担当者」と、予算を承認する「決済担当者」は、多くの場合別の人です。

| 役割 | 誰か | 関心事 |
|-----|-----|-------|
| **現場担当者** | 担当者・課長クラス | 機能・使い勝手・スケジュール |
| **決済担当者** | 部長・役員・経営者 | 費用対効果・リスク・予算内に収まるか |

現場担当者だけと話していると、こんな失敗が起きます。

```
よくある失敗：
  ① 担当者に「だいたいXXXX万円です」と伝える
  ② 担当者は「わかりました」と返事する
  ③ 担当者が上司に報告したら「そんな予算はない」と却下される
  ④ 「あの担当者はOKと言っていたのに…」という状況になる
```

**決済担当者に直接打診することが、後からの「聞いていない」を防ぐ唯一の方法です。**

現場担当者には「予算を承認できる方に同席していただけますか？」と一声かけましょう。
最初は断られることもありますが、「概算金額のご説明があるため」と理由を添えると通りやすくなります。

### Section 2：超概算を「幅（レンジ）」で伝える

**一言でいうと：1点ではなく「〇〇円〜〇〇円」で伝える。これが後のクレームを防ぐ。**

超概算（プロジェクト初期段階の概算）は、精度が低い見積もりです。
一般的に、超概算の精度は **±30〜50%** と言われています。

超概算は「低く言って後から上げる」ことはできません。
金額が上振れすると「話が違う」というクレームに直結します。
だからこそ、最初から上限を含んだ幅で提示することが重要です。

> **関連教材：** 超概算を提示する前に「顧客の予算感を先に聞く」
> というステップがあります。幅の下限を顧客の予算に合わせるためです。
> 詳しくは「超概算：【対客】決済担当者に予算の打診」を参照してください。


**悪い例：**

```
「このシステムは5,000万円です」
→ 後から7,000万円になったとき：「話が違う！5,000万円と言ったじゃないか！」
```

**良い例：**

```
「現時点では4,000万円〜7,000万円の範囲を想定しています。
 要件定義が完了した段階で、より正確な数字をお出しします。」
→ 後から6,500万円になっても：「最初からその範囲内です」
```

### Section 3：「なぜこの金額か」を説明する

**一言でいうと：金額だけ伝えると「高い」になる。価値と比較軸を一緒に伝える。**

決済担当者が「高い」と感じるのは、金額の大きさだけが原因ではありません。
「この金額に見合う価値があるのか」が見えないことが原因です。

#### ① 金額が高い理由の説明

```
・要件の詳細がまだ確定していない
・外部連携先の仕様が未確認
・非機能要件（セキュリティ・性能・運用）の詳細が未定
```

これらの不確定要素があるため、現時点の見積もりは
「確認できていない部分をリスクとして上乗せした金額」になります。

顧客への伝え方：
「現時点では仕様が確定していない部分があるため、
 上限を多めに見た金額でお伝えしています。
 要件定義が進むにつれて、より正確な数字に絞り込んでいきます。」

#### ② 内訳を大まかに示す

 └ 【補足】「高い」と言われたときは機能を絞るかフェーズを分ける

細かい内訳は不要ですが、「何にお金がかかるか」の構造を示すと納得感が上がります。

| 費用区分 | 概算割合 | 補足 |
|--------|--------|------|
| 開発費（設計・実装・テスト） | 約60% | エンジニア人件費が中心 |
| プロジェクト管理費 | 約15% | PMおよびPLの稼働費 |
| インフラ・ライセンス費 | 約15% | サーバー・ソフトウェア費用 |
| 導入支援・教育費 | 約10% | マニュアル作成・研修など |

内訳を示したことで「ここは削れないか」という話になった場合、
以下の2つのアプローチで選択肢を提示します。

| アプローチ | 内容 | 使う場面 |
|---------|-----|--------|
| **機能を絞る** | 優先度の低い機能を今回のスコープから外す | 「全部は要らないかも」という反応のとき |
| **フェーズを分ける** | 全機能を複数フェーズに分割し、初期投資を抑える | 「一度に全額は出しにくい」という反応のとき |

「削る」のではなく「後回しにする」という提示が、
顧客が受け入れやすい選択肢になります。

#### ③ 比較軸を示す

金額だけを提示すると「高いか安いか」の判断ができません。
何かと比べることで、顧客が「この投資は妥当だ」と判断できるようになります。

**比較軸の例：**

| 比較の切り口 | 伝え方の例 |
|-----------|---------|
| **現状のコストと比べる** | 「現在、手作業で月○時間かかっている業務が自動化されます。人件費換算で年間○百万円の削減効果が見込めます」 |
| **導入しない場合のリスクと比べる** | 「このまま現行システムを使い続けた場合、○年後には保守コストが現在の2倍になる見込みです」 |
| **代替手段と比べる** | 「パッケージソフトでの代替も検討しましたが、カスタマイズ費用を含めると今回のスクラッチ開発と同程度になります」 |

比較軸は「費用対効果」を示すものであり、
決済担当者が「この投資は正しい」と判断するための材料になります。

### Section 4：クレームを防ぐ「4つの約束」

**一言でいうと：口約束は後で覚えていない。記録に残すことが最大のクレーム防止策。**

予算に関するクレームの大半は、以下の4つのどれかで防げます。

#### ① 前提条件を明示する

超概算には必ず「前提条件」があります。
前提が変われば金額も変わることを、最初に合意します。
前提条件には3つの種類があります。

**❶ 数値・範囲の前提**

システム規模や対象範囲に関する数値的な前提です。

```
例：
・システム利用ユーザー数：社内ユーザー100名以下
・外部連携：既存の基幹システムとの連携1件（APIあり）
・開発期間：6ヶ月
・運用保守は別途見積もり
```

**❷ シナリオ前提**

どのような業務シナリオを対象とするかも、前提条件になります。
シナリオが変われば必要な機能が変わり、金額が変わります。

```
例（受発注管理システムの場合）：

  シナリオ前提：
    「受注は社内担当者が手動で入力する」
    ↓
    → 入力フォーム・承認ワークフロー機能が必要

  シナリオが変わった場合（顧客が直接入力する）：
    「顧客ポータルから直接発注できる」
    ↓
    → 顧客向けUI・外部アクセス認証・セキュリティ強化が追加で必要
    → 金額が変わる
```

想定するシナリオを明示することで、顧客との間で
「何を作るか」の共通認識が生まれます。

**❸ やらないことの前提（スコープ外の明示）**

超概算で見落とされがちですが、**「やらないこと」を明示することが見積もりの生命線**です。
含まれていないことを言わないと、顧客は「含まれている」と思います。

```
やらないことの前提条件（例）：

  ・性能テスト・障害テスト（負荷テスト・フェイルオーバー確認）
  ・インフラ増強（サーバースペックアップ・ネットワーク改修）
  ・本システムの保守（リリース後の運用・障害対応）
  ・脆弱性診断（セキュリティ診断・ペネトレーションテスト）
  ・オペレーター向けトレーニング（操作研修・マニュアル作成）
```

「やらない」は「できない」ではなく「今回のスコープに含まれない」という意味です。
必要であれば追加見積もりで対応できることも一言添えると、顧客の安心感が高まります。

```
伝え方の例：
「今回の超概算には、性能テストや保守対応は含まれていません。
 必要な場合は別途お見積もりします。
 また、上記の前提が変わった場合、金額が変動することをご了承ください。」
```

#### ② 精度を正直に伝える

「超概算なので精度が低い」ことを隠すと、後から必ず問題になります。

```
良い伝え方：
「現在は要件定義前の超概算のため、精度は±40%程度です。
 要件定義完了後に概算、基本設計完了後に詳細見積もりを
 段階的にご提示します。」
```

「精度が低い」と伝えることは、誠実さの証明になります。
顧客は「正直に言ってくれた」という安心感を持ちます。

#### ③ 書面（メール・議事録）に残す

口頭だけの金額提示は、後から「そんな金額は聞いていない」という水掛け論になります。
打ち合わせ後には必ず、議事録かメールで「本日ご説明した金額と前提条件」を文章で送ります。

```
メールの例：
「本日ご説明した超概算の内容を下記の通りご確認いただけますか。
 ・概算金額：○千万円〜○千万円（前提：○○○の場合）
 ・精度：現時点で±40%程度
 ・次のステップ：要件定義完了後に概算見積もりをご提示」
```

「ご確認ください」と送ることで、顧客が黙認した時点で合意記録になります。

#### ④ 増額の可能性を最初から伝える

幅（レンジ）で提示していても、要件定義を進める中で
その上限すら超える可能性があります。
「上限を超えるかもしれない」ということも最初に伝えておくことで、
増額報告が「予告通りの話」になります。

```
最初から言っておく言葉：
「超概算のため、要件定義を進める中で金額が上振れする可能性があります。
 その場合は都度ご報告し、ご判断をいただく形で進めます。」
```

### Section 5：決済担当者への伝え方——言葉を選ぶ

**一言でいうと：決済担当者は「技術の話」より「経営の話」で考える。**

決済担当者（役員・経営者）は、技術的な詳細には興味がありません。
彼らが判断したいのは「この投資は正しいか」という1点です。

#### 避けるべき言葉と、使うべき言葉

| 避けるべき言葉 | 使うべき言葉 |
|------------|------------|
| 「APIを使って連携します」 | 「既存システムと自動でデータ連携します」 |
| 「サーバーの冗長化が必要です」 | 「障害時でもサービスが止まらない構成にします」 |
| 「工数が多いので高くなります」 | 「複雑な要件のため、開発に時間がかかります」 |
| 「要件定義が終わらないと出せません」 | 「今は幅のある概算で、詳細確定後に正式な数字をお出しします」 |

技術用語を経営言語に変換する習慣が、決済担当者との信頼関係を作ります。

## まとめとネクストアクション

### 3つの重要ポイント

1. **現場担当者ではなく「決済担当者」に直接伝える**
   予算を持つ上位者に直接打診することが、「聞いていない」クレームを防ぐ唯一の方法。
   「予算承認できる方に同席いただけますか？」と一声かけるだけでリスクが大きく下がる。

2. **金額は「幅（レンジ）＋前提条件＋精度」の3点セットで伝える**
   1点の数字は後から必ずトラブルになる。「○○万円〜○○万円、前提は○○、精度は±40%」
   という形で伝えることで、後の変動を「想定内」に変えられる。

3. **必ず書面に残す。口頭だけで終わらせない**
   打ち合わせ後のメール1通が、最大のクレーム防止策になる。
   「本日ご説明した金額と前提条件です、ご確認ください」と送るだけでよい。
