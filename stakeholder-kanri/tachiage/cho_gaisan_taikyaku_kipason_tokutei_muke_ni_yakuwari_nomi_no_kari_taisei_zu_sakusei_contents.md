# ステークホルダー管理 > 立ち上げ

## 超概算：【対客】キーパーソン特定向けに役割のみの仮体制図作成

---

## 導入

### このスキルを身につけると、何が変わるか

「プロジェクトが始まってから、意思決定者が誰かわからないまま進んでいた」
「担当者に確認したらOKだったのに、後から別の人が『聞いていない』と言い出した」
「キーパーソンを特定するタイミングが遅くて、後から関係者が一気に増えた」——

こうした「誰が誰かわからない問題」は、プロジェクト開始前の**仮体制図**で防げます。
超概算フェーズで「役割のみの仮体制図」を作ることは、キーパーソンを特定するための最速の方法です。

このスキルを学ぶことで：
- キーパーソンを早期に特定し、「後から知らない人が出てくる」状況を防げる
- 「役割のみ」で書くことで、人名が決まっていない段階でも体制を可視化できる
- 顧客側・ベンダー側の意思決定ラインが明確になる
- 体制図をヒアリングのツールとして使える

---

## 学習目標

このテキストを読み終えると、以下ができるようになります。

1. **超概算フェーズで「役割のみの仮体制図」を作る目的と使い方を説明できる**
2. **顧客側・ベンダー側それぞれに必要な役割を列挙し、仮体制図の骨格を作れる**
3. **仮体制図をヒアリングツールとして使い、キーパーソンを特定できる**

---

## 本編

---

### Section 1：なぜ「役割のみの仮体制図」が必要か

**一言でいうと：名前ではなく「役割」で書くことで、キーパーソンを特定するための地図になる。**

プロジェクトの初期段階では、顧客側の体制がまだ決まっていないことがほとんどです。
「誰がPMになるか」「承認者が誰か」は、顧客の社内調整が終わっていない段階では答えが出ません。

そこで、名前ではなく「役割（ロール）」だけを書いた仮体制図を作ります。

**仮体制図の2つの目的：**

| 目的 | 内容 |
|-----|-----|
| **意思決定ラインの可視化** | 誰がどこで何を決めるかを構造として見える化する |
| **キーパーソン特定のヒアリングツール** | 「この役割には誰が入りますか？」と確認するための土台にする |

**メタファー：**
仮体制図は「キャスト表のないオーディション会場」のようなものです。
役の種類（役割）を先に決めておき、「このキャラクターを演じる人は誰ですか？」と顧客に確認します。
役割が明確なほど、顧客は「誰を当てるか」を考えやすくなります。

---

### Section 2：「役割のみ」で作る理由

**一言でいうと：人名を書くと議論が始まる。役割で書くと構造の話ができる。**

超概算フェーズで人名を入れた体制図を作ると、以下のリスクがあります。

```
人名を先に書くリスク：
・「なぜあの人が入っているのか」という社内政治が動き始める
・担当者が知っている範囲の人名しか入らず、意思決定者が抜け落ちる
・人が変わるたびに体制図を作り直す手間が生じる
```

「役割のみ」で作ることには、こんなメリットがあります。

```
役割のみで書くメリット：
・「この役割を担う人は誰ですか？」という会話が自然に生まれる
・人名が入っていないので、顧客が気軽にコメントできる
・後から担当者が変わっても体制図の骨格は変わらない
・意思決定ラインを「構造」として議論できる
```

「仮体制図を一緒に作る」という作業自体が、キーパーソン特定のヒアリングになります。

---

### Section 3：仮体制図に含める「役割の一覧」

**一言でいうと：顧客側の「意思決定ライン」と「業務実行ライン」の両方を入れる。**

仮体制図は、顧客側とベンダー側の両方を含めて作ります。
特に重要なのは、顧客側の「誰が何を決めるか」が見えるようにすることです。

#### 顧客側の役割

| 役割名 | 役割の内容 | 重要度 |
|------|---------|------|
| **プロジェクトオーナー（PO）** | 最終意思決定者。予算・スコープの最終承認者 | ★★★ |
| **ステアリングコミッティ（SC）** | 重要事項の承認・エスカレーション先 | ★★★ |
| **顧客側PM（プロジェクトマネージャー）** | ベンダーPMとの窓口・社内調整担当 | ★★★ |
| **業務担当者（スーパーユーザー）** | 業務要件を持っている現場のキーパーソン | ★★ |
| **IT担当者（情報システム部）** | インフラ・セキュリティ・既存システムの承認者 | ★★ |
| **法務・調達担当者** | 契約・発注の承認者 | ★ |

#### ベンダー側の役割

| 役割名 | 役割の内容 |
|------|---------|
| **PM（プロジェクトマネージャー）** | プロジェクト全体管理・顧客との窓口 |
| **PL（プロジェクトリーダー）** | 技術面のリード・開発チームのまとめ役 |
| **開発チーム** | 設計・実装・テスト担当 |
| **QA担当** | 品質保証・テスト管理 |

#### 仮体制図のイメージ

```
【顧客側】                         【ベンダー側】
┌────────────────────┐             ┌──────────────────────┐
│ プロジェクトオーナー（PO）│             │                      │
│    →最終意思決定         │             │                      │
└───────────┬────────┘             │                      │
            │                         │                      │
┌───────────▼────────┐             │                      │
│ ステアリングコミッティ  │◄────────────►│ PM                   │
│    →重要事項の承認      │  定期報告・  │                      │
└───────────┬────────┘  意思決定    │                      │
            │                         └──────────┬───────────┘
┌───────────▼────────┐                          │
│ 顧客側PM               │◄────────────────────────►│ PL                   │
│    →日次の窓口         │       日次連携           │                      │
└───┬───────────┬──────┘                          └──────┬───────────┘
    │           │                                         │
┌───▼───┐   ┌───▼──────┐                         ┌──────▼───────────┐
│業務担当│   │IT担当者   │                         │  開発チーム / QA  │
└───────┘   └──────────┘                         └──────────────────┘
```

この図の「役割名」の部分に、後からヒアリングで確認した人名を入れていきます。

---

### Section 4：仮体制図をヒアリングツールとして使う

**一言でいうと：体制図を見せながら「この役割には誰が入りますか？」と聞くだけで、キーパーソンが特定できる。**

仮体制図を作った後、担当者との打ち合わせでそのまま使います。

#### ヒアリングの流れ

```
Step 1：仮体制図を共有する
  「現時点でベンダー側として想定している体制図を作りました。
   顧客様側の体制についても一緒に確認させていただきたいのですが、
   この役割にはどなたが入られる予定でしょうか？」

Step 2：意思決定ラインから確認する（上位から順に）
  「プロジェクトオーナー（最終承認者）はどなたになりますか？」
  「定期的なプロジェクト報告はどなた宛てに行いますか？」
  「契約や発注の承認はどなたがされますか？」

Step 3：業務担当者を確認する
  「業務要件をご存知の方（スーパーユーザー）はどなたですか？
   要件定義でヒアリングさせていただきたい方です。」
  「既存システムの詳細をご存知の情報システム部の方はいらっしゃいますか？」

Step 4：「わからない」への対応
  「まだ決まっていない場合は、いつ頃決まりそうですか？
   今回は役割名だけで進め、人名が決まった時点でご連絡いただければ大丈夫です。」
```

「まだ決まっていない」という回答は、それ自体が重要な情報です。
「未定の役割がある」ことを把握することで、プロジェクト計画のリスクとして管理できます。

---

### Section 5：キーパーソン特定後にやること

**一言でいうと：特定したキーパーソンの情報を記録し、アプローチ計画を立てる。**

ヒアリングで人名が埋まり始めたら、以下を整理します。

#### キーパーソン管理表（仮体制図のサポート情報）

| 役割 | 氏名 | 関心事・特徴 | アプローチ優先度 |
|-----|-----|-----------|-------------|
| プロジェクトオーナー | 未確認 | 予算・ROIを重視する経営層 | 高（予算確定前に面会） |
| 顧客側PM | 山田様 | 現場出身、技術理解あり | 高（日次窓口） |
| 業務担当者 | 未確認 | 要件定義フェーズで特定する | 中 |
| IT担当者 | 鈴木様 | セキュリティ要件に厳しい | 中（設計フェーズ前に確認） |

「未確認」の役割は、次のアクションとしてリストに入れます。
「いつ・誰が・何を確認するか」を明示することで、キーパーソン特定が進みます。

## アクティブラーニング

以下の問いについて、自分のPJを思い浮かべながら考えてみてください。

**問い1：**
今担当しているPJの体制図はありますか？
顧客側の「意思決定者」「承認者」「業務担当者」が全員わかりますか？

**問い2：**
「後から出てきた関係者」にこれまで苦労したことはありますか？
仮体制図があれば、その関係者を早期に特定できたでしょうか？

**問い3：**
「まだ体制が決まっていない」と言われたとき、どう対応しますか？
未確定の役割があることはプロジェクトのリスクとして管理できていますか？

---

## まとめとネクストアクション

### 3つの重要ポイント

1. **超概算フェーズで「役割のみ」の仮体制図を作る。人名は後から埋める**
   人名を先に入れると社内政治が動く。役割だけ書いて「この役割は誰ですか？」と聞くことで、
   自然にキーパーソン特定のヒアリングが始まる。

2. **顧客側は「意思決定ライン（PO・SC）」と「実行ライン（PM・業務担当）」の両方を入れる**
   意思決定ラインが見えていないと、後から「その人は聞いていない」が必ず起きる。
   上位から順に「誰が最終承認しますか？」と確認する習慣をつける。

3. **「未確認・未定」の役割はリスクとして管理する**
   「まだ決まっていない」は放置しない。いつ決まるかを確認し、
   「未確定の役割がある」こと自体をプロジェクト計画のリスクとして記録する。
