# ステークホルダー管理 > 計画

## 【外部連携先／協力ベンダー】内部決済者／上長を巻き込んだ担当管理者とのホットライン確立

---

## 導入

### このスキルを身につけると、何が変わるか

「協力ベンダーの進捗が遅れているのに、担当者に言っても改善されない」
「外部連携先の担当者が異動してしまい、引き継ぎが不十分でプロジェクトが止まった」
「外部パートナーとの問題が現場レベルで解決できず、自社の上長を巻き込もうとしても状況を知らないため動けなかった」——

外部連携先・協力ベンダーとの関係も、担当管理者レベルだけでは対応できない問題があります。
このスキルは、**外部パートナーの担当管理者との日常的なホットラインを設計しながら、同時に内部の上長を巻き込んだ「上層ライン」を計画フェーズから準備する**技術です。

このスキルを学ぶことで：
- 外部パートナーとの問題が現場レベルで止まらず、必要なとき上層で解決できる
- 内部上長が外部パートナーの状況を把握し、適切な支援・判断ができる
- 担当者の異動・変更が起きても、組織間の関係が途絶えない
- 「言えない・動けない」状況を構造として防げる

---

## 学習目標

このテキストを読み終えると、以下ができるようになります。

1. **外部連携先・協力ベンダーの「担当管理者レベル」と「上層レベル」の2段構えの必要性を説明できる**
2. **内部上長を外部パートナーの関係に巻き込むための具体的なタイミングと方法を実践できる**
3. **担当管理者レベルのホットライン設計（連絡頻度・手段・内容）を計画フェーズで合意できる**

## 本編

---

### Section 1：外部パートナーとのホットラインが「2段構え」である理由

**一言でいうと：担当者レベルで動かない問題は、上層レベルで動かす。その準備を計画フェーズで作る。**

外部連携先・協力ベンダーとの関係は、多くの場合「現場の担当管理者同士」だけで動いています。

```
【よくある構造】

  自社                          外部パートナー
  ──────────────────────────────────────────
  上長・決済者            ←─未接続─→  管理者・責任者
  ──────────────────────────────────────────
  PM                      ←────────→  担当管理者
                              日常連絡
```

この構造で問題が起きると、こうなります。

```
【担当者レベルだけのとき】
  問題発生（遅延・品質問題・仕様変更）
  → PMが担当管理者に指摘
  → 「社内で確認します」と言われ、何日も返事がない
  → PMが自社上長に報告するが、上長は外部の状況を知らない
  → 「外部にもっと強く言ってください」と言われても、
    「どこに・誰に・どう言うか」の回路がない
  → 問題が長期化する
```

上層ラインがあると：

```
【上層ライン込みのとき】
  問題発生
  → PMが担当管理者に指摘（通常ルート）
  → 改善されない場合、自社上長から外部管理責任者に直接連絡
    「弊社としても最重要事項として対処いただきたい」
  → 外部パートナー側で「上から話が来た」という優先対応が始まる
  → 問題が短期間で解決しやすくなる
```

---

### Section 2：外部連携先と協力ベンダーで異なるホットラインの設計

**一言でいうと：外部連携先は「技術窓口」、協力ベンダーは「技術＋契約窓口」の2種類が必要。**

外部連携先と協力ベンダーでは、関係の性質が違うため、ホットラインの設計も変わります。

#### 外部連携先のホットライン設計

外部連携先（他社システム・APIサービスなど）との主な問題は「技術的な対応」です。

| 想定される問題 | 必要なホットライン |
|------------|----------------|
| API仕様の変更・廃止 | 技術担当者への即時連絡ライン |
| 接続障害・性能問題 | 障害対応窓口（緊急連絡先） |
| 仕様の解釈相違 | 技術責任者レベルの確認ライン |
| 接続申請・環境準備の遅延 | 管理責任者への依頼ライン |

```
外部連携先で確認すべきホットライン：
  ① 日常技術連絡先：担当エンジニア（メール・チャット）
  ② 緊急障害連絡先：障害対応窓口（電話番号・時間帯）
  ③ 上位確認先（遅延・変更時）：技術管理責任者
```

#### 協力ベンダーのホットライン設計

協力ベンダーとの問題は「技術」だけでなく「契約・コスト・リソース」にも及びます。

| 想定される問題 | 必要なホットライン |
|------------|----------------|
| 進捗遅延・品質問題 | PM・PL間の日常連絡ライン |
| コスト超過・追加見積もり | 営業担当・PM上長レベルの交渉ライン |
| リソース不足・担当者変更 | 管理責任者レベルの調整ライン |
| 契約条件の変更 | 決済責任者レベルの合意ライン |

```
協力ベンダーで確認すべきホットライン：
  ① 日常作業連絡：PM・PL間（メール・チャット・週次定例）
  ② 技術問題・品質指摘：PL・技術責任者間
  ③ 進捗遅延・コスト問題：PM上長・ベンダー営業/管理責任者間
  ④ 契約変更・重大問題：自社決済者・ベンダー決済者間
```

### Section 3：担当管理者レベルのホットラインを設計する

**一言でいうと：「何を・いつ・どうやって連絡するか」を計画フェーズで文書化して合意する。**

担当管理者レベルの日常ホットラインは、プロジェクトの「血流」です。
ここが詰まると、あらゆる情報が流れなくなります。

#### 連絡設計の要素

```
計画フェーズで合意する内容：

① 連絡手段
  ・メール（記録が残る公式連絡）
  ・チャット（迅速な確認・共有）
  ・電話（緊急時・複雑な状況の確認）
  ・定例会（週次・隔週の同期）

② 連絡頻度
  ・定例会：週次 or 隔週（進捗・課題の同期）
  ・随時連絡：課題・変更・懸念が発生したとき
  ・緊急連絡：障害・重大問題時（当日中に連絡）

③ 連絡内容の範囲
  ・何を共有するか（進捗・課題・変更）
  ・何を共有しないか（内部のコスト・社内稟議など）

④ 記録のルール
  ・重要な合意事項はメールで確認
  ・定例会は議事録を作成して共有
```

#### 合意を取り付ける際のポイント

計画フェーズのキックオフで、担当管理者と以下を確認します。

```
「今後の連絡についてご確認させてください。

 日常的な進捗・課題の共有は週次の定例会と
 随時チャットでお願いしたいと思っています。

 重大な問題や変更が発生した場合は、
 当日中にお電話でご連絡することはできますか？

 また、緊急時の連絡先（担当者不在時の代理の方）も
 事前に教えていただけますか？」
```

### Section 4：内部上長を外部パートナーの関係に巻き込む

**一言でいうと：上長が外部パートナーを「知っている」状態を、計画フェーズから作る。**

外部連携先・協力ベンダーとの上層ラインを確立するには、内部上長を早期に関与させる必要があります。

#### 内部上長への説明

まず、自社の上長に「なぜ関与してほしいか」を説明します。

```
上長への説明の構成：

① 外部パートナーの概要（誰と・どんな役割で・どれくらいの重要度か）
② 想定されるリスク（遅延・品質問題・仕様変更など）
③ 上長に担ってほしい役割（キックオフ挨拶・問題時の上層交渉）
④ 具体的なアクション（いつ・どの場で引き合わせたいか）
```

```
上長への説明例：

「今回のプロジェクトでは協力ベンダーの○○社に
 インフラ構築を委託します（約○○○万円規模）。

 過去の類似案件ではリソース不足による遅延が起きやすい
 パートナーです。問題が発生した場合に
 担当者レベルでは解決が難しいことが想定されます。

 キックオフの際に上長からも一言ご挨拶いただき、
 ○○社の管理責任者と顔見知りになっていただけますか？

 プロジェクトを通じて問題が起きたとき、
 上長から直接ご連絡いただけると対処が速くなります。
 キックオフのご挨拶だけで構いません（15分程度）。」
```

#### 接点を作るタイミング

| タイミング | 内容 | 目的 |
|---------|-----|-----|
| **外部パートナーのキックオフ** | 自社上長と外部パートナー管理責任者を引き合わせる | 顔見知りの関係を作る |
| **フェーズ区切りのレビュー** | 上長が成果物レビューに同席する | 進捗・品質を上長が直接確認する |
| **重大課題・遅延発生時** | 上長から外部パートナーの管理責任者に直接連絡 | 解決の優先度を上げる |

### Section 5：ホットラインを「機能させ続ける」設計

**一言でいうと：計画フェーズで作った仕組みは、定期的にメンテナンスしないと劣化する。**

担当者の異動・連絡手段の変化・関係の形骸化——これらを放置するとホットラインは機能しなくなります。

#### 担当者変更への対応

```
担当者変更が起きたとき：
  ① 新担当者の連絡先・役割を即座に更新する
  ② 引き継ぎ資料に「連絡ルールと緊急連絡先」が含まれているか確認する
  ③ 自社上長に「担当者が変わった」と報告し、必要なら再度の引き合わせを設定する
```

#### 関係の形骸化を防ぐ

定例会が「形式的な報告会」になっていないかを定期的に確認します。

```
定例会が機能しているサイン：
  ✅ 課題・懸念が率直に出てくる
  ✅ 決定事項が議事録に残り、次回確認される
  ✅ 担当管理者が「困っていること」を言いやすい雰囲気がある

定例会が形骸化しているサイン：
  ❌ 毎回「特に問題ありません」で終わる
  ❌ 議事録が作られない・共有されない
  ❌ 課題が出てくるのは定例会外の緊急連絡のときだけ
```

形骸化のサインが見られたら、「もっとざっくばらんに話せる場を作りましょう」と担当管理者に声をかけます。

## まとめとネクストアクション

### 3つの重要ポイント

1. **外部パートナーとのホットラインは「担当管理者レベル」と「上層レベル」の2段構えで設計する**
   担当者レベルで動かない問題は上層で動かす。
   その上層ラインを計画フェーズのキックオフで作っておくことが、問題解決の速さを決める。

2. **外部連携先は「技術窓口＋緊急連絡先」、協力ベンダーは「技術窓口＋契約窓口」を分けて確認する**
   担当管理者1人に全部集中させると、その人が不在・異動のとき全部止まる。
   種類ごとに窓口を分けて管理することが、ホットラインの安定につながる。

3. **担当者変更・形骸化に備えて「メンテナンスの仕組み」を最初から作る**
   「作ったホットラインが劣化する」ことを前提に設計する。
   担当者変更時の手順・定例会の形骸化チェックを計画に組み込む。
