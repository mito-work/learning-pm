# 結合テスト方針／方式の管理

## 確認テスト

**Q1. 結合テストで最も重点的に確認すべきことは何ですか？**

A) 1つのプログラムの中に書き間違い（タイポ）がないか。

B) 異なる機能同士をつないだときに、正しくデータが受け渡されるか。

C) パソコンの画面が自分好みの色になっているか。

**Q2. 結合テスト中にバグが大量発生しました。PM（マネジャー）が取るべき行動はどれですか？**

A) バグの発生傾向（品質トレンド）を分析し、スケジュールへの影響を判断する。

B) すべてのバグを自分でプログラミングして直す。

C) 「バグが出るのはやる気がないからだ」とメンバーを叱る。

**Q3. 「完了定義」が必要な理由として、最も適切なものはどれですか？**

A) 早く仕事を切り上げて、飲みに行くため。

B) メンバー全員が「どこまでやれば合格か」を共通認識として持ち、次工程への流出を防ぐため。

C) 報告書に書く文字数を増やすため。

---

## 👉 **正解を確認する Q1: [ B ] / Q2: [ A ] / Q3: [ B ]**

### 【解説】

#### Q1：結合テストの焦点

正解は **B** です。
Aは「単体テスト」の領域です。結合テストは「点（単体）」と「点」をつないで「線（連携）」にする工程なので、インターフェース（接合部）が主役です。

* **ポイント：** 「単体OK ＋ 単体OK ＝ 結合NG」はよくある話です。

#### Q2：PMの役割

正解は **A** です。
PMは「工程の安定」に責任を持ちます。バグの出方を見て「このまま進めても大丈夫か？」「納期に影響しないか？」という**全体のリスク判断**を行うのが仕事です。

* **ポイント：** 現場がパニックになっている時こそ、PMは数字で冷静に状況を見ます。

#### Q3：完了定義の意義

正解は **B** です。
基準が曖昧だと、「たぶん大丈夫」という主観で次工程に進んでしまい、より大きな炎上を招きます。合格ラインを数値化することで、**客観的に**品質を保証できます。

* **ポイント：** 完了定義は、プロジェクトを守る「合格証」です。
