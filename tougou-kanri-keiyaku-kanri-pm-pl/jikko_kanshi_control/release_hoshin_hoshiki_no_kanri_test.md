# リリース方針／方式の管理

## 確認テスト

**Q1. リリース管理の本来の目的として、最も適切なものはどれですか？**

A) 1秒でも早く、新しい機能を本番環境に反映させること。

B) 制御された手順で、安全に本番環境への変更を適用し、リスクを最小化すること。

C) 担当者が徹夜してでも、予定された日に必ずリリースを完了させること。

**Q2. リリース直前に行う「Go/No-Go判断」で、「No-Go（中止）」を出すべき状況はどれですか？**

A) 手順書の一部に、まだ実際に試していない不確実な作業が含まれている。

B) リリース作業中に食べるお弁当がまだ届いていない。

C) 担当エンジニアが少し緊張している。

**Q3. 「ロールバック」が必要な理由として、正しいものはどれですか？**

A) サーバーの容量を節約するために、古いデータを消すため。

B) リリース作業中に重大な問題が起きた際、即座に元の正常な状態に戻して業務を守るため。

C) プログラミングの腕を磨くために、何度もやり直しをするため。

---

## 👉 **正解を確認する Q1: [ B ] / Q2: [ A ] / Q3: [ B ]**

### 【解説】

#### Q1：リリース管理の目的

正解は **B** です。
速さ（A）や根性（C）よりも、**「安全性と制御」**が最優先です。リリースは、実ユーザーの業務に直結するため、失敗した時のダメージが最も大きい工程だからです。

* **ポイント：** リリース管理は「ブレーキ」の役割も持っています。

#### Q2：No-Goの判断基準

正解は **A** です。
「本番でやってみないとわからない」という手順がある状態でのリリースは、ただのギャンブルです。不確実な要素があるなら、**勇気を持って中止し、再準備する**のがプロの判断です。

* **ポイント：** 不安要素をゼロにするのがリリース準備です。

#### Q3：ロールバックの意義

正解は **B** です。
どんなに準備しても、本番では予想外のことが起きる可能性があります。その時、「元に戻せる」という保証があるからこそ、攻めのリリースができます。**ロールバックは「敗北」ではなく、ユーザーを守るための「安全装置」**です。

* **ポイント：** 戻し方のないリリースは、パラシュートのないスカイダイビングと同じです。
