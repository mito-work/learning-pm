
# 当初のリリース方針／方式の確定

## 確認テスト

**Q1. リリースの本質的な説明として、最も適切なものはどれですか？**

A) 開発環境で書いたコードを、GitHubなどのリポジトリに保存すること。

B) 本番環境へ反映し、実ユーザーが使い始め、責任が開発から運用へ移行すること。

C) プログラムのバグをすべて修正し、エンジニアが作業を終えること。

**Q2. リリースにおける「方針（思想）」の例として正しいものはどれですか？**

A) 「手動でサーバーにログインしてファイルを配置する」という手順のこと。

B) 「今回はリスクを抑えるため、段階的に一部のユーザーから公開する」という考え方のこと。

C) 「リリース作業中に使うチャットツールをSlackにする」という連絡手段のこと。

**Q3. リリース計画において「ロールバック」の手順を決めておくべき最大の理由は？**

A) 作業が予定より早く終わった時に、暇つぶしをするため。

B) リリース作業中に深刻な不具合が起きた際、速やかに元の状態に戻して業務への影響を最小化するため。

C) 新しい機能が気に入らなかったユーザーのために、いつでも古い画面に戻せるようにするため。

---

## 👉 **正解を確認する Q1: [ B ] / Q2: [ B ] / Q3: [ B ]**

### 【解説】

#### Q1：リリースの本質

正解は **B** です。
単なる「デプロイ（配置）」は作業の一部に過ぎません。リリースとは、システムが「社会に出る」ことであり、そこから発生する**責任を引き受ける**ことを意味します。

* **ポイント：** リリースは「終わり」ではなく「始まり」です。

#### Q2：方針と方式

正解は **B** です。
Aは「方式（やり方）」であり、Cは「体制・ツール」です。方針とは、「一括でいくか（一発勝負）」「段階的にいくか（安全重視）」といった、**リスクに対する戦略**のことです。

* **ポイント：** 戦略（方針）が決まらないと、具体的な戦術（方式）は決まりません。

#### Q3：ロールバックの重要性

正解は **B** です。
リリースは100%成功するとは限りません。失敗した時に「戻せない」ことが最大の事故です。「いつまでに終わらなければ、元の状態に戻して翌朝の業務を守る」という**撤退基準**がプロの仕事には不可欠です。

* **ポイント：** 命綱（ロールバック）のない綱渡りは、プロの仕事ではありません。
