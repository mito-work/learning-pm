# 当初の要件定義支援方針／方式の確定

## 確認テスト


**Q1. 要件定義の本質として、最も適切な説明はどれですか？**

A) お客様の出してきた要望を、漏れなくすべてシステム化すること。

B) 予算と時間の範囲内で、何を作り何を作らないかの「合意」を作ること。

C) 最新の技術を使って、お客様が驚くような多機能なシステムを提案すること。

**Q2. キックオフ資料の「体制図」で最も明確にすべき役割は誰ですか？**

A) 資料作成を担当する実務メンバー。

B) 最終的な合意（Go/No Go）を判断する「決定権者」。

C) プロジェクトを時々見に来る他部署の担当者。

**Q3. 「要件凍結日」を設定する最大のメリットは何ですか？**

A) 開発チームが、それ以降の変更要望を「変更管理」としてコントロールできる。

B) お客様が、凍結日まではいくらでも無制限に要望を追加できるようになる。

C) 要件定義の資料作成を、その日までにすべて終わらせて休めるようになる。

---

## 👉 **正解を確認する Q1: [ B ] / Q2: [ B ] / Q3: [ A ]**

### 【解説】

#### Q1：合意形成こそがゴール

正解は **B** です。
要望をすべて聞くと、予算オーバーや納期遅延を招きます。実務では「優先順位をつけて捨てる」という合意形成が最も重要です。

* **ポイント：** 「全部やる」は「何も決めない」のと同じです。

#### Q2：誰が船の進路を決めるか

正解は **B** です。
現場が「OK」と言っても、上層部が後から覆せば全てが白紙になります。誰が最終判断をするのかを最初に握ることが、手戻り防止の最優先事項です。

* **ポイント：** 決定権者が不在の会議はリスクであると認識しましょう。

#### Q3：プロジェクトの防波堤

正解は **A** です。
凍結日（デッドライン）がないと、開発中も延々と要望が変わり続け、プロジェクトが終わりません。Aのように「ここからはルールが変わります」と線を引くことが、炎上防止の鉄則です。

* **ポイント：** 凍結日は、お互いを守るための「約束の日」です。
