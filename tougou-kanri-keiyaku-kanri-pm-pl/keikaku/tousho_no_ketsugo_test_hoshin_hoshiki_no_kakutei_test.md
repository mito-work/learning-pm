
# 当初の結合テスト方針／方式の確定

## 確認テスト

**Q1. 結合テストの本来の目的として、最も適切なものはどれですか？**

A) プログラム1つ1つの内部ロジックが正しいか細かくチェックすること。

B) 画面やAPI、外部システムなどが正しく「連携」することを確認すること。

C) プログラムの書き方がルール（コーディング規約）通りか確認すること。

**Q2. 「方針（思想）」の説明として正しいものはどれですか？**

A) 「テスト結果をどのツールで管理するか」という具体的な手順のこと。

B) 「誰がテストコードを書くか」という役割分担のこと。

C) 「どのレベルまで品質を担保するか（業務フロー重視か、網羅重視か）」という考え方のこと。

**Q3. 結合テストの方針を「最初（当初）」に決めなければならない最大の理由は？**

A) テストの期間をできるだけ短くして、早く帰れるようにするため。

B) 責任境界や環境準備の不備による、プロジェクト後半の致命的な炎上を防ぐため。

C) プログラマーがテストコードを書く練習時間を確保するため。

---

## 👉 **正解を確認する Q1: [ B ] / Q2: [ C ] / Q3: [ B ]**

### 【解説】

#### Q1：連携の保証

正解は **B** です。
Aは「単体テスト」の役割であり、Cは「コードレビュー」の役割です。結合テストの核心は、バラバラの部品を合わせた時に「データが正しく受け渡されるか」という**インターフェース（接合部）の検証**にあります。

* **ポイント：** 「点」ではなく「線」でつなげて見るのが結合テストです。

#### Q2：方針と方式の違い

正解は **C** です。
AやBは「方式（やり方・手順）」に該当します。「方針」は、プロジェクト全体で何を優先してテストを行うかという**戦略**を指します。

* **ポイント：** 方針（ゴール）がブレると、方式（手段）がどれだけ立派でも失敗します。

#### Q3：リスクの早期回避

正解は **B** です。
結合テストでのトラブル（環境不足や仕様の食い違い）は、プロジェクトの終盤に発覚するため、修正コストが非常に高くなります。最初にルールを固定することで、手戻りを最小限に抑えます。

* **ポイント：** 「結合テストの失敗は、設計の失敗」と言われるほど、事前の準備が重要です。
