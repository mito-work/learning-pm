
# 当初の基本設計方針／方式の確定

## 確認テスト

**Q1. 「方針（スタンス）」に該当するものは次のうちどれですか？**

A) 全体構成図を先に確定させてから各機能の設計に入る。

B) システムの将来的な拡張性を考え、部品をバラバラに作る（疎結合）。

C) 週に一度、進捗レビュー会を実施して進める。

**Q2. PM（プロジェクトマネージャー）が設計思想の固定を重視する最大の理由は？**

A) プログラミング言語の最新機能を活用するため。

B) 契約範囲を明確にし、追加費用やスケジュールのリスクを管理するため。

C) 画面レイアウトをより美しくするため。

**Q3. 小規模プロジェクトにおいて、炎上を防ぐために最低限必要な「方式」の例は？**

A) 全機能のソースコードを基本設計時にすべて書く。

B) 毎日10時間のミーティングを行う。

C) 全体構成図を先に確定させ、機能単位で合意を取りながら進める。

---

## 👉 **正解を確認する Q1: [ B ] / Q2: [ B ] / Q3: [ C ]**

### 【解説】

#### Q1：スタンスとプロセスの見極め

正解は **B** です。
Bは「どういう考えで作るか」という思想（スタンス）を指します。AとCは「どう進めるか」という「方式」の話です。

* **ポイント：** 「どんな性格のシステムにするか」が方針です。

#### Q2：ビジネスを守るための防壁

正解は **B** です。
PMはビジネスの責任者です。思想が決まっていないと「どこまでが契約内か」が曖昧になり、際限ない修正依頼で赤字になるリスク（契約リスク）が高まります。

* **ポイント：** 設計思想はビジネスを守る武器になります。

#### Q3：最小限のルールで最大の結果

正解は **C** です。
小規模でも「地図（全体図）」と「合意（レビュー）」がなければ迷走します。AやBは現実的ではなく、かえって効率を下げます。

* **ポイント：** 「全体から詳細へ」が設計の鉄則です。
