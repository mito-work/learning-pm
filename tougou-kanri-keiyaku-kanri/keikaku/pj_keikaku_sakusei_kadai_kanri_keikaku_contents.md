# 【PJ計画作成】課題管理計画

> **〜問題を未然に防ぐための運用設計〜**

## 導入：なぜ「課題管理」を学ぶのか？

プロジェクト（PJ）を進めていると、必ず「あれ、これどうするんだっけ？」「このままだとマズいかも」という**モヤモヤ**が発生します。

このスキルを習得すると：

* **「突然の炎上」がなくなります：** 小さな火種のうちに消し止める力がつきます。
* **「言った・言わない」がなくなります：** 課題と決定事項を記録することで、認識のズレや記憶違いによるトラブルを防げます。
* **「やること・やらないこと」の経緯が残ります：** なぜその決断をしたのか、誰が承認したのか、判断の根拠がいつでも振り返れる状態になります。
* **顧客・ステークホルダーからの信頼が得られます：** 問題が報告されるたびに対応状況が見えることで、「このPMは任せられる」という評価につながります。
* **仕事のスピードが上がります：** 「誰が・いつまでに・何を」が決まるので、迷う時間が減ります。

逆に、課題管理を怠ると、ある日突然**「手遅れの状態」**で問題が爆発し、徹夜や謝罪に追われることになります。そして「そんな話は聞いていない」「いつ決まったのか」という水掛け論が始まります。課題管理は、プロジェクトを健康に保つための**「予防医学」**であり、チーム全員の記憶を補う**「組織の記録係」**でもあるのです。

---

## 学習目標

1. 「課題」と「障害」の違いを、中学生に教えるように説明できる。
2. 課題管理表に必要な項目と各項目の役割を説明できる。
3. 課題管理が他の管理プロセス（変更管理・障害管理・申し送り管理）とどう連携するかを説明できる。

## 本編

### ① なぜ課題を管理するのか（課題管理の目的）

**結論：人間の記憶と口頭・チャットの共有には限界がある。課題は「記録」し「一元管理」することで初めて機能する。**

課題管理が必要な理由は3つあります。

**1. 人間は覚えていられない**
プロジェクト中に発生する課題は複数あり、それぞれ担当者・期限・優先度が異なります。「あの件、どうなった？」という確認が繰り返されるのは、誰かの記憶に頼っているからです。課題は記録することで、記憶に頼らない管理ができます。

**2. 散らばっていると意味がない**
Slackに書いたこと、メールで伝えたこと、口頭で決めたこと——それぞれバラバラに存在すると「あの情報どこだっけ」が起きます。Slackは特に流れやすく、数日後には遡ることが難しくなります。課題管理表に一元化することで、誰でも・いつでも・同じ情報を見られる状態を作ります。

**3. 後回しにしたものを忘れない**
優先度が低い課題は意図的に後回しにすることがあります。しかし後回しにしたまま放置されると、期限直前に「忘れていた」が発生します。課題管理表にステータスと期限を記録しておくことで、後回しにしても追跡できます。

---

### ② 課題の正体を知る（課題と障害の違い）

**結論：課題とは「未来の問題の芽」である。**

「課題」と「障害」は似ていますが、時間の軸が違います。

| 区分 | 状態 | 例え話 |
| --- | --- | --- |
| **課題** | まだ起きていない（未来） | 「雨が降りそうだから傘を持とう」 |
| **障害** | すでに起きている（現在） | 「雨が降って服がびしょ濡れだ！」 |

**メタファー：**
「課題管理」は、キャンプで**「夜に雨が降りそうだから、今のうちにテントにカバーをかけよう」**と相談して決めておくようなものです。

---

### ③ 課題管理表の「必須項目」

**結論：担当と期限がない課題は、ただの「メモ」である。**

課題を管理する表には、以下の項目を必ず入れましょう。

| 項目 | 内容 | 役割 |
| --- | --- | --- |
| **課題ID** | 001, 002... | 名前を付ける（「あの1番の件」と呼べる） |
| **概要** | 何が起きそうか | 誰が見ても状況がわかるように書く |
| **完了基準** | 何をもって解決とするか | 「なんとなく片付いた」にならないよう、完了の定義を先に決める |
| **ステータス** | 未・進行中・完了 ※完了は移行済みも含む | 今どうなっているか一目でわかる |
| **期限** | いつまでにやるか | ゴールがないと後回しにされる |
| **優先度** | 高・中・低 | どれから手をつけるべきか決める |
| **担当者** | 誰がやるか | **「全員でやる」は「誰もやらない」と同じ** |
| **対応履歴** | 誰がいつ何をしたか | 経緯を残すことで「言った・言わない」を防ぎ、引き継ぎも容易にする |
| **障害管理に移行** | 課題が顕在化した場合にフラグを立てる | 「まだ起きていない」から「すでに起きた」に変わったタイミングを記録する |
| **変更管理に移行** | スコープや仕様の変更につながった場合にフラグを立てる | 変更管理表と紐付けて、いつ・どのような結論で・どこに移行したかを残す |
| **申し送り管理に移行** | 次回営業・次フェーズへの引き継ぎが必要な場合にフラグを立てる | ①今回スコープに入れられなかった顧客要望を次回提案のネタとして営業に引き継ぐ ②プロジェクト終了時に顧客との関係・注意点・追加案件候補を次回担当営業に渡す |

#### 課題を書くときの注意点

顧客と課題を共有する場面を想定して、最初から以下を避けた書き方をしておくと、共有時の修正が不要になります。

```
  ❌ 内部の担当者名・社内スラング
  ❌ 技術的な詳細（顧客が判断できない情報）
```

---

### ④ 課題管理の位置付け（他の管理プロセスとの関係）

**結論：課題管理は「入口」であり「振り分けの場所」。変更管理・障害管理・申し送り管理の手前にある。**

プロジェクトでは「見積もりに書かれていること以外はやらない」が基本原則です。変更が必要な場合は変更管理の手続きを踏みます。変更管理は仕様・見積もりが確定した後に機能する仕組みです。

課題管理はその手前にあり、「まだ解決策が決まっていない・振り分けが決まっていない状態」のものを受け取る場所です。

```
課題が発生する
  ↓
課題管理表に記録（ここが入口）
  ↓
 ├─ その場で解決できた ──────────────→ 完了
 ├─ 仕様・スコープの変更が必要 ──────→ 変更管理に移行
 ├─ すでに問題として顕在化 ──────────→ 障害管理に移行
 └─ 次回営業・次フェーズへの引き継ぎ → 申し送り管理に移行
```

課題管理表に入った課題は、解決されるか・他の管理プロセスに移行されるかのどちらかで「完了」になります。「ずっと課題管理表に残り続けること」は運用の失敗サインです。

### ⑤ 課題更新の3つのルール

定期的な見直し：表を「生きたもの」にする。

## まとめとネクストアクション

### 4つの重要ポイント

1. **課題管理が必要な理由は3つ：** 人間は覚えていられない・散らばると機能しない・後回しにしても追跡できる。この3点が課題管理の目的。

2. **課題管理表は項目の設計が肝：** 担当・期限だけでなく、完了基準・対応履歴・移行フラグまで最初から設計する。「担当者：全員」「完了基準：なし」の課題は機能しない。

3. **課題管理は「入口」であり「振り分けの場所」：** 課題は解決されるか・他の管理プロセスに移行されるかのどちらかで完了にする。ずっと残り続けるものは運用の失敗サイン。

4. **書き方は顧客共有を想定する：** 内部の担当者名・社内スラング・顧客が判断できない技術詳細は最初から避けて書く。
