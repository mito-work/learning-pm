# ドキュメント形式／作成ツール確定

> **〜情報の"迷子"を防ぎ、チームの視線を一つにする〜**

---

## 導入：ドキュメント設計は「事務作業」ではない

プロジェクトが始まると、大量の資料が生まれます。
しかし、ルールがなければ資料は「情報の墓場」になります。

* 「最新版がどこにあるか分からない」
* 「人によって書き方がバラバラで、何が正しいかわからない」
* 「あの決定、どこに書いてあったっけ？」

これらはすべて、ドキュメントのルールがないことで起きます。

ドキュメントには2つの役割があります。

**① チームが「今どこにいるか」を共有するナビゲーター**
**② 「いつ・誰が・何を決めたか」を証明する記録**

特に②は、前の教材で学んだ「言った・言わない」を防ぐための直接的な武器です。
正しく設計されたドキュメントがあれば、「そんな話は聞いていない」に対して、議事録・合意書・変更履歴で即座に反論できます。

このスキルを習得すると：

* **「最新版はどれ？」がなくなります：** 全員が同じファイルを見て動けます
* **「決め事の根拠」が残ります：** 誰が・いつ・何を承認したかが追跡できます
* **「炎上の証拠」も残ります：** トラブル時に自分たちを守る記録になります
* **チームの生産性が上がります：** 探す時間・確認する時間がなくなります

---

## 学習目標

1. ドキュメントのルールがないことで起きる「3つのリスク」を説明できる
2. ツール選定において重視すべき「2つの基準」を挙げられる
3. 誰でも迷わずファイルを探せる「保存場所・命名規則・バージョン管理」を設計できる

## 本編

---

### ① ルールがないと起きる「3つのリスク」

**結論：形式のバラバラは、チームの「信頼のバラバラ」に直結する。**

| リスク | 具体的な実態 |
| --- | --- |
| **認識のズレ** | Aさんは「納期」、Bさんは「リリース日」と書く。同じ日のはずが、会議で食い違う |
| **レビューの停滞** | 毎回構成が違うため、「中身」より「どこを見ればいいか」に時間を取られる |
| **品質のムラ** | 詳しい人と雑な人で資料の細かさが全然違い、判断の基準がブレる |

> **メタファー：**
> 料理のレシピ本で、あるページは「グラム表記」、次のページは「コップ一杯」とバラバラだったら、同じ味を作るのは不可能ですよね。ドキュメントも同じです。「書き方の統一」は、チームが同じゴールに向かうための共通言語です。

---

### ② ツール選定の「2つの基準」

**結論：「共同編集できるか」と「履歴が残るか」——この2つだけで選ぶ。**

ツールが統一されていないと、情報の「上書き消失」や「先祖返り（古い版に戻る）」が日常化します。

**なぜ「共同編集」が重要か：**
メール添付のファイルは、誰かが開いて編集している間、他の人が別の版を作ってしまいます。気づいたときには「どれが最新か」が誰にもわからない状態になります。

**なぜ「履歴管理」が重要か：**
「誰がいつ変えたか」がわかると、「あの変更は誰の判断か」が追跡できます。これは課題管理と同じく「言った・言わない」を防ぐための記録です。

| 用途 | 推奨ツール例 | 選定のポイント |
| --- | --- | --- |
| **文書作成** | Word / Google Docs | 変更履歴・コメント機能で誰が何を変えたか追跡できる |
| **表計算** | Excel / Google Sheets | 同時編集可能・ロック機能で誤上書きを防げる |
| **情報集約** | Notion / Google Drive | 「一箇所」で全員が最新情報を参照できる |

**NG例：**
* メールの添付ファイルで共有（版が分散する）
* 個人PCに保存（担当者が不在のとき誰もアクセスできない）
* チャットの流れの中にファイルを投げる（後から探せない）

---

### ③ 「名前」と「場所」のルール設計

**結論：ファイルの名前と置き場所は、プロジェクト開始時に全員で決める。**

#### 保存場所のルール

```
推奨構成の例：

📁 [プロジェクト名]/
  📁 00_管理/         ← 計画書・議事録・課題管理表
  📁 01_要件/         ← 要件定義書・スコープ合意書
  📁 02_設計/         ← 設計書・画面仕様
  📁 03_テスト/       ← テスト仕様書・テスト結果
  📁 99_Archive/      ← 古いバージョンの退避場所
```

「Archive フォルダ」を最初から作っておくことで、最新版フォルダには常に「今使うファイル」だけが入った状態を保てます。

#### 命名規則

```
[プロジェクト名]_[書類の種類]_[日付]_[バージョン]

例：ABCシステム_要件定義書_20260401_v1.2
```

日付とバージョンを入れることで、「これが最新版かどうか」がファイルを開かずにわかります。

---

### ④ バージョン番号の「共通言語」

**結論：数字を見れば「状態」がわかるようにする。**

| バージョン | 意味 | 使うタイミング |
| --- | --- | --- |
| **v0.x** | ドラフト（下書き） | 社内レビュー中・未承認の状態 |
| **v1.0** | 正式版（初回承認） | 顧客または上司の承認を得た状態 |
| **v1.x** | 軽微な修正 | 正式版に対する小さな変更 |
| **v2.0** | 大幅改訂 | 構成や内容を大きく作り直した場合 |

「v0.xのまま顧客に送らない」「承認前はドラフトと明示する」——この習慣だけで、「まだ確定していない資料が一人歩きする」トラブルを防げます。

## まとめとネクストアクション

### 3つの重要ポイント

1. **形式は品質：** 書き方・用語を揃えることで、ミスとストレスを減らす。「バラバラ」は「信頼のバラバラ」に直結する
2. **ツールは2基準で選ぶ：** 「共同編集」と「履歴管理」——この2つを満たさないツールは使わない
3. **ルールを明文化して共有：** 口頭で説明しても守られない。計画書に「命名規則・保存場所・バージョン番号の意味」を書き込む

### 明日からできるアクション

> **今関わっているプロジェクトの共有フォルダに「00_管理」と「99_Archive」フォルダを作り、最新版だけが見える状態に整理する。**
