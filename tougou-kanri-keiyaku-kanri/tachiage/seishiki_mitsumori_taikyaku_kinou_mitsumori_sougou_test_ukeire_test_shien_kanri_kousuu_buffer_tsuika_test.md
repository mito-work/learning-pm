# 正式見積：【対客】機能見積に総合テスト／受入テスト支援／管理工数／バッファ追加

## 確認テスト

**Q1. 見積の中に「総合テスト工数」を別で入れる理由として、最も適切なものはどれですか？**

A) プログラミング作業が早く終わった時の暇つぶしにするため。

B) 機能単体ではなく、システム全体が連携して正しく動くかを確認するため。

C) 開発者のミスを隠すための予備時間を確保するため。

**Q2. 顧客から「管理工数が高い。削れないか？」と言われた時の対応として正しいものはどれですか？**

A) 「そうですよね」と同意し、管理工数をゼロにしてその分残業してカバーする。

B) 「これは会社のルールなので削れません」と、理由を説明せずに突っぱねる。

C) 「管理工数は、品質と納期を担保するための司令塔の役割です。削るとプロジェクトが迷走し、納期遅延のリスクが高まります」と説明する。

**Q3. 「バッファ」を顧客に説明する際の、最も納得感の高い伝え方はどれですか？**

A) 「何が起こるか分からないので、とりあえず2割乗せておきました」

B) 「現時点で確定しきれていない要件や、外部要因による不確実性を吸収するための調整枠です」

C) 「値引き交渉をされた時のために、多めに見積もっておきました」

---

## 👉 **正解を確認する Q1: [ B ] / Q2: [ C ] / Q3: [ B ]**

### 【解説】

#### Q1：全体最適の視点

正解は **B** です。
開発者は自分の作った機能が動くと満足しがちですが、実務では「他の機能との結合」でトラブルが起きます。

* **ポイント：** 「単体テストは開発に含むが、結合・総合テストは別工程」と分けることで、見積の透明性が上がります。

#### Q2：管理の価値を正しく伝える

正解は **C** です。
Aはチームが崩壊し、Bは顧客の信頼を失います。「管理＝手を動かしていない無駄な時間」と思っている顧客に対し、それが「プロジェクトの事故を防ぐための不可欠な投資」であることをプロとして説明しましょう。

* **ポイント：**

##### 1. 顧客への納得感（表向きのロジック）

プロジェクトを無事に成功させるためには、これだけ多くの要素を同時にコントロールしなければなりません。
「管理を削る＝品質や納期が崩れる」という因果関係を、対象ごとに明確に伝えます。

* **進捗管理・課題管理を削る** ➔ トラブルの発見や遅れへの対策が遅れ、最終的な**納期遅延**を招く。
* **変更管理・品質管理を削る** ➔ 仕様がブレて手戻り（作り直し）が発生し、著しい**クオリティ低下**を招く。
* **リソース・コミュニケーション管理を削る** ➔ チーム内の情報共有や人員配置が不全に陥り、**現場が崩壊**する。

##### 2. 自社内のリアル（生産性向上の本質）

これほど多岐にわたる管理業務（**進捗、課題、変更、品質、リソース・コミュニケーション**）は、決してPM一人が抱え込むものではありません。ここがプロジェクトの利益率を上げるための鍵になります。

* **管理はチーム全員で行うもの：**
  提示されたこれら全ての管理は、本来チーム全員で共通のルールを守り、バトンを繋ぐようにして回すものです。
* **メンバーの意識でコストが変わる：**
  現場の「管理に対する意識」が高く、ルールが浸透しているチームほど、PMが軌道修正や確認に割く労力（コスト）は減り、プロジェクトは自律的にスムーズに回ります。
* **浮いた工数は「自社の利益」に：**
  顧客に見せる「管理の価値（見積もり）」はプロの仕事としてしっかり担保しつつ、内部の仕組み化（チームの成熟）によって実際の管理工数を浮かせる。これこそが、開発現場における「生産性向上や効率改善」の本当の意味です。

#### Q3：不確実性の数値化

正解は **B** です。
AやCは「根拠がない」と思われ、不信感に繋がります。バッファは「保険」ではなく、現状の「曖昧さ」に対するコストです。

* **ポイント：** バッファの理由を「要件の不確定さ」や「環境差異」と紐づけると、顧客は「じゃあ要件を早く固めよう」という協力的な姿勢になります。
