# 超概算：【対客】見積作成

## 1. 導入：なぜ「ざっくり」が重要なのか？

プロジェクトの始まりに、お客さまから「結局、いくらくらいかかるの？」と聞かれて困ったことはありませんか？
この「超概算」を正しく使いこなせると、以下のメリットがあります。

* **無駄な作業の回避：** 予算が全く合わない案件に時間を割かずに済みます。
* **信頼の構築：** 「後から金額が跳ね上がった！」というトラブルを防げます。
* **意思決定の加速：** お客さまが「やる・やらない」を即座に判断できるようになります。

---

## 2. 学習目標

本テキストを読み終えると、以下の状態になれます。

* 超概算（ROM）の役割を、**専門用語を使わず**に説明できる。
* 10MM（10人月）の案件を、**お客さまが納得する形**で提示できる。

---

## 3. 本編

### ① 結論：超概算は「当てるため」ではなく「外さないため」にある

超概算の目的は、正確な金額を出すことではありません。
**「このくらいの予算感で、認識にズレはないですか？」**という方向性を確認するための道具です。

> **【例え話：家づくり】**
> 注文住宅で「キッチンをこだわりたい」と言われた時、「1,500万円で建ちます」と断言するのは危険です。「だいたい1,200万〜1,800万円くらいですが、その予算感で進めて大丈夫ですか？」と聞くのが超概算です。

### ② 精度：「上限」で提示する

PMBOK（プロジェクト管理の世界標準）では、超概算の誤差を ±30〜50% 程度と定義しています。

| 項目 | 内容 |
| --- | --- |
| **呼び方** | 超概算（ROM：Rough Order of Magnitude） |
| **情報の量** | 少ない（ふわっとしている） |
| **誤差の幅** | ±30〜50%（かなり広め） |

**【アクション】**
一点の数字（例：1,000万円）でも、幅（例：800万〜1,200万円）でもなく、**上限（例：上限1,200万円）**で提示しましょう。
幅で伝えると顧客は下限（800万円）で計画を立て、後から「話が違う」になります。

### ③ 単位の変換：MM（人月）を「日常の言葉」に変える

プロ同士では「10MM（10ヶ月分の作業量）」で通じますが、お客さまには伝わりません。

* **社内：** 「この案件は10MMくらいですね」
* **対客：** 「**2人で作業して、5ヶ月くらいかかる**規模感です」

> **一度手を止めて考えてみましょう：**
> あなたがお客さまだとしたら、「10MMです」と言われるのと「100万円の人が10ヶ月分働く量です」と言われるの、どちらがイメージしやすいですか？

### ④ 前提条件を明示する：超概算に含める「約束事」を定義する

超概算を作成する段階で、「前提条件」を明確に定義します。
前提が変われば金額も変わることを、顧客への打診前に整理しておきます。
前提条件には3つの種類があります。

**❶ 数値・範囲の前提**

システム規模や対象範囲に関する数値的な前提です。

```
例：
・システム利用ユーザー数：社内ユーザー100名以下
・外部連携：既存の基幹システムとの連携1件（APIあり）
・開発期間：6ヶ月
・運用保守は別途見積もり
```

**❷ シナリオ前提**

どのような業務シナリオを対象とするかも、前提条件になります。
シナリオが変われば必要な機能が変わり、金額が変わります。

```
例（受発注管理システムの場合）：
  シナリオ前提：「受注は社内担当者が手動で入力する」
  ↓ → 入力フォーム・承認ワークフロー機能が必要

  シナリオが変わった場合（顧客が直接入力する）：
  「顧客ポータルから直接発注できる」
  ↓ → 顧客向けUI・外部アクセス認証・セキュリティ強化が追加で必要 → 金額が変わる
```

**❸ やらないことの前提（スコープ外の明示）**

**「やらないこと」を明示することが見積もりの生命線**です。
含まれていないことを言わないと、顧客は「含まれている」と思います。

```
やらないことの前提条件（例）：
  ・性能テスト・障害テスト（負荷テスト・フェイルオーバー確認）
  ・インフラ増強（サーバースペックアップ・ネットワーク改修）
  ・本システムの保守（リリース後の運用・障害対応）
  ・脆弱性診断（セキュリティ診断・ペネトレーションテスト）
  ・オペレーター向けトレーニング（操作研修・マニュアル作成）
```

「やらない」は「できない」ではなく「今回のスコープに含まれない」という意味です。
必要であれば追加見積もりで対応できることも一言添えると、顧客の安心感が高まります。

### ⑤ 前提条件の変更を顧客に予告する

超概算を打診する際、「前提が変わった場合は金額が変動する」ことを最初に伝えます。
これにより、変更報告が「予告通りの話」になります。

```
最初から言っておく言葉：
「超概算のため、要件定義を進める中で前提条件が変わった場合は
 金額が変動することがあります。
 その場合は都度ご報告し、ご判断をいただく形で進めます。」
```

## 4. 実践：10MM案件の見積シミュレーション

10MM（単価100万円と想定）の案件を提示する場合、以下の3ステップで構成します。

1. **根拠を添える：** 「過去の似たようなシステムがこのくらいでした」
2. **上限で出す：** 「上限1,200万円程度と予測されます」
3. **前提を添える：** 「要件が確定すれば、この上限内に収めます。前提が変わった場合は都度ご報告します」

---

## 5. まとめ

1. **超概算は「会話のキャッチボール」：** 予算の壁を突破するための道具。
2. **数字は「上限」で出す：** ±30〜50%のブレをあらかじめ上限に織り込む。
3. **前提条件を定義して言い添える：** 数値範囲・シナリオ・やらないことを明示し、「前提が変わったら金額も変わる」と伝える。
4. **要件定義後に正式見積を出す：** 超概算はあくまで最初の方向感。段階的に精度を上げていく。
