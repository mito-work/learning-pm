# 統合／契約管理（PM単独） > 実行・監視・コントロール

## 定期的な課題更新／顧客との課題共有／見直し

---

## 導入

### このスキルを身につけると、何が変わるか

課題管理表を作った。でも、気づいたら誰も更新していなかった。
顧客との打ち合わせで「あの件、どうなってますか？」と聞かれ、
「確認して折り返します」と言ってしまった——

課題管理表は「作ること」ではなく「使い続けること」が本質です。
更新されない課題管理表は、「情報の墓場」になるだけです。

このスキルを学ぶことで：
- 課題が「放置される」状態をなくせる
- 顧客に「いつでも状況を説明できる」自信がつく
- 「言った・言わない」「決めたはずなのに」が消える
- 定例会が「報告会」から「意思決定の場」に変わる

---

## 学習目標

このテキストを読み終えると、以下ができるようになります。

1. **課題の「更新タイミングと更新内容」を習慣として説明できる**
2. **顧客への課題共有で「何を見せ・何を伝えるか」を判断できる**
3. **課題の見直しサイクルを設計し、チームで運用できる**

## 本編

### Section 1：なぜ「定期更新」が必要か

**一言でいうと：課題は「生き物」です。放置すると腐ります。**

植物で考えてみましょう。
水をやらない植物はしおれ、やがて枯れます。
課題管理表も同じです。
更新しなければ、情報が古くなり、誰も信頼しなくなります。
「どうせ古い情報しか載っていない」と思われた瞬間、課題管理表は機能を失います。

**更新が止まると起きること：**

| 症状 | 結果 |
|-----|------|
| ステータスが「進行中」のまま放置される | 「終わったのか・まだなのか」誰もわからない |
| 期限が過ぎた課題が残り続ける | 「どれが本当に重要か」が判断できない |
| 新しい課題が追加されない | 「知らなかった」「聞いていない」が頻発する |
| 誰も開かなくなる | 課題管理表が形骸化し、別の管理方法が乱立する |

---

### Section 2：いつ課題を上げるか

**一言でいうと：課題は気づいたそのタイミングで登録する。**

課題は発生したとき・気づいたときに都度登録します。

#### 登録するタイミング

```
課題を上げるタイミング：
  ✅ 打ち合わせ中に未解決のまま持ち越された事項が出たとき
  ✅ 作業中に「これ、どうするんだっけ？」という判断が必要な事項が生じたとき
  ✅ 顧客・関係者への確認が必要な事項が生じたとき
```

#### 登録時の書き方ルール

課題を登録するときは、以下のルールで書きます。確認・判断が必要な項目は、後の定例確認のタイミングで埋めます。

| 項目 | 登録時のルール |
|------|-------------|
| **ステータス** | 「未着手」で登録する |
| **期限** | 決まっていれば書く。決まっていなければ空欄でOK |
| **担当者** | 担当してほしい人を書く |
| **優先度** | 登録時は書かなくてOK。定例確認時に他の課題との比較で決める |
| **対応履歴** | 登録時はなし。対応が始まったら記録する |

> ※ 各項目の定義は「【PJ計画作成】課題管理計画」の課題管理表（必須項目）を参照

**更新するのは「担当者自身」です。**
PMが全員の課題を代わりに更新するのは非現実的です。
「担当者が自分の課題を更新する」ルールを最初に決めておきます。

---

### Section 3：課題が増えすぎる前に——「登録基準」と「棚卸し」

**一言でいうと：「とりあえず登録」が課題管理を死なせる。登録基準を最初に決める。**

#### よくある失敗：「とりあえず登録」で課題管理表が機能しなくなる

プロジェクトが進むにつれ、「なんか気になる」「念のため記録しておこう」という課題が積み上がっていきます。
気づいたときには50件以上の課題が並び、どれが本当に重要かわからない状態になります。

こうなると、チームの誰も課題管理表を開かなくなります。
「どうせ古い情報ばかり」「自分の課題がどこにあるかわからない」——これが課題管理の死です。

**ただし、漏れるくらいならとりあえず登録してOKです。**
登録のハードルを上げすぎると、大事な課題が抜け落ちます。「とりあえず登録して、有識者に都度レビューしてもらいながら、定例確認のタイミングで加筆・修正・マージする」という運用にすることで、漏れを防ぎながら課題管理表をきれいに保てます。有識者レビューと定例でのチェック・マージがセットで機能することが前提です。

#### ① 登録基準を明文化する

「何でも登録しなければいけない」という暗黙のプレッシャーが「とりあえず登録」を生みます。
プロジェクト開始時に、以下のような登録基準をチームで合意しておきます。

```
課題管理表に登録するもの：
  ✅ 担当者と期限が決まるもの
  ✅ スコープ・納期・品質に影響する可能性があるもの
  ✅ 顧客の意思決定が必要なもの

課題管理表に登録しないもの：
  ❌ 「〇〇を確認する」レベルの日常タスク → チャット・タスクツールで管理
  ❌ アイデアレベルの「気になること」→ 別途メモや議事録に記録
```

登録基準が明確になると、「これは課題管理表に入れるべきか」という迷いが消えます。

> **「完了基準」が言語化できないものは、まだ登録しない。**
> 「なんとなく気になる」という段階では、完了基準を定義できないため登録は早いです。完了基準（何をもって解決とするか）が言語化できた段階で初めて登録します。これにより課題管理表が「気になることメモ」にならずに済みます。

#### ② 週次の「棚卸し」で課題を整理する

課題管理表は増える一方ではいけません。
定期的に「本当にこの課題はまだ必要か？」を確認する「棚卸し」が必要です。

| 状態 | 対応 |
|-----|------|
| 2週間以上ステータスが変わっていない | 担当者に状況確認。「保留」に変更して理由を記載 |
| 1ヶ月以上「保留」のまま | 「本当に必要か」を判断。不要なら「クローズ（対応不要）」 |
| 状況が変わって不要になった | 「対応不要」の理由を一行書いてクローズ |

**「クローズ（対応不要）」は失敗ではありません。**
状況の変化によって不要になった課題をきちんとクローズすることは、課題管理表を「生きた状態」に保つための重要な運用です。

#### ③ 優先度で「今週触らないものは見えなくする」

課題が多い場合、Low優先度の課題はフィルタリングして表示しない運用も有効です。

```
週次レビューで見る範囲：
  ✅ Critical / High：必ず確認
  ✅ Medium：止まっているものだけ確認
  ❌ Low：今週のレビューでは表示しない（月次でまとめて確認）
```

「登録したまま忘れる」より「登録して意図的に今週は見ない」方が健全です。
「Lowに設定 = 今週は対応しない」という判断をしていることを、チームで共有しておきます。

### Section 4：いつ課題を確認するか

**一言でいうと：毎日個人で確認する習慣と定例会での全員確認で、課題が放置されない状態を作る。**

課題の確認には2段階あります。

#### ① 個人の日次確認

登録は都度でよいですが、確認は毎日行います。30秒でも構いません。

```
確認すること：
  ・自分が担当している課題のステータスに変化があるか
  ・今日アクションが必要な課題があるか
  ・期限が近い課題がないか
```

#### ② 定例会での全員確認

定例会の度に課題管理表を全員で確認します。自分では把握できていても、他のメンバーに伝わっていないことがあります。欠席メンバーへの共有にもなります。

```
定例会での確認内容：
  ・前回からのステータス変化を全員で確認する
  ・担当者と期限を全員の認識に合わせる
  ・優先度を他の課題との比較で見直す
  ・新規課題の追加と加筆・修正を確認する
```

全員が自律的に更新・確認できている状態になれば、定例での確認時間は短縮・省略できます。
定例は「抜けを防ぐための場」であり、「管理者が報告を受ける場」ではありません。

#### 確認項目のチェックリスト

| 確認項目 | 確認ポイント |
|--------|-----------|
| **ステータス** | 未着手・進行中・完了・保留のどれかになっているか |
| **期限** | 変更があれば理由とともに更新しているか |
| **対応履歴** | 「何をしたか・何が決まったか」が一行でも書かれているか |
| **担当者** | 担当が変わった場合に反映されているか |
| **優先度** | 他の課題との比較で見直されているか |

### Section 5：顧客への共有——「何を見せ・何を伝えるか」

**一言でいうと：課題を隠すとあとで爆発する。でも全部見せると不安にさせる。**

顧客への課題共有には「さじ加減」が必要です。

#### 共有の基本原則

**隠してはいけない理由：**
顧客が関係する課題を内部だけで抱えると、
後から「なぜ早く教えてくれなかったのか」と信頼を失います。
特に「顧客側の決断が必要な課題」は、即座に共有が必要です。

**全部見せない理由：**
内部の細かい技術課題・チームの作業調整を全部見せると、
顧客は「こんなに問題があるのか」と不安になります。
顧客が不安になると、過度な介入・追加確認が増えてプロジェクトが遅れます。

#### 顧客共有の分類基準

| 種類 | 共有すべきか | 理由 |
|-----|-----------|------|
| 顧客の意思決定が必要な課題 | **必ず共有** | 顧客が動かないと解決しない |
| スコープ・納期に影響する課題 | **必ず共有** | 契約上の合意に関わる |
| 内部の技術的な課題 | 解決してから報告 | 顧客には「対応済み」として伝える |
| チームの作業分担・調整 | 共有不要 | 顧客が関与する性質のものではない |

#### 顧客共有のタイミングと形式

```
タイミングの目安：
・週次の定例会で課題一覧を共有（1〜2週間サイクル）
・Criticalな課題は発生した当日に個別連絡
・月次で課題の傾向（増減・解決率）をサマリーとして報告
```

**共有する資料の見せ方：**

内部用と外部用でファイルを分ける必要はありません。課題管理表の「対象（顧客確認/内部確認）」列でフィルタリングして、顧客確認の行だけ共有します（「対象」列の定義は「【PJ計画作成】課題管理計画」を参照）。

顧客向けの課題共有では、すべての列を見せる必要はありません。

```
顧客向け課題共有の推奨項目：
  ✅ 課題の概要（何が課題か）
  ✅ 影響（何に影響するか・なぜ顧客に関係するか）
  ✅ 現在の対応状況（今どうなっているか）
  ✅ 顧客への依頼事項（決めてほしいこと・確認してほしいこと）
  ✅ 期限（いつまでに回答・決定が必要か）
```

### Section 6：クローズの「明確な基準」

**一言でいうと：「なんとなく終わった」はクローズではない。「何が決まったから完了」と書く。**

課題のクローズは、記録として最も重要な瞬間です。
「完了」にするときは、必ず以下を残します。

```
クローズ時に記録すること：
・何が決まったか（決定内容）
・誰が承認したか（承認者）
・いつ決まったか（決定日）
・次の課題・アクションはないか（後続タスクの有無）
```

**クローズの例（良い例）：**

```
課題：外部連携の仕様が未確定
ステータス：完了
対応コメント：2026/06/15 顧客の田中様より仕様書を受領。
              連携方式はAPI方式で確定。
              設計書への反映はエンジニアの鈴木が6/20までに対応。
```

**クローズの例（悪い例）：**

```
課題：外部連携の仕様が未確定
ステータス：完了
対応コメント：解決しました
```

悪い例では、「何が決まったか」「誰が決めたか」が残りません。
3ヶ月後に「あの仕様どうなってましたっけ？」と言われたとき、
記録がなければ答えられません。

### Section 7：見直しサイクルの設計

**一言でいうと：「見直す場」を最初からスケジュールに入れる。**

見直しは「やろうと思えばできる」では定着しません。
定例会のアジェンダに最初から組み込むことで、
「課題を見直す時間」を確保します。

**週次定例会の課題レビュー（15分）のアジェンダ例：**

```
① 前回からのアップデート確認（5分）
  ・完了になった課題をクローズ確認
  ・期限が変わった課題の理由を確認

② 止まっている課題の確認（5分）
  ・1週間以上ステータスが変わっていない課題を確認
  ・誰がいつまでに何をするかを再確認

③ 新規課題の追加（3分）
  ・今週新たに気づいた課題を全員で共有・追加

④ 優先度の見直し（2分）
  ・状況変化で優先度が変わった課題を調整
```

この15分を習慣にするだけで、課題が「放置」から「管理」に変わります。

## まとめとネクストアクション

### 4つの重要ポイント

1. **課題は「作るだけ」では意味がない。登録は都度、確認は毎日**
   課題は気づいたタイミングで都度登録し、毎日30秒確認する習慣をつける。
   定例会では全員で認識を合わせ、抜けをなくす。自律的にできれば定例の確認時間は短縮できる。

2. **「とりあえず登録」は定例でマージ・修正する前提でOK**
   登録のハードルを上げすぎると課題が漏れる。まず登録して、定例確認のタイミングで加筆・修正する運用が現実的。
   ただし、登録基準（スコープ・納期・顧客判断に関わるもの）は最初に合意し、不要なものは「対応不要」でクローズする。

3. **顧客に共有するのは「顧客が関係する課題だけ」。隠すより、適切に見せる**
   意思決定が必要・スコープや納期に影響する課題は即共有。
   内部の技術課題は解決してから報告。この分類が顧客との信頼を作る。

4. **クローズは「何が決まったか」を書いて初めて完了**
   「完了」にする瞬間こそ、最も重要な記録のタイミング。
   決定内容・承認者・決定日を残すことで、未来の「言った・言わない」を防ぐ。

### 明日からできるネクストアクション

> **今の課題管理表を開き、「1週間以上更新されていない課題」を全員で確認する時間を、次の定例会のアジェンダに15分追加する。**
