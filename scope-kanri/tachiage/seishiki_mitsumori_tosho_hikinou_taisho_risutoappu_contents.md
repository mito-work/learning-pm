# スコープ管理 > 立ち上げ

## 正式見積：当初非機能／対象のリストアップ

---

## 導入

### このスキルを身につけると、何が変わるか

「見積もりを出したのに、後から『セキュリティ対応も含まれると思っていた』と言われた」
「対象システムの範囲が曖昧なまま進んで、途中から想定外のシステムへの改修が発生した」
「機能の工数しか見積もっていなかったので、性能テストや負荷試験の工数が丸ごと漏れていた」——

見積もりのミスは、多くの場合「機能」しか考えていないことから起きます。
システム開発には機能要件（何ができるか）と同じくらい、非機能要件（どう動くか）と対象範囲（どこまでやるか）の整理が必要です。
このスキルは、**正式見積フェーズで「非機能要件」と「対象のスコープ」を漏れなくリストアップし、見積もりの抜け漏れを防ぐ**技術です。

このスキルを学ぶことで：
- 非機能要件の見落としによる後工程の工数増加を防げる
- 対象範囲が曖昧なまま進むスコープクリープを計画段階で防げる
- 「言った・言わない」のトラブルが起きにくい明確なスコープ合意ができる
- PLへの依頼に「非機能要件」の確認を含められる

---

## 学習目標

このテキストを読み終えると、以下ができるようになります。

1. **非機能要件の主要カテゴリを挙げ、プロジェクトに必要な項目をリストアップできる**
2. **対象スコープ（システム・業務・ユーザー）を明確に定義し、スコープ外も明示できる**
3. **リストアップした内容を顧客と合意するための確認ができる**

## 本編

---

### Section 1：なぜ「機能」だけを見積もると失敗するのか

**一言でいうと：システム開発の工数は「機能を作る工数」と「機能を安全・快適に動かすための工数」の両方が必要だ。**

機能要件だけを見積もって起きる典型的な問題を見てみましょう。

```
【機能のみ見積もったときに起きること】

  見積もり時点で考慮した工数：
    機能A（ユーザー管理）：10人日
    機能B（データ検索）：15人日
    機能C（帳票出力）：8人日
    合計：33人日

  後から発覚した工数：
    セキュリティ対応（認証・権限・ログ）：8人日
    性能改善（検索が重い・タイムアウト対応）：10人日
    障害対応・ログ設計：5人日
    ブラウザ対応・スマホ表示対応：6人日
    合計：29人日（≒最初の見積もりと同規模）

  結果：見積もりが90%増しになる
```

この「後から出てくる工数」の多くは、非機能要件に関するものです。
機能そのものの開発ではなく、「機能を安全に・速く・安定して動かすための作業」が漏れています。

---

### Section 2：非機能要件のリストアップ——主要カテゴリと確認ポイント

**一言でいうと：非機能要件は「SUPAR（性能・セキュリティ・可用性・保守性・操作性）」の5カテゴリで整理する。**

非機能要件を漏れなく整理するために、代表的なカテゴリと各カテゴリで確認すべき内容を押さえます。

| カテゴリ | 主な確認項目 | 典型的な工数が漏れるポイント |
|--------|-----------|----------------------|
| **性能（Performance）** | レスポンス時間・同時接続数・データ量・バッチ処理時間 | 性能テスト・負荷試験・チューニング工数 |
| **セキュリティ（Security）** | 認証方式・権限設計・ログ・暗号化・脆弱性対応 | セキュリティ設計・診断対応・コードレビュー工数 |
| **可用性（Availability）** | 稼働率・障害復旧時間・バックアップ方式 | 冗長化設計・障害テスト・監視設計工数 |
| **保守性（Maintainability）** | ログ設計・エラーハンドリング・コード規約・ドキュメント | ログ実装・コードレビュー・ドキュメント作成工数 |
| **操作性（Usability）** | 対応ブラウザ・スマホ対応・アクセシビリティ | クロスブラウザテスト・レスポンシブ対応工数 |

#### 顧客への確認の仕方

非機能要件は顧客から自発的に「○○が必要です」と言ってくれることはほとんどありません。
PMから「これはどうしますか？」と問いかけることが必要です。

```
非機能要件の確認例（性能）：
「検索機能についてですが、同時に何人くらいのユーザーが
 使う想定ですか？また、検索結果が表示されるまで
 どのくらいの時間を許容できますか？
 ユーザー数・応答時間によって設計と工数が変わります。」

非機能要件の確認例（セキュリティ）：
「このシステムで扱う情報の機密レベルはどのくらいですか？
 社外秘情報・個人情報が含まれますか？
 セキュリティの要求水準によって設計の方針が変わります。」
```

### Section 3：対象のリストアップ——「どこまでやるか」を明確にする

**一言でいうと：「何を作るか」だけでなく「どのシステム・業務・ユーザーが対象か」を境界線として明確にする。**

「対象のリストアップ」は、プロジェクトの境界線を引く作業です。

#### リストアップすべき対象の種類

```
① 対象システム
  ・今回新規構築するシステム
  ・改修・連携するシステム（既存システム）
  ・データ移行が必要なシステム
  ・対象外のシステム（明示的にスコープ外と合意する）

② 対象業務プロセス
  ・今回の開発でカバーする業務
  ・自動化・効率化の対象
  ・対象外の業務（手動のまま残す業務）

③ 対象ユーザー・部門
  ・このシステムを使う部門・役割
  ・管理者・一般ユーザーの区別
  ・対象外のユーザー（他部門・外部ユーザーなど）

④ 対象データ
  ・新規作成・管理するデータ
  ・既存データから移行するデータ
  ・対象外のデータ（移行しないデータ）
```

#### 「スコープ外」の明示が重要な理由

スコープのリストアップで最も重要なのは、**「やらないこと」を明示すること**です。

```
【スコープ外を明示しない場合】
  見積もり時点のスコープ：「○○システムの構築」
  ↓
  開発途中に顧客から：
  「△△の機能も入れてほしい」
  「✕✕のシステムとも連携してほしい」
  「●●の既存データも移行してほしい」
  ↓
  「見積もりに含まれていると思っていました」
  → スコープクリープ発生・追加費用の交渉が難航

【スコープ外を明示した場合】
  「今回のスコープ：○○。スコープ外：△△・✕✕」
  ↓
  顧客から追加要望が来たとき：
  「こちらはスコープ外でご合意いただいていましたが、
   追加する場合の工数・費用をお見積もりします」
  → 追加費用の交渉に根拠ができる
```

### Section 4：リストアップの実践——テンプレートの使い方

**一言でいうと：毎回ゼロから考えず、チェックリスト形式のテンプレートで漏れを防ぐ。**

正式見積フェーズでのリストアップは、テンプレートを使って機械的に確認することで漏れを防ぎます。

#### 非機能要件チェックリスト（簡易版）

```
□ 性能
  □ 同時接続ユーザー数（想定：___人）
  □ 画面レスポンス時間（目標：___秒以内）
  □ バッチ処理時間（目標：___時間以内）
  □ データ量（初期：___件、3年後想定：___件）

□ セキュリティ
  □ 認証方式（ID/PW・SSO・多要素認証）
  □ 権限設計（役割別アクセス制御の有無）
  □ 取り扱いデータの機密レベル（個人情報・社外秘など）
  □ セキュリティ診断の要否

□ 可用性
  □ 稼働時間（24時間・営業時間内など）
  □ 許容停止時間（計画停止・障害時）
  □ バックアップ頻度・保存期間

□ 保守性
  □ 運用ログの要件
  □ エラー通知の要件
  □ ドキュメントの範囲（設計書・操作マニュアルなど）

□ 操作性
  □ 対応ブラウザ・バージョン
  □ モバイル対応の要否
  □ アクセシビリティ対応の要否
```

#### 対象スコープ確認チェックリスト（簡易版）

```
□ 対象システム
  □ 新規構築するシステム・画面
  □ 既存システムとの連携（連携先リスト）
  □ データ移行の有無と対象
  □ 明示的なスコープ外システム

□ 対象業務
  □ 今回カバーする業務プロセス
  □ 対象外の業務プロセス

□ 対象ユーザー
  □ 利用部門・役割
  □ 対象外のユーザー

□ 対象データ
  □ 移行するデータ・しないデータ
  □ マスタデータの準備（誰がいつ準備するか）
```

### Section 5：リストアップ後の顧客との合意

**一言でいうと：リストアップは「PMだけで作って終わり」ではない。顧客と合意してはじめてスコープになる。**

リストアップした非機能要件と対象スコープは、顧客に確認・合意を取る必要があります。

#### 合意の取り方

```
「整理した内容をご確認いただけますか。

 今回のプロジェクトの対象は○○と整理しています。
 スコープ外については△△と整理していますが、
 認識の違いがあればご指摘ください。

 非機能要件については
 ・性能：同時接続○○人、レスポンス○秒以内
 ・セキュリティ：○○方式での認証
 という方針で進めようとしていますが、よろしいですか？

 この内容を正式見積もりの前提条件として
 扱わせていただきます。」
```

**「正式見積もりの前提条件」という言葉が重要です。**
後から「そんな話はしていない」となったとき、「○月○日に合意した前提条件に基づいて見積もっています」と示せる記録が守りになります。

## まとめとネクストアクション

### 3つの重要ポイント

1. **見積もりは「機能要件」だけでは完成しない。非機能要件（性能・セキュリティ・可用性・保守性・操作性）を必ずセットでリストアップする**
   非機能要件の工数は機能要件の工数に匹敵することがある。
   「後から出てきた」では遅い。正式見積フェーズで確認することが必須。

2. **「やること」だけでなく「やらないこと（スコープ外）」を明示的に合意する**
   スコープ外を明示しないと「含まれると思っていた」というトラブルが必ず起きる。
   スコープ外の明示が、後の追加費用交渉の根拠になる。

3. **リストアップした内容は顧客との合意を経て「前提条件」にする**
   PMだけで作ったリストは「PMの認識」にすぎない。
   顧客と合意した瞬間に「スコープの合意書」になる。
