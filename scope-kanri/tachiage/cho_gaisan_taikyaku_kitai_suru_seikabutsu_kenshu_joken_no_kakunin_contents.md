# スコープ管理 > 立ち上げ

## 超概算：【対客】期待する成果物／検収条件の確認

---

## 導入

### このスキルを身につけると、何が変わるか

「ソースコードも納品してほしかったのに、言われていないからと渡してもらえなかった。」
「設計書なんて必要ないと思っていたら、後から『ドキュメントを出してくれ』と言われた。」
「システムが動いているのに、なぜ検収してもらえないのかわからない。」

成果物と検収条件の確認は、プロジェクトの「終わり方」を定義する作業です。
「何を作るか」は話し合うのに、「何を渡すか」「どうなれば完了とするか」を
話し合わずに進めるプロジェクトは驚くほど多い。

この確認が曖昧なままだと：
- 納品物を巡る「言った・言わない」が発生する
- 検収が通らず入金が止まる
- フェーズが終わっても「まだ何かが足りない」と言われ続ける

超概算フェーズで「何を渡すか」「どうなれば完了か」を合意しておくことで：
- 成果物の作成工数を正確に見積もりに含められる
- 検収の条件を双方が理解した状態でプロジェクトを進められる
- フェーズ完了の基準が明確になり、次のフェーズへスムーズに移行できる

---

## 学習目標

このテキストを読み終えると、以下ができるようになります。

1. **成果物の種類と、各フェーズで何を納品するかを説明できる**
2. **検収条件の設定方法と、顧客に確認すべき内容を理解できる**
3. **成果物リストと検収条件を超概算の前提として整理できる**

## 本編

### Section 1：成果物と検収条件とは何か

**一言でいうと：成果物は「渡すもの」、検収条件は「何をもってOKとするか」です。**

引越し業者で考えてみましょう。
- **成果物** ＝ 「新居に運んだ荷物・設置した家具」（何を納めるか）
- **検収条件** ＝ 「全ての荷物が新居に届いていて、破損がないこと」（どうなればOKか）

この2つが事前に合意されていれば、引越し完了の判断は明確です。
「棚は組み立てまでやってもらえると思っていた」「フックの取り付けも含むはず」
——これが成果物の認識ズレです。

システム開発でも同じです。

| 用語 | 意味 | 例 |
|-----|------|-----|
| **成果物** | プロジェクト（またはフェーズ）の終わりに顧客に引き渡すもの | 要件定義書・設計書・システム・マニュアル |
| **検収条件** | 成果物が「完成した」と認める基準・条件 | 全機能が動作すること、不具合がCritical0件であること |

**この2つはセットで確認します。**
成果物が決まっても検収条件がなければ「何をもって完成とするか」がわかりません。
検収条件があっても成果物が曖昧なら「何を確認すれば良いか」がわかりません。

---

### Section 2：成果物の種類

**一言でいうと：システム本体だけでなく、ドキュメント類も「渡すもの」に含まれる。**

システム開発の成果物は大きく3つに分けられます。

#### ① ドキュメント類（書類・仕様書）

| 成果物 | 内容 | 主に作成するフェーズ |
|------|------|--------------|
| 要件定義書 | システムに必要な要件をまとめた文書 | 要件定義 |
| 外部設計書 | 画面・帳票・データの設計をまとめた文書 | 設計 |
| 内部設計書 | システム内部のロジック・DB設計をまとめた文書 | 設計 |
| テスト仕様書 | テストの内容・手順・結果をまとめた文書 | テスト |
| 操作マニュアル | ユーザー向けの操作手順書 | リリース前 |
| 運用手順書 | システム管理者向けの運用・保守手順書 | リリース前 |
| 議事録・進捗報告 | 会議の記録・プロジェクトの進捗報告 | 全フェーズ |

#### ② システム関連（動くもの）

| 成果物 | 内容 |
|------|------|
| 動作するシステム（本番環境） | 実際に本番で使えるシステム |
| テスト環境 | テスト用の環境・データ |
| ソースコード | システムの設計図にあたるプログラムのコード |
| 設定ファイル・構成情報 | サーバー・ミドルウェアの設定情報 |
| データベース構造（DDL） | データベースの設計情報 |

#### ③ プロジェクト管理関連

| 成果物 | 内容 |
|------|------|
| プロジェクト計画書 | スコープ・スケジュール・体制をまとめた計画書 |
| スコープ合意書 | In Scope / Out of Scopeの合意文書 |
| 変更管理記録 | 変更が発生した場合の記録 |

### Section 3：顧客が期待する成果物を確認する

**一言でいうと：「何が欲しいか」を聞かないと、「渡したもの」と「欲しかったもの」がズレる。**

顧客が何を期待しているかは、聞かないとわかりません。
以下の質問で、期待する成果物を引き出します。

#### ソースコードの扱い

```
使える質問：
「今回開発したシステムのソースコード（プログラム）は
 納品いただく必要はありますか？」

「将来、別のベンダーに保守・改修を依頼する可能性はありますか？
 その場合、ソースコードの引き継ぎが必要になります。」
```

ソースコードの納品は、顧客がシステムを自社で保有・管理したい場合に必要です。
ベンダーが保守契約を結ぶ場合、ソースコードを渡さないケースもあります。
**どちらが希望か、早期に確認して契約条件に明記することが重要です。**

#### ドキュメントの範囲

```
使える質問：
「設計書や仕様書などのドキュメント類は、
 どの範囲まで納品が必要ですか？」

「社内の情報システム部門が引き継いで保守する場合、
 どんな資料があると助かりますか？」

「過去に発注したシステムのドキュメントで、
 『あれがあって助かった』『これがなくて困った』という経験はありますか？」
```

ドキュメントはどこまで作るかによって工数が大きく変わります。
「最低限あれば良い」なのか「将来の保守に必要な全ドキュメント」なのかで、
工数が倍以上変わることがあります。

#### 環境の引き渡し

```
使える質問：
「テスト環境は、本番リリース後も残しておきますか？
 それとも本番環境のみで問題ありませんか？」

「サーバーの設定情報や構成図は、
 運用担当者向けに残しておく必要がありますか？」
```

### Section 4：フェーズごとの成果物と検収条件

**一言でいうと：プロジェクト全体の検収だけでなく、各フェーズの検収条件も決める。**

大きなプロジェクトでは、全体を通じて1回だけ検収するのではなく、
フェーズごとに検収を行います。

```
フェーズ構成と成果物・検収の例：

Phase 1：要件定義
  成果物  ：要件定義書・スコープ合意書
  検収条件：双方が内容を確認し、合意のサインをする

Phase 2：設計
  成果物  ：外部設計書・内部設計書・DB設計書
  検収条件：設計書の内容を顧客が確認し、内容に問題ないとサインする

Phase 3：開発・テスト
  成果物  ：動作するシステム（テスト完了）・テスト仕様書・テスト結果
  検収条件：Critical不具合がゼロ。合格基準を満たしたテスト結果を提出

Phase 4：リリース・導入
  成果物  ：本番稼働システム・操作マニュアル・運用手順書・ソースコード
  検収条件：本番稼働確認・受入テスト完了・検収書へのサイン
```

フェーズごとに検収することで：
- 問題をフェーズ内で発見・解決できる
- 支払いをフェーズ完了にひもづけられる（キャッシュフローの安定）
- 「全部終わったのに一括で検収してもらえない」というリスクを分散できる

---

### Section 5：検収条件の設定方法

**一言でいうと：「何をもって完了とするか」を、客観的な条件として定義する。**

検収条件は「判断できる基準」でなければなりません。
「ちゃんと動いていること」は判断基準ではありません。
「何をもってちゃんと動いているとするか」を具体化します。

**検収条件の要素：**

| 要素 | 内容 | 例 |
|-----|------|-----|
| **機能条件** | 必要な機能が実装されていること | In Scopeの全Must機能が動作すること |
| **品質条件** | 一定の品質基準を満たしていること | Critical・High不具合がゼロであること |
| **文書条件** | 必要なドキュメントが揃っていること | 設計書・マニュアル・テスト結果が提出されていること |
| **手続き条件** | 承認の手続きが完了していること | 最終承認者が検収書にサインすること |

**検収条件の記述例：**

```
【フェーズ4（リリース・導入）の検収条件】

以下のすべてを満たした場合に検収完了とする。

条件① 機能条件
  ・本番環境でIn Scopeの全Must機能が正常に動作すること
  ・受入テストを実施し、顧客担当者が動作を確認していること

条件② 品質条件
  ・Critical不具合：0件
  ・High不具合   ：0件
  ・Medium以下   ：リリース後対応として許容（件数の上限：20件以内）

条件③ 文書条件
  ・操作マニュアル（最終版）が納品されていること
  ・テスト仕様書およびテスト結果が提出されていること
  ・ソースコード一式が納品されていること（顧客要望による）

条件④ 手続き条件
  ・顧客の最終承認者（○○部長）が検収確認書にサインすること
```

### Section 6：よくある落とし穴

**一言でいうと：「当たり前」と思っていたことが、相手には当たり前ではない。**

#### 落とし穴1：ソースコードの認識ズレ

ベンダーは「ソースコードは企業秘密なので渡さない」という方針だったが、
顧客は「発注したのだから当然もらえる」と思っていた。
契約段階で確認していなかったため、リリース後に大きなトラブルになった。

**対策：** ソースコードの帰属（著作権・納品の有無）を超概算フェーズで確認し、
契約書に明記する。

#### 落とし穴2：「設計書は不要」と言っていたのに後から要求される

顧客が「設計書は作らなくていい」と言っていたが、
リリース後に「保守担当者に引き継ぐために設計書が必要」と言われた。
後から作成すると、多大な工数がかかる。

**対策：** 「将来の保守・改修・引き継ぎ」のシナリオを見越して、
どのドキュメントが必要かを超概算フェーズで確認する。

#### 落とし穴3：検収条件が「動いていること」だけ

「システムが動いていれば検収します」と言われたが、
何をもって「動いている」とするかが曖昧で、
些細な不具合を理由に検収を先延ばしにされた。
入金が3ヶ月遅れ、ベンダーのキャッシュフローが逼迫した。

**対策：** 「Critical不具合ゼロ」「○月○日までに検収完了」という
具体的な条件と期限を事前に合意する。

### Section 7：確認結果の記録方法

**一言でいうと：成果物リストと検収条件を、フェーズごとに対応させて記録する。**

**成果物・検収条件確認シート（超概算時点）：**

```
■ 成果物・検収条件（超概算時点）

【納品成果物リスト】
  ドキュメント類
    ✅ 要件定義書
    ✅ 外部設計書
    ✅ テスト仕様書・テスト結果
    ✅ 操作マニュアル
    ✅ 運用手順書
    ❌ 内部設計書（今回は省略。別途費用で対応可）

  システム関連
    ✅ 本番稼働システム
    ✅ テスト環境（リリース後3ヶ月間保持）
    ✅ ソースコード一式（顧客要望により納品）
    ✅ DB設計書（DDL含む）

  プロジェクト管理
    ✅ 議事録（毎回の打ち合わせ後に共有）
    ✅ スコープ合意書

【検収条件】
  Phase 1（要件定義）
    ・要件定義書の内容に双方が合意し、サインすること

  Phase 2（設計）
    ・外部設計書の内容を顧客が確認し、異議なしのサインをすること

  Phase 3〜4（開発・リリース）
    ・Critical・High不具合がゼロであること
    ・操作マニュアル・テスト結果が納品されていること
    ・本番稼働を確認し、最終承認者が検収確認書にサインすること

【ソースコードの帰属】
  著作権    ：開発完了後、顧客に譲渡（契約書に明記）
  納品形式  ：GitHubリポジトリの移管またはZIP納品

■ 前提条件
  - 検収確認書へのサインが確認できた日を検収完了日とする
  - 検収完了から30日以内に支払い
  - 検収後の変更は仕様変更として別途費用
```

## アクティブラーニング

以下の問いについて、自分のPJを思い浮かべながら考えてみてください。

**問い1：**
今のPJで「何を納品するか」のリストはありますか？
ソースコードやドキュメント類の扱いは契約書に明記されていますか？

**問い2：**
検収条件は「動いていること」以上の具体的な条件になっていますか？
「何をもって完了とするか」を双方が同じ言葉で理解できていますか？

**問い3：**
フェーズごとの検収は設定されていますか？
一括検収のみの場合、入金が最後まで発生しないリスクを認識していますか？

## まとめとネクストアクション

### 3つの重要ポイント

1. **成果物は「システム本体」だけではない。ドキュメント・ソースコードも含めて合意する**
   何を渡すかを明示しないと「渡したもの」と「欲しかったもの」がズレる。
   特にソースコードの帰属は契約書に明記する必要がある。

2. **検収条件は「動いていること」では不十分。客観的な条件と手続きを定義する**
   「Critical不具合ゼロ」「承認者のサイン」という具体的な条件が、
   検収を円滑に進める鍵。曖昧な条件は先延ばしの温床になる。

3. **フェーズごとに成果物と検収条件を設定し、入金リスクを分散する**
   一括検収はベンダーのキャッシュフローリスクが高い。
   フェーズごとの検収を設定することで、問題の早期発見と安定したキャッシュフローを実現できる。

### 明日からできるネクストアクション

> **今の担当PJで「成果物リスト・検収条件シート」を作り、顧客と合意する。**

| 成果物 | 要否 | 担当 | 納品タイミング |
|------|------|------|------------|
| 要件定義書 | 要 / 不要 | | Phase 1完了時 |
| 設計書（外部） | 要 / 不要 | | Phase 2完了時 |
| 設計書（内部） | 要 / 不要 | | Phase 2完了時 |
| テスト仕様書・結果 | 要 / 不要 | | Phase 3完了時 |
| 操作マニュアル | 要 / 不要 | ベンダー / 顧客 | リリース前 |
| 運用手順書 | 要 / 不要 | ベンダー / 顧客 | リリース前 |
| ソースコード | 要 / 不要 | | リリース時 |
| 本番システム | 要 | | リリース日 |

このリストと検収条件をセットにして顧客と合意することで、
「終わり方」が明確なプロジェクトを最初から設計できます。
