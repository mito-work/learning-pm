# スコープ管理 > 立ち上げ

## 正式見積：納品対象成果物のリストアップ

---

## 導入

### このスキルを身につけると、何が変わるか

「動くシステムを納品したら『設計書はどこですか？』と言われた」
「テスト結果報告書は当然もらえると思っていたと、プロジェクト終盤に初めて言われた」
「操作マニュアルが含まれていなかったため、無償で作ることになった」
「プロジェクトがいつ終わるのかの基準が曖昧で、追加要求が止まらなかった」——

「何を納品するか」が合意されていないプロジェクトは、終わり方が決まらないプロジェクトです。
顧客が「受け取れるもの」を把握していなければ、プロジェクトがいつ完了するかを双方が判断できません。
このスキルは、**正式見積フェーズで「何を・どんな状態で・どの形式で」納品するかを成果物リストとして明確にし、完了の定義を顧客と合意する**技術です。

> **やらないことリストとの違い：** やらないことリストは「行為・作業の除外（何をしないか）」を明確にするもの。納品物リストは「成果物の明確化（何を渡すか）」を正の形で列挙するもの。両者はセットで使うことで、スコープの内側と外側を完全に定義できます。

このスキルを学ぶことで：
- 「設計書ももらえると思っていた」という期待のズレを事前に防げる
- 成果物リストが「プロジェクト完了」の客観的な基準になる
- 追加要求が来たとき「合意した成果物の範囲外」として対応できる
- 見積もりの工数を「成果物ごとに積み上げる」思考ができる

---

## 学習目標

このテキストを読み終えると、以下ができるようになります。

1. **5カテゴリ（システム・設計書・テスト・運用・管理）で成果物を漏れなくリストアップできる**
2. **各成果物の「形式・レビュー条件・提出方法」を明確にして合意できる**
3. **成果物リストを「プロジェクト完了の定義」と紐づけて管理できる**

## 本編

---

### Section 1：納品成果物の明確化がなぜ「完了の定義」につながるのか

**一言でいうと：「何を渡せばプロジェクトが終わるか」が決まっていないプロジェクトは、永遠に終わらない。**

成果物リストは、プロジェクトの「完了条件」です。

```
【成果物リストがないときに起きること】

  顧客：「システムは動いているけど、まだ設計書をもらっていない」
  PM：「設計書は含まれていないと思っていました」
  顧客：「システム開発を発注したら設計書は当然もらえると思っていた」
  ↓
  完了の判定ができない
  追加作業が発生する
  「いつ終わるか」が顧客にも自分にもわからなくなる

【成果物リストがあるときの対話】

  PM：「今月末の納品では、以下を揃えてお渡しします。
       ①システム本体（本番環境へのデプロイ）
       ②基本設計書・詳細設計書
       ③テスト結果報告書
       これらが揃い、顧客様の確認が完了した時点でプロジェクト完了となります」
  顧客：「わかりました。操作マニュアルは含まれますか？」
  PM：「今回の見積もりには含まれていません。必要でしたら別途対応します」
  ↓
  完了の定義が明確になる
  追加要求に根拠を持って対応できる
```

### Section 2：5カテゴリで成果物をリストアップする

**一言でいうと：成果物は「システム・設計書・テスト・運用・管理」の5カテゴリで洗い出す。カテゴリごとに「含む・含まない」を明示する。**

#### カテゴリ①：システム・ソフトウェア

```
□ 動作するシステム・アプリケーション
  （本番環境・ステージング環境へのデプロイ完了状態）
□ ソースコード
  （バージョン管理システムへの登録・コメント整備の有無）
□ 環境構築スクリプト・設定ファイル
  （Dockerfile・インフラ定義ファイルなど）
□ マイグレーションスクリプト（DBの初期構築・変更スクリプト）
```

#### カテゴリ②：設計ドキュメント

```
□ 要件定義書（機能要件・非機能要件のまとめ）
□ 基本設計書（画面設計・機能設計・外部インターフェース設計）
□ 詳細設計書（クラス設計・モジュール設計・処理フロー）
□ DB設計書・テーブル定義書・ER図
□ API仕様書（外部公開・内部利用のインターフェース定義）
□ インフラ構成図（ネットワーク・サーバー構成）
```

#### カテゴリ③：テスト関連

```
□ テスト計画書（テスト方針・範囲・スケジュール）
□ テスト仕様書・テストケース一覧
□ テスト結果報告書（単体テスト・結合テスト・システムテスト）
□ バグ管理票・不具合対応履歴
```

#### カテゴリ④：運用・引き渡し関連

```
□ 操作マニュアル（エンドユーザー向け）
□ 管理者マニュアル（システム管理者向け）
□ 環境構築手順書（新規構築・再構築のための手順）
□ 運用手順書（バックアップ・障害対応・定期作業の手順）
□ 移行計画書・データ移行手順書
```

#### カテゴリ⑤：プロジェクト管理関連

```
□ 議事録（打ち合わせの記録・合意事項の記録）
□ WBS・スケジュール表
□ 課題管理表（プロジェクト中の課題・対応履歴）
□ 変更管理記録（スコープ変更・仕様変更の履歴）
```

### Section 3：成果物の「品質条件」を定義する

**一言でいうと：成果物の名前だけ並べても不十分。「誰がチェックして・どの状態で・どの形式で渡すか」を決めることが合意を完成させる。**

成果物リストに「品質条件」を付けることで、受け渡しの基準が明確になります。

| 品質条件の要素 | 確認すべきこと | 例 |
|------------|------------|---|
| **形式** | どのファイル形式で渡すか | Word / Excel / PDF / GitHubリポジトリ |
| **レビュー条件** | 誰がレビューして「OK」と判断するか | PMが確認 / PLが確認 / 顧客が確認 |
| **版管理** | どのバージョンを最終版とするか | 顧客確認後のPDF確定版 / タグ打ちしたリリースブランチ |
| **提出方法** | どうやって渡すか | メール添付 / 共有フォルダ / GitHubリポジトリURL |

#### 成果物の品質条件を書く例

```
成果物：基本設計書

形式：Microsoft Word形式（.docx）
     最終提出はPDF変換版も同時提供
レビュー条件：PM確認 → 顧客担当者確認 → 顧客承認者の承認を経て確定
版管理：顧客から承認を受けたバージョンが最終版
提出方法：共有フォルダ（○○）への格納後、URLをメールで通知
```

```
成果物：ソースコード

形式：GitHubリポジトリへの登録
     ブランチ：main（本番稼働バージョン）
レビュー条件：PLのコードレビュー完了・CI/CDパイプラインのテスト通過
版管理：本番デプロイ時点のコミットにタグ（v1.0）を付与
提出方法：リポジトリへのアクセス権限を顧客担当者に付与
```

### Section 4：「含まない成果物」を明示する

**一言でいうと：何を渡さないかを書くことが、何を渡すかを書くことと同じくらい重要。**

前の教材（やらない対象の前提条件化）と同様に、成果物リストでも「含まない成果物」の明示が必要です。

```
成果物リストに「含まない」と明示すべき典型例：

❶ 詳細設計書
  → 「基本設計書までは作成します。詳細設計書は作成しません」
  → 顧客が後から「詳細設計書はどこですか？」と言うことがある

❷ 操作マニュアル
  → 「マニュアルは含まれません（画面上のヘルプテキストで代替）」
  → 「システム開発に操作マニュアルは当然含まれる」と思う顧客は多い

❸ テスト結果報告書
  → 「テストは実施しますが、テスト結果報告書のドキュメント化は含みません」
  → 実施したことの証拠としてのドキュメントを求められるケースがある

❹ ソースコードの提供
  → 「今回の契約ではソースコードの提供は含まれません（SaaS型提供）」
  → ソースコードが自社の資産になると思っている顧客への確認が必要

❺ 議事録の作成
  → 「議事録の作成は顧客様側でお願いします」
  → PMが作成するものと思っている顧客への確認
```

「含まない」を明示するときは、前の教材で学んだように「代わりに誰がどうするか」をセットで書きます。

### Section 5：成果物リストを顧客と合意する

**一言でいうと：成果物リストは「PMが作るもの」ではなく「顧客と合意するもの」。合意のプロセスが完了の定義を作る。**

#### 合意の進め方

```
「今回のプロジェクトで納品する成果物を
 以下のとおり整理しました。

 【納品成果物】
  ① システム本体（本番環境へのデプロイ）
  ② 基本設計書（Word形式・顧客確認後PDF確定版）
  ③ テスト結果報告書（単体・結合・システムテスト）
  ④ 操作マニュアル（エンドユーザー向け）
  ⑤ 議事録（各打ち合わせ後、3営業日以内に共有）

 【含まれない成果物（ご確認ください）】
  ・詳細設計書（基本設計書で代替）
  ・管理者マニュアル（環境構築手順書で代替）
  ・運用手順書（ご要望があれば別途お見積もりします）

 プロジェクト完了は、上記①〜⑤の納品が完了し、
 顧客様のご確認が得られた時点とします。

 内容にご認識の違いがあればお知らせください。
 確認いただけましたら、この内容で進めます。」
```

#### 合意後の注意点

- 合意した成果物リストは見積書・提案書に記載する
- プロジェクト開始時のキックオフでも再確認する
- 成果物の変更が生じた場合は変更管理として記録する

## まとめとネクストアクション

### 3つの重要ポイント

1. **成果物リストは「プロジェクト完了の定義」。リストが合意されていないプロジェクトは終わり方が決まらない**
   「何を渡せばプロジェクトが終わるか」を双方が把握していることが、追加要求の歯止めになる。
   5カテゴリ（システム・設計書・テスト・運用・管理）でリストアップし、含まない成果物も明示する。

2. **成果物の「品質条件（形式・レビュー・版管理・提出方法）」まで定義することが、受け渡しのトラブルを防ぐ**
   「設計書を渡した」「まだ最終版じゃない」という水掛け論を防ぐには、「誰が確認して・何の形式で・どこに」が事前に合意されていることが必要。

3. **「含まない成果物」の明示が、後の追加工数の根拠になる**
   詳細設計書・操作マニュアル・テスト結果報告書・ソースコード提供——これらは「含まれると思っていた」が最も多い典型的な成果物。
   「含まない」を書いておくことが、追加費用の交渉根拠になる。
