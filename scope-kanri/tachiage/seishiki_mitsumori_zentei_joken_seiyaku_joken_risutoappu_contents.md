# スコープ管理 > 立ち上げ

## 正式見積：前提条件・制約条件のリストアップ

---

## 導入

### このスキルを身につけると、何が変わるか

「顧客が仕様の提示を遅らせたことで納期がズレたのに、追加費用の根拠がなかった」
「予算の上限を知らずに見積もりを出し、大幅な削減交渉を強いられた」
「既存システムの制約を把握していなかったため、設計を途中で大幅に見直すことになった」——

見積もりが「使えないもの」になる原因の多くは、前提条件と制約条件の見落としです。
見積もりは「何かを仮定した上で成り立つ」ものです。
その仮定（前提）と動かせない制限（制約）が明文化されていなければ、見積もりは砂上の楼閣です。
このスキルは、**正式見積フェーズで前提条件と制約条件を漏れなくリストアップし、見積もりの土台を固める**技術です。

このスキルを学ぶことで：
- 前提条件が崩れたとき「スコープ変更・工数増加」を根拠を持って説明できる
- 制約条件を共有することで、後から「それはできない」という手戻りを防げる
- 「言った・言わない」のトラブルが起きにくい見積もりの合意ができる
- 追加費用・工数増加の交渉に使える「記録」が残る

---

## 学習目標

このテキストを読み終えると、以下ができるようになります。

1. **前提条件と制約条件の違いを説明し、それぞれの主要な項目をリストアップできる**
2. **前提条件が崩れた場合の「工数変動の見通し」をセットで示せる**
3. **リストアップした内容を顧客と合意するための確認ができる**

## 本編

### Section 1：前提条件と制約条件——「2つの違い」を理解する

**一言でいうと：前提条件は「こうであるはずだ」という仮定、制約条件は「これは変えられない」という制限。同じように見えて、崩れたときの影響が全く違う。**

まず、この2つの言葉を明確に分けます。

| | 定義 | 崩れたとき |
|--|-----|---------|
| **前提条件** | プロジェクトが成立するために「こうであるはずだ」と仮定していること | スコープや工数の見直しが必要になる |
| **制約条件** | 外から課せられた「変えられない制限・境界」 | 制約の中でスコープ・品質・コストを調整する必要がある |

#### 具体例で見る違い

```
【前提条件の例】
  「要件定義書は着手前に顧客から提供される」
  「既存システムのAPIドキュメントは整備されている」
  「テスト環境は本番環境と同等の構成で用意できる」
  「顧客側の担当者は週2回の打ち合わせに参加できる」

  → これらが崩れると工数・スケジュールが変わる

【制約条件の例】
  「本番稼働は○年○月○日まで（顧客の業務上の締め切り）」
  「予算の上限は○千万円まで」
  「使用するシステムは○○クラウドのみ（社内IT方針）」
  「個人情報は社外のサーバーに置けない（セキュリティポリシー）」

  → これらは交渉・変更ができない絶対条件
```

前提条件は「崩れた場合の影響」を事前に伝えておくことが重要です。
制約条件は「設計・提案をこの条件の中で行う」という境界線の共有が重要です。

### Section 2：前提条件のリストアップ

**一言でいうと：前提条件は「顧客側」「ベンダー側」「外部環境」の3方向から洗い出す。**

前提条件を網羅的にリストアップするには、誰の前提かを整理します。

#### 顧客側の前提条件

顧客が「やってくれると思っていた」ことが崩れると、最も大きな影響が出ます。

```
確認すべき顧客側の前提条件：

□ 情報提供の前提
  ・要件定義書・仕様書は着手前に揃う（いつ提供されるか）
  ・既存システムの仕様・ドキュメントは整備されている
  ・マスタデータ・移行データは指定期日までに提供される

□ 意思決定の前提
  ・仕様の確定は○週間以内に行われる
  ・テスト結果への承認は○営業日以内に得られる
  ・顧客側の関係部門の合意は担当者が取得する

□ リソースの前提
  ・顧客側の担当者は週○回の打ち合わせに参加できる
  ・顧客側でのテスト実施（受入テスト）に必要な人員は確保されている
  ・顧客社内の調整（他部門への説明・合意取得）は顧客側が行う
```

#### ベンダー側の前提条件

自社が「できると思っていた」ことが崩れた場合も、見積もりに影響します。

```
確認すべきベンダー側の前提条件：

□ 技術・環境の前提
  ・既存システムとの連携に必要なAPIが公開されている
  ・テスト環境は本番と同等の構成で用意できる
  ・使用するサービス・ライブラリの利用条件に問題がない

□ 人員の前提
  ・担当PLは○月から参画できる
  ・必要なスキルを持つエンジニアがアサイン可能
```

#### 外部環境の前提条件

```
確認すべき外部環境の前提条件：

□ サードパーティの前提
  ・外部連携先のAPI仕様は本番稼働まで変更されない
  ・利用するクラウドサービスの仕様・料金は見積もり時点から変更されない

□ 法規制の前提
  ・適用される法規制・規格は変更されない（または変更対応は別途扱う）
```

### Section 3：前提条件が崩れたときの「影響の見通し」をセットで示す

**一言でいうと：「前提が崩れたら工数が増える」では弱い。「具体的に何がどう変わるか」をセットで書く。**

前提条件の最大の価値は「崩れたときの根拠」になることです。
そのため、前提条件だけでなく「これが崩れると何が起きるか」をセットで記録します。

```
前提条件と影響のセット記載例：

前提条件：
  「要件定義書は○月○日までに顧客から提供される」

崩れた場合の影響：
  「提供が1週間遅れるごとに、着手を1週間後ろにズラす必要があります。
   最終的な納期に影響が出る可能性があります。」

---

前提条件：
  「既存システムのAPIドキュメントが整備されている」

崩れた場合の影響：
  「ドキュメントが未整備の場合、
   調査工数として別途○〜○人日が発生します。」

---

前提条件：
  「仕様の確定は各機能の着手2週間前に行われる」

崩れた場合の影響：
  「仕様変更が着手後に発生した場合、
   手戻り工数が追加費用として発生します。」
```

この「影響の見通し」が、後の追加費用・スケジュール変更交渉の根拠になります。

### Section 4：制約条件のリストアップ

**一言でいうと：制約条件は「QCDのどれを最優先するか」を決める情報でもある。早く把握するほど設計の選択肢が広がる。**

制約条件を把握することは、プロジェクトの「動かせない壁」を知ることです。
この壁の中でどう設計・提案するかを考えるための情報です。

| 制約の種類 | 主な確認内容 |
|---------|-----------|
| **時間的制約** | 最終納期・主要マイルストーンの日付（動かせない理由とセットで確認） |
| **予算的制約** | 予算の上限・支払い時期・超過した場合の対応ポリシー |
| **技術的制約** | 使用が指定されている技術・禁止技術・既存インフラの制限 |
| **リソース制約** | 顧客側のアサイン可能人員・自社での対応可能スキルセット |
| **規制・ポリシー制約** | 情報セキュリティポリシー・業界規制・法令要件 |

#### 制約条件の確認で押さえるポイント

制約条件は「なぜその制約があるのか」を把握することが重要です。

```
【制約条件の確認例】

時間的制約：
  「○月○日という納期は、どのような理由から設定されていますか？
   業務上の締め切り（法定報告・新年度移行・キャンペーン開始など）
   であれば、絶対に動かせない条件として把握します。」

  理由が把握できると：
  ・「○月○日が絶対」なのか「できれば○月」なのかが判断できる
  ・間に合わない場合の「代替策（フェーズ分割・スコープ削減）」を提案できる

予算的制約：
  「予算の上限はご共有いただけますか？
   予算の範囲に合わせてスコープの優先順位付けのご提案が可能です。」

  理由が把握できると：
  ・予算内でどこまでできるかを先に整理できる
  ・「全部やると予算超過になるが、優先度の高いものだけなら収まる」
   という提案が可能になる
```

### Section 5：顧客との合意——前提条件・制約条件を「見積もりの土台」にする

**一言でいうと：PMが作ったリストを顧客と合意することで、見積もりは「土台のある数字」になる。**

リストアップした前提条件・制約条件は、顧客に確認して合意を取ります。

#### 顧客への共有方法

```
「正式見積もりを作成するにあたり、
 以下の前提条件・制約条件をご確認いただけますか。

 【前提条件（これを仮定して見積もります）】
  ・要件定義書は○月○日までにご提供いただける
  ・仕様確定は着手2週間前に行われる
  ・既存システムのAPIドキュメントは整備されている

 【制約条件（これは変えられない条件として理解しています）】
  ・本番稼働は○月○日まで
  ・使用クラウドは○○のみ
  ・予算上限は○千万円

 前提条件については、崩れた場合に工数・スケジュールへの
 影響が生じます。その点もあらかじめご認識いただけますか。

 確認いただき、認識の違いがある場合はご指摘ください。
 この内容で見積もりを進めさせていただきます。」
```

#### 合意のポイント

- 書面（メール・ドキュメント）で確認し、返信またはサインをもらう
- 「認識の違いがなければ合意とみなします」という形でも可
- 合意した日付・手段を記録に残す

## まとめとネクストアクション

### 3つの重要ポイント

1. **前提条件は「崩れたときの影響」とセットで記録する。数字の根拠が後の交渉を守る**
   「前提条件が崩れた」という事実だけでは交渉にならない。
   「この前提が崩れると、具体的に○人日・○週間の追加が発生する」という見通しが根拠になる。

2. **制約条件は「なぜその制約か」を把握して設計に活かす**
   「なぜ○月○日が納期か」を知ることで、代替策（フェーズ分割・スコープ削減）の提案が可能になる。
   「動かせない制限」を早く知るほど、その中での最適解を設計できる。

3. **リストアップした内容を顧客と合意し、「見積もりの土台」として書面に残す**
   PMだけが把握している前提・制約は「PMの認識」にすぎない。
   顧客との合意が記録された瞬間に「プロジェクトの共通認識」になる。

### 明日からできるネクストアクション

> **今担当しているPJの前提条件を1つ書き出し、「これが崩れたら何が起きるか」を一言で書く。書けない前提条件があれば、顧客またはPLに確認する。まず1つを明文化することが、前提条件管理の始まり。**
