# スコープ管理 > 立ち上げ

## 正式見積：技術的実現性／概算工数のPLへの依頼

---

## 導入

### このスキルを身につけると、何が変わるか

「PLに見積もりを依頼したら、精度が低くて提案書に使えないものが上がってきた」
「『技術的に難しいかもしれない』という話を後から聞かされ、顧客への提案後に仕様を覆すことになった」
「工数を出してもらったが、前提条件が不明で、なぜその数字なのか説明できなかった」——

正式見積の品質は、PLへの依頼の質で決まります。
このスキルは、**PMがPLに対して「何を・どう見積もってほしいか」を整理して依頼し、技術的実現性と概算工数を正確に引き出す**技術です。

このスキルを学ぶことで：
- PLに渡す情報を整理でき、手戻りの少ない見積もりが出るようになる
- 技術的な不確かさを早期に把握し、顧客への提案前にリスクを潰せる
- 「なぜその工数か」を説明できる見積もりが手に入る
- PMとPLの間に「一緒に考える」関係が生まれる

---

## 学習目標

このテキストを読み終えると、以下ができるようになります。

1. **PLへの見積もり依頼に必要な情報（要件・制約・確認事項）を整理して渡せる**
2. **「技術的実現性」と「概算工数」を分けて依頼できる**
3. **PLから受け取った見積もりを顧客提案に使うための確認ができる**

## 本編

---

### Section 1：PMがPLに依頼する前に整理すべきこと

**一言でいうと：情報が足りない依頼からは、精度の低い見積もりしか出てこない。渡す前に情報を揃える。**

PLへの見積もり依頼は「お願いします」の一言では機能しません。
PLが適切な見積もりを出すためには、以下の情報が必要です。

```
PLへの依頼パッケージ（最低限必要な情報）：

① 要件・スコープの概要
  ・何を作るか（機能・システムの範囲）
  ・何を作らないか（スコープ外の明確化）
  ・顧客が特に重視しているポイント

② 制約条件
  ・希望納期（顧客の期待するリリース時期）
  ・予算の目安（概算でも共有できる場合）
  ・技術的な前提（既存システムとの連携・使用技術の指定など）

③ 不確かな点のリスト
  ・PMが技術的に判断できない事項
  ・顧客から詳細が確認できていない事項

④ 見積もりの用途と精度要件
  ・何に使うか（顧客提案・社内承認・予算申請など）
  ・どのくらいの精度が必要か（±30%程度の概算でよいか）
  ・いつまでに必要か（提出期限）
```

この情報が揃っていないと、PLは「自分で仮定を置いた見積もり」を出すしかなくなります。
その仮定がPMや顧客の認識と違っていた場合、見積もりは使えないものになります。

---

### Section 2：「技術的実現性」と「概算工数」を分けて依頼する

**一言でいうと：「できるか」と「何日かかるか」は別の問いだ。まず「できるか」を確認してから「何日か」を聞く。**

PMがPLに依頼するときに混在しやすい2つの確認事項を、意識的に分けます。

#### 技術的実現性の確認

「これは実現できるか」という問いです。

```
技術的実現性の確認で聞くべきこと：

・この要件はシステムとして実現可能か？
・既存システムとの連携で技術的なハードルがあるか？
・使用する技術・ライブラリ・APIで制約はあるか？
・「できる」としたらどんな前提が必要か？
・「難しい」としたら代替案はあるか？
```

**重要：「技術的に難しい」は「できない」ではない。**

PLが「技術的に難しいです」と言ったとき、それは「代替案・追加工数・トレードオフがある」というサインです。
「では別の方法では？」「どんな条件なら実現できますか？」という問いに変えると、解決策が見えてくることがほとんどです。

```
❌ 「難しいですか。ではこの機能は諦めます（顧客に伝えます）」
✅ 「難しい場合、どんな代替案が考えられますか？
   工数や条件はどう変わりますか？」
```

#### 概算工数の確認

「どれくらいかかるか」という問いです。

```
概算工数の確認で聞くべきこと：

・この機能/システムを実装するのに何人日かかるか？
  （設計・実装・テスト・ドキュメントを含む）
・工数の前提条件は何か？
  （メンバー構成・既存資産の流用度合い・レビュー回数など）
・不確かさが大きい部分はどこか？
  （工数が大きくブレる可能性のある箇所）
・リスク（工数が増える可能性）はどこにあるか？
```

---

### Section 3：依頼書の書き方——PLが作業しやすい渡し方

**一言でいうと：依頼は「口頭だけ」にしない。書面で渡すことで、認識のズレと記憶の薄れを防ぐ。**

PLへの見積もり依頼は、口頭だけでなく書面（メール・チャット・ドキュメント）で残します。

#### 依頼書の構成例

```
件名：正式見積もり依頼（○○プロジェクト）

○○さん

以下の内容で技術的実現性と概算工数の確認をお願いします。

【プロジェクト概要】
・顧客：○○株式会社
・概要：○○システムの構築
・背景：○○の課題を解決するため○○を開発したい

【要件・スコープ】
・機能A：○○（詳細は添付の要件メモを参照）
・機能B：○○
・スコープ外：○○（顧客と合意済み）

【制約条件】
・希望納期：○年○月（顧客の希望）
・連携先：既存の○○システム（○○のAPIを使用）
・技術前提：○○を使う方向で顧客と話している

【確認してほしいこと】
① 技術的実現性：上記機能は実現可能か？
   難しい場合、代替案はあるか？
② 概算工数：全体の工数を教えてほしい（±30%程度の精度でOK）
   機能別に分けてもらえると助かる
③ リスク：工数が大きく変動しそうな部分はどこか？

【用途・期限】
・顧客への提案書に使用（顧客への提示は○月○日予定）
・見積もり提示期限：○月○日（○日後）

不明点があればいつでも声をかけてください。
```

**期限は「余裕を持って伝える」のが基本です。**
PLが見積もりを作るためにも時間が必要です。
顧客への提示日から逆算して、最低3〜5営業日以上の余裕を設けます。

---

### Section 4：PLとの「見積もり精度」の合意

**一言でいうと：「概算」と「詳細見積もり」の精度の違いを最初に合意しないと、ズレが起きる。**

正式見積もりにも「精度」があります。
フェーズや用途によって、求める精度は変わります。

| 見積もりの種類 | 精度 | 用途 |
|------------|-----|-----|
| **概算見積もり** | ±30〜50% | 顧客への予算感の提示・商談継続の判断 |
| **正式見積もり（一次）** | ±20〜30% | 提案書・契約書への記載 |
| **詳細見積もり** | ±10〜15% | WBS・工程表・リソース計画との整合 |

正式見積もりフェーズのPLへの依頼では、「提案書に使う一次見積もり（±20〜30%程度）」が一般的な要求です。

```
精度合意の確認例：

「今回の見積もりは顧客への提案書に使います。
 詳細仕様はまだ確定していないので、
 ±30%程度の精度で構いません。
 大きくブレる可能性がある部分はリスクとして
 別途記載してもらえれば助かります。」
```

「±30%でいい」という言葉があるだけで、PLは安心して「現時点でわかる範囲」の見積もりを出せます。
「完璧でないといけない」という圧力がかかると、PLは「確認してから」とウエイティングになりがちです。

---

### Section 5：PLから受け取った見積もりを確認する

**一言でいうと：「数字」だけを受け取っても使えない。「前提条件とリスク」がセットでなければ顧客に説明できない。**

PLから見積もりを受け取ったら、以下を確認します。

```
見積もり受け取り後の確認チェックリスト：

① 前提条件の確認
  ・この工数はどんな前提で出しているか？
    （チーム構成・既存資産の活用度・要件の確定度など）
  ・前提が崩れた場合、工数はどう変わるか？

② リスクの確認
  ・工数が増える可能性のある部分はどこか？
  ・顧客との仕様確認でスコープが広がった場合の影響は？

③ 「難しい」と言われた箇所の代替案確認
  ・代替案の工数・品質・リスクは？
  ・顧客への説明はどう行うか？

④ 顧客提示前のPLへの最終確認
  ・この内容で顧客に提示してよいか？
  ・追加で確認したい点はないか？
```

#### 受け取った見積もりで疑問がある場合

```
「ありがとうございます。
 機能Aの工数が○人日とのことですが、
 これは○○（前提条件）を想定しているということでしょうか？
 
 もし○○（別の前提）の場合、工数はどう変わりますか？」
```

「なぜその工数か」を理解していないと、顧客から「なぜ○人日かかるのですか？」と聞かれたときに答えられません。
見積もりの「根拠」を理解することが、PMとしての責任です。

## まとめとネクストアクション

### 3つの重要ポイント

1. **PLへの依頼は「情報パッケージ」を整えてから。要件・制約・確認事項・期限をセットで渡す**
   口頭だけの依頼は認識のズレと記憶の薄れを生む。
   書面で渡すことで、PLが「自分で仮定を置かなくていい」状態を作る。

2. **「技術的実現性」と「概算工数」は別の問いとして依頼する。「難しい」は「できない」ではない**
   まず「できるか（実現性）」を確認してから「何日か（工数）」を聞く順序が基本。
   「難しい」と言われたら「代替案は？」に変換する習慣が、提案の幅を広げる。

3. **見積もりは「数字」だけでなく「前提条件とリスク」をセットで受け取る**
   工数の根拠を理解していないと、顧客への説明もPL本人への追加依頼もできない。
   「なぜその数字か」を理解することがPMの責任。

---

### 明日からできるネクストアクション

> **次にPLへ見積もりを依頼するとき、「用途・期限・精度」の3点を冒頭に明示する。「今回は提案書用で±30%程度でOK、○日までにほしい」この一言があるだけで、PLが出しやすい見積もりになる。**
