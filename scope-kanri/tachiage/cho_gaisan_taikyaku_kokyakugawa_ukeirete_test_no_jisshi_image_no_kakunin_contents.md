# スコープ管理 > 立ち上げ

## 超概算：【対客】顧客側受入テストの実施イメージの確認

---

## 導入

### このスキルを身につけると、何が変わるか

「受入テストはこちらでやります、大丈夫です。」
この言葉を信じてスケジュールを組んだら、リリース直前に問題が続出した——

- 受入テストの担当者が決まっておらず、誰もやらなかった
- 「何を確認すればよいかわからない」と言われ、ベンダーが巻き取ることになった
- 「とりあえずOK」でサインオフされたが、本番後に「やっぱり違う」が続発した
- 検収が通らず、支払いが滞った

受入テストは、システムをリリースしてよいかどうかを顧客が「正式に判断する」場です。
ベンダーにとっては「検収＝入金」に直結する重要な工程でもあります。

しかし顧客側の多くは、受入テストをどう進めるべきか具体的なイメージを持っていません。
超概算フェーズで「どんな体制で・何を確認して・どう判断するか」を一緒に描くことで：

- 顧客が受入テストに本気で取り組む体制を早期に作れる
- 「何をもって完了とするか」の基準を事前に合意できる
- 検収・入金のタイミングを明確にしてプロジェクトリスクを減らせる

---

## 学習目標

このテキストを読み終えると、以下ができるようになります。

1. **受入テストと総合テストの違いを説明できる**
2. **受入テストの実施体制・合格基準・承認プロセスを顧客と確認できる**
3. **受入テストの合意内容を超概算の前提条件として整理できる**

## 本編

---

### Section 1：受入テストとは何か

**一言でいうと：顧客が「このシステムを本番で使う」と正式に判断するための最終確認テストです。**

前回の学習で総合テスト（シナリオテスト）を学びました。
受入テストはその次のステップです。

注文住宅で考えてみましょう。
- **総合テスト**＝施工会社が「建物として問題なく建っているか」を確認する（施工品質の確認）
- **受入テスト**＝施主（顧客）が「自分が注文した通りに建ったか」を確認する（引渡し前の最終チェック）

「施工会社がOKを出した」と「施主が引渡しを受け入れた」は別の話です。
受入テストは、顧客が主体となって「自分の要件を満たしているか」を確認する工程です。

**総合テストと受入テストの違い：**

| 項目 | 総合テスト（シナリオテスト） | 受入テスト（UAT） |
|-----|----------------------|----------------|
| **目的** | システムが仕様通りに動くか確認する | 顧客が「要件を満たした」と正式に判断する |
| **主な実施者** | ベンダー or 顧客（前回学んだ分担による） | **顧客**（ベンダーは支援） |
| **合格基準** | テストケースの通過率 | 顧客が「使える」と判断できるか |
| **完了後の意味** | 品質確認が完了した | **検収＝正式なシステムの引渡し** |
| **ベンダーへの影響** | 次の工程へ進む | **入金・契約完了に直結する** |

`UAT（User Acceptance Testing）：「ユーザー受入テスト」の英語略称。ベンダーが作ったシステムを、実際に使うユーザー（顧客）が確認する最終テストのこと。`

---

### Section 2：受入テストの実施イメージを確認する

**一言でいうと：「誰が・何を使って・どんな手順で・何日間・どう判断するか」の5つを確認する。**

顧客は「受入テストはやります」と言っても、
具体的な進め方まで考えていないことがほとんどです。
PMが一緒にイメージを作ることで、顧客の準備が進みます。

#### ① 実施体制（誰がやるか）

```
使える質問：
「受入テストは、どなたが担当されますか？
 現場の実際のユーザーの方に参加いただけますか？」

「意思決定者（最終的にOKを出せる方）は誰ですか？
 テスト担当者と意思決定者は同じですか？」

「受入テストに、何名くらいが参加できますか？」
```

受入テストには2種類の役割があります。

| 役割 | 内容 |
|-----|------|
| **テスト実施者** | 実際にシステムを操作して確認する現場担当者 |
| **最終承認者** | 「受け入れる・受け入れない」を判断できる責任者 |

実施者と承認者が同じ場合もありますが、
大きな組織では「現場担当者がテストし、部長が最終承認する」という構造になることが多いです。
承認者が誰かを早期に確認しておくことで、意思決定が止まるリスクを防げます。

#### ② 確認内容（何を確認するか）

```
使える質問：
「受入テストでは、どんなことを確認したいですか？」

「特に念入りに確認したい業務・機能はありますか？
 ここが動かないとリリースできない、というものを教えてください。」

「通常の業務フロー以外に、
 月末処理・イレギュラーな例外パターンも確認しますか？」
```

#### ③ 実施期間（いつ・何日間やるか）

```
使える質問：
「受入テストに使える期間はどれくらいですか？」

「テスト中に気になる点が見つかった場合、
 それを確認・修正する時間も含めてスケジュールに組み込めますか？」

「本番リリース希望日から逆算すると、受入テストはいつから始める必要がありますか？」
```

受入テストの期間目安：

| システム規模 | 目安の期間 |
|-----------|---------|
| 小規模 | 3日〜1週間 |
| 中規模 | 1〜2週間 |
| 大規模 | 2週間〜1ヶ月 |

#### ④ 合格基準（何をもって完了とするか）

```
使える質問：
「受入テストが終わった後、どんな状態になれば
 『OK』と判断できますか？」

「テストで気になる点がゼロでなくても、
 軽微なものは許容してリリースする、ということはできますか？」

「最終的に「合格」と判断するのは誰で、
 どのような手続きで承認してもらえますか？」
```

---

### Section 3：合格基準の設定

**一言でいうと：「なんとなくOK」ではなく、判断できる基準を事前に作る。**

受入テストで最も揉めやすいのが「合格基準の曖昧さ」です。
「問題なかったのでOKです」という判断は、
後から「やっぱりここが違う」という追加要求の温床になります。

**合格基準の設定例：**

```
【合格とみなす基準（例）】
  ① 必須機能（Must）がすべて動作すること
  ② 業務上クリティカルな不具合（業務が止まるレベル）がゼロであること
  ③ 軽微な不具合（表示上の問題・使い勝手の改善）は
     リリース後対応として許容すること
  ④ 上記を、最終承認者（○○部長）が書面でサインすること
```

**不具合の重大度分類（例）：**

| 重大度 | 定義 | リリース判断 |
|------|------|-----------|
| **Critical** | 業務が完全に止まる。データが壊れる | リリース不可・必ず修正 |
| **High** | 主要機能が使えない。代替手段がない | 修正後にリリース |
| **Medium** | 不便だが業務は継続できる | リリース後に修正 |
| **Low** | 軽微な表示の問題・使い勝手の改善 | 次回アップデートで対応 |

この基準を超概算フェーズで合意しておくことで、
「これは直してからリリースすべきか」という判断をその場でできるようになります。

---

### Section 4：検収・支払いとの関係

**一言でいうと：受入テストの完了が「検収＝正式な引渡し」につながり、入金に直結する。**

受入テストはベンダーにとって、単なる品質確認ではありません。
**検収の合意が、請求・支払いのトリガーになります。**

```
受入テスト完了
    ↓
顧客が「合格」と判断
    ↓
検収書への署名・捺印
    ↓
ベンダーが請求書を発行
    ↓
顧客が支払い
```

この流れを顧客と事前に共有しておくことで：
- 「検収書にサインするとは知らなかった」という混乱を防げる
- 検収完了のタイミングを双方で認識できる
- 「口頭でOKと言ったがサインはしていない」というトラブルを防げる

```
確認の問いかけ：
「受入テストが完了し、問題ないと判断された後、
 正式に受け入れを承認する手続き（検収）はどんな形を想定していますか？」

「検収書（確認書）へのサインは、
 どなたが行う権限をお持ちですか？」

「サインまでに、社内の決裁プロセスはどれくらい時間がかかりますか？」
```

### Section 5：よくある失敗と対策

**一言でいうと：「やります」という言葉と「できる体制がある」は別物。**

#### 失敗パターン1：受入テストの担当者が直前まで決まらない

「誰がやるかはリリースが近づいたら決めます」と言われ、
結局テスト開始2日前に初めて担当者が決まった。
その担当者はシステムを初めて見る状態だった。

**対策：** 超概算フェーズで「○月には担当者を決め、要件定義フェーズで業務を把握してもらう」という
ロードマップを提示し、早期確定を促す。

#### 失敗パターン2：受入テストが「形式的なOK」になる

「忙しいので軽く確認してOKにした」と言われたが、
本番後に「こんな動きだとは思わなかった」が続出した。

**対策：** 受入テストで確認すべき重要シナリオをリスト化し、
「このシナリオを全員が確認してOKを出す」という形式にする。
「軽く確認」が起きないように、テスト項目を可視化する。

#### 失敗パターン3：「受入テスト合格後の追加修正」の扱いが曖昧

受入テストに合格してリリースしたが、
本番稼働後に「やっぱりここを変えてほしい」が来た。
「テスト時に見落としていたので直してほしい」か
「仕様変更なので追加費用が必要」かの判断が曖昧だった。

**対策：** 「検収完了後の変更は仕様変更として追加費用が発生する」という基準を
検収書や契約書に明記しておく。

---

### Section 6：確認結果の記録方法

**一言でいうと：体制・期間・合格基準・検収手続きをセットで記録する。**

**受入テスト確認シート（超概算時点）：**

```
■ 受入テスト計画（20XX年XX月XX日時点）

【実施体制】
  テスト実施者 ：営業部 田中様・山田様（現場の実際のユーザー）
  最終承認者   ：営業部長 鈴木様
  ベンダー支援 ：テスト環境準備・不具合対応・テスト項目リスト提供

【実施期間】
  期間        ：2週間（本番リリースの3週間前〜1週間前）
  不具合対応  ：テスト期間内に修正・再確認

【確認内容】
  主要シナリオ ：受注〜請求・月次締め・マスタ管理（計30シナリオ）
  テスト項目  ：ベンダーがリスト化・顧客が確認・合意してから実施

【合格基準】
  条件①      ：Critical・High不具合がゼロであること
  条件②      ：Medium以下の不具合はリリース後対応で許容
  条件③      ：最終承認者（鈴木部長）が検収書にサイン

【検収・支払い】
  検収手続き  ：検収確認書への署名・捺印
  支払いタイミング：検収書受領後30日以内

■ 前提条件
  - テスト担当者は要件定義フェーズ（○月）から業務把握に参加いただく
  - 検収完了後の変更は仕様変更として別途見積もりが必要
  - テスト期間の短縮はリスクが高まることを双方で合意済み
```

## まとめとネクストアクション

### 3つの重要ポイント

1. **受入テストは「品質確認」ではなく「正式な引渡し」。検収・入金に直結する**
   「なんとなくOK」ではなく、最終承認者のサインをもって完了とする。
   この認識を顧客と共有することが、検収トラブルを防ぐ最大の対策。

2. **合格基準を事前に定義する。「Critical不具合ゼロ」が最低ライン**
   「問題なければOK」は合格基準ではない。
   不具合の重大度分類と、どのレベルまで許容してリリースするかを事前に合意する。

3. **受入テストの担当者と最終承認者を早期に確定させる**
   「リリース直前に誰かに頼む」では必ず失敗する。
   要件定義フェーズから担当者を巻き込み、システムを理解してもらうことが重要。
