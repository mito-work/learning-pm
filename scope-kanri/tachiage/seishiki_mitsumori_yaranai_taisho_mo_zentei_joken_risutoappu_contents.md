# スコープ管理 > 立ち上げ

## 正式見積：やらない対象も前提条件としてリストアップ

---

## 導入

### このスキルを身につけると、何が変わるか

「スコープ外と説明したのに『含まれていると思っていた』と言われた」
「見積書に書いていなかったデータ移行の作業が、当然やってもらえるものとして進んでいた」
「ユーザーマニュアルの作成は当然含まれると顧客が思っており、後から無償で対応することになった」——

「やらないことを言わなかったこと」は、「やることを言わなかったこと」と同じくらい問題を起こします。
見積もりに「やること」だけを書き、「やらないこと」を書かなければ、顧客は「書いていないこともやってもらえる」と解釈しがちです。
このスキルは、**「やらない対象」を単なるスコープ外リストではなく「前提条件」として明文化し、見積もりの合意を堅固にする**技術です。

このスキルを学ぶことで：
- 「含まれると思っていた」という認識のズレを構造的に防げる
- 追加要求が来たとき「前提条件の変更として扱う」根拠が生まれる
- 「暗黙のスコープ外」を可視化し、顧客と明示的に合意できる
- 見積もりの境界線が双方にとって明確な共通認識になる

---

## 学習目標

このテキストを読み終えると、以下ができるようになります。

1. **「やらない対象」を前提条件の形式で書く理由と効果を説明できる**
2. **5つのカテゴリ（機能・システム・作業・データ・運用）でやらない対象を洗い出せる**
3. **「暗黙のスコープ外」を言語化し、顧客との合意に組み込める**

## 本編

### Section 1：「スコープ外リスト」と「前提条件」——なぜ書き方が違うと効果が変わるのか

**一言でいうと：「スコープ外」は「今回はやらない」という一覧止まりだが、「前提条件」は「これを仮定して見積もっている」という合意になる。**

同じ内容でも、書き方次第で顧客の受け取り方が変わります。

```
【書き方の比較：データ移行を例に】

❶ スコープ外リストの書き方
  「スコープ外：データ移行」

  顧客の解釈：「今回はやらないが、費用を追加すればやってもらえる」
            「プロジェクトの中でいつかやってもらえる」

❷ 前提条件の書き方
  「既存データの移行は含まない（手動での移行は顧客様が実施する）
   ことを前提として見積もっています。
   移行対応が必要になった場合、別途工数見積もりと
   追加費用のご相談が必要です。」

  顧客の解釈：「移行は自分たちでやる前提になっている。
            必要なら改めて依頼しなければいけない」
```

「前提条件として書く」ことで、3つの効果が生まれます。

```
効果①：合意の重みが変わる
  「スコープ外と聞いた」→「前提条件として合意した」の違い

効果②：後から追加要求が来たときの根拠になる
  「前提条件が変わったため、追加工数が発生します」と言える

効果③：顧客が「自分たちがやること」を認識する
  「顧客が実施する」と書かれることで、顧客側の準備が促される
```

### Section 2：5つのカテゴリで「やらない対象」を洗い出す

**一言でいうと：「やらないこと」は「作らない機能」だけではない。作業・データ・運用まで5つのカテゴリで漏れなく洗い出す。**

「やらない対象」は、機能だけではありません。
以下の5カテゴリで系統的に洗い出すことで、見落としを防ぎます。

#### カテゴリ①：機能スコープ外（今回作らない機能・画面）

```
前提条件の書き方例：

「○○機能（レポート出力機能）は今回のスコープに含まれません。
 必要になった場合、次フェーズでの追加開発となります。」

「管理者向け設定画面は含まれません。
 設定変更はシステム設定ファイルの直接編集で対応します。」
```

#### カテゴリ②：対象システム外（今回手を入れないシステム・連携しないシステム）

```
前提条件の書き方例：

「○○システム（在庫管理システム）との連携は含まれません。
 連携が必要になった場合、別途インターフェース設計・開発が必要です。」

「スマートフォンアプリへの対応は含まれません。
 PCブラウザのみの対応とします。」
```

#### カテゴリ③：作業スコープ外（顧客が自分でやること・ベンダーがやらないこと）

```
前提条件の書き方例：

「本番環境へのリリース作業は顧客様が実施することを前提とします。
 手順書は提供しますが、実作業はお客様の担当者が行います。」

「受入テスト（UAT）の実施は顧客様が行うことを前提とします。
 テスト計画書・テストケースは提供しますが、
 実施・結果判定は顧客様の担当者が行います。」

「ユーザーへの操作説明・研修は含まれません。
 操作マニュアルの提供のみとします。」
```

#### カテゴリ④：データスコープ外（移行しないデータ・管理しないデータ）

```
前提条件の書き方例：

「○年以前の過去データの移行は含まれません。
 移行対象は直近○年分のデータとします。」

「既存データのクレンジング・正規化は含まれません。
 データの品質保証は顧客様の責任範囲とします。」

「マスタデータ（商品マスタ・顧客マスタ）の
 初期投入は顧客様が実施することを前提とします。」
```

#### カテゴリ⑤：運用・保守スコープ外（本番稼働後の作業）

```
前提条件の書き方例：

「本番稼働後の運用保守（障害対応・問い合わせ対応）は
 今回の契約に含まれません。
 別途保守契約のご締結が必要です。」

「本番稼働から○ヶ月後以降のバグ対応は
 今回の契約スコープ外となります。」

「追加機能の開発・仕様変更への対応は
 本プロジェクト完了後、改めてお見積もりします。」
```

### Section 3：「暗黙のスコープ外」を言語化する

**一言でいうと：「当然やらないと思っていること」でも、顧客には「当然やってもらえると思っていること」であるケースがある。**

PMが「言うまでもない」と思っていることが、顧客の期待と食い違うことは多いです。

```
よくある「暗黙のスコープ外」と顧客の期待のズレ：

PMの認識                   顧客の期待（よくある誤解）
────────────────────────────────────────────
ユーザーマニュアルは作らない → 当然作ってくれると思っていた
本番リリース作業はやらない   → 「納品」にはリリースまで含まれると思っていた
既存データの整理はやらない   → 移行前にきれいにしてもらえると思っていた
性能テストはやらない        → テストフェーズに含まれると思っていた
本番後の問い合わせ対応はしない→ バグが出たら無償で直してもらえると思っていた
他部門への説明資料は作らない  → プロジェクト説明用の資料も作ってもらえると思っていた
```

これらを「暗黙のスコープ外」のまま放置すると、プロジェクト中に「当然やってもらえると思っていた」という要求が出てきます。

#### 暗黙のスコープ外を洗い出す方法

```
PMが「当然やらない」と思っている事項を書き出すチェック：

① 「これは見積もりに含めていないけど、聞かれたらどう答えるか？」
  → 「含まれていません」と答えるものはすべて前提条件にする

② 「顧客が納品物を受け取ったとき、『これだけですか？』と
  言うとしたら何について言いそうか？」
  → その「言いそうなこと」が暗黙のスコープ外

③ 過去のプロジェクトで「含まれていると思っていた」と
  言われた事項を列挙する
  → 自社の経験則から「要注意な暗黙スコープ外」を積み上げる
```

### Section 4：前提条件として書く際のフォーマット

**一言でいうと：「○○はやらない」だけでは弱い。「なぜ・誰がやるか・変わった場合は」の3点を添える。**

「やらない対象」を前提条件として書くときの構成：

```
前提条件の構成：

① やらない対象：何が含まれないか
② 代替の扱い：誰がやるか・どう対処するか
③ 変更した場合の影響：これが変わった場合の対応

例：
「○○機能（CSVエクスポート）は今回のスコープに含まれません①。
 データの抽出はシステム担当者がDBに直接アクセスして行います②。
 エクスポート機能が必要になった場合は、別途工数見積もりの
 ご相談が必要です③。」
```

#### 顧客への提示方法

「やらない対象」の前提条件は、できれば「やること」と同じドキュメントに並べて示します。

```
見積書への記載例：

【本見積もりに含まれる主な作業】
  ・○○機能の設計・開発・テスト
  ・○○システムとのインターフェース実装
  ・単体テスト・結合テスト

【本見積もりの前提条件（含まれない作業）】
  ・データ移行（顧客様が実施）
  ・本番リリース作業（手順書を提供、作業は顧客様が実施）
  ・ユーザーマニュアルの作成
  ・本番稼働後の保守・運用対応
  ・受入テスト（顧客様が実施）
```

「含まれるもの」と「含まれないもの」を同じページに並べることで、顧客が「読み飛ばす」ことを防ぎます。

---

### Section 5：顧客との合意——「やらない対象」を受け入れてもらう伝え方

**一言でいうと：「やらない」の伝え方が悪いと、合意する前に関係が悪化する。「誰がやるか」を明確にすることが鍵。**

「やらないこと」を顧客に伝えるときは、「できません」ではなく「この範囲でお見積もりしています」という言い方を使います。

```
避けるべき伝え方：
  「データ移行はスコープ外なのでやりません」
  → 「やらない」という突き放した印象になる

推奨する伝え方：
  「今回の見積もりでは、データ移行は含まれていません。
   移行作業は○○様のシステム担当者が行う前提で
   整理しています。
   もし弊社でのご対応が必要でしたら、別途工数をお見積もり
   しますのでご相談ください。」
```

「やらない」を「誰がやるか」の明確化とセットにすることで、顧客が「では誰がやるのか」を考えるきっかけになります。
「弊社でやる場合は追加費用」という選択肢を示すことで、押しつけではなく「選択の確認」になります。

## まとめとネクストアクション

### 3つの重要ポイント

1. **「スコープ外」ではなく「前提条件」として書くことで、合意の重みが変わる**
   「スコープ外」は「今回はやらない一覧」にすぎない。
   「前提条件」として書くことで「この仮定のもとで見積もっている」という合意になり、後の追加要求を変更依頼として扱う根拠ができる。

2. **「暗黙のスコープ外」を洗い出して言語化する**
   「当然やらない」と思っていることでも、顧客は「当然やってもらえる」と思っているケースがある。
   本番リリース・マニュアル作成・データ移行・保守対応は、特に「暗黙の期待」が生まれやすい。

3. **「やらない」は「誰がやるか」とセットで伝える**
   「やりません」で終わると顧客は宙ぶらりんになる。
   「○○は顧客様が実施する前提です。ご依頼の場合は別途お見積もりします」という形が、関係を壊さずに境界線を引く伝え方。
