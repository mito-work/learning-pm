# スコープ管理 > 立ち上げ

## 正式見積：スコープ変更時の追加見積等の合意

---

## 導入

### このスキルを身につけると、何が変わるか

「仕様変更のたびに顧客と追加費用の交渉になり、関係が悪化した」
「『ちょっとした修正』を積み重ねていたら、工数が見積もりの2倍近くになっていた」
「スコープ変更の記録がなく、最終的に何がどう変わったのかを誰も把握できなかった」
「追加費用を請求しようとしたが、変更ルールを事前に決めていなかったため根拠がなかった」——

スコープ変更は、すべてのプロジェクトで起きます。問題は「変更が起きること」ではなく、「変更が起きたときのルールを決めていないこと」です。
このスキルは、**正式見積フェーズで「スコープが変わったときに何が起きるか」を事前に顧客と合意し、変更管理の仕組みをプロジェクト開始前に設計する**技術です。

このスキルを学ぶことで：
- 変更が起きたときに追加費用・スケジュール変更を根拠を持って提示できる
- 「小さな変更の積み重ね」でスコープが崩れるスコープクリープを防げる
- 変更管理のプロセスが透明になり、顧客との信頼関係を保ちながら変更に対応できる
- 変更の記録が残り、プロジェクト全体で「何がどう変わったか」を追跡できる

---

## 学習目標

このテキストを読み終えると、以下ができるようになります。

1. **「スコープ変更」に当たる事項の定義を顧客と合意できる**
2. **変更管理のプロセス（申請→影響分析→追加見積→承認）を設計して運用できる**
3. **変更ルールを「プロジェクトを守る仕組み」として顧客に説明できる**

## 本編

---

### Section 1：なぜ「変更ルール」を見積もり段階で決めるのか

**一言でいうと：変更が起きてから「追加費用が発生します」と言っても遅い。「変わったら費用が変わる仕組み」を事前に合意しておく。**

変更ルールを決めずにプロジェクトを始めると、こうなります。

```
【変更ルールなしのプロジェクト】

  プロジェクト中盤、顧客から変更依頼が来る：
  「この画面にCSV出力機能も追加してほしい」
  ↓
  PM：「追加費用が発生しますがよいですか？」
  顧客：「そんな話は最初に聞いていない。
        少し追加するだけでなぜ費用が増えるのか」
  ↓
  ・「最初から含まれるべきだった」vs「スコープ外だ」の水掛け論
  ・顧客関係が悪化する
  ・吸収するか追加費用を請求するか、その都度交渉が必要になる
  ・積み重なると工数が崩壊する
```

変更ルールを事前に合意しておくと：

```
【変更ルール合意済みのプロジェクト】

  同じ変更依頼が来る：
  「この画面にCSV出力機能も追加してほしい」
  ↓
  PM：「変更依頼として受け付けます。
      影響を確認したうえで追加工数と費用をご提示します。
      （事前合意のルール通り）」
  顧客：「わかりました。では確認してから判断します」
  ↓
  ・合意ずみのプロセスを踏んでいるため、顧客も手続きとして受け入れやすい
  ・追加費用の提示が「交渉」ではなく「確認」になる
  ・記録に残る
```

「変更管理のルール」は、プロジェクトが正常に動いているときに決めるものです。
問題が起きてから決めようとすると、感情的になっているときに議論が発生します。

---

### Section 2：合意すべき3つの要素——「何が変更か」「どうするか」「費用はどうなるか」

**一言でいうと：変更管理の合意は「定義・プロセス・費用の扱い」の3点をセットで決める。**

#### 要素①：「スコープ変更」に当たる事項の定義

何が「スコープ変更」で、何が「変更ではない（通常対応の範囲）」かを定義します。

```
スコープ変更に当たる事項の例：
  ✅ 機能の追加（見積もりに含まれていない機能の新規追加）
  ✅ 機能の仕様変更（確定後の仕様を変更する）
  ✅ 対象システム・連携先の追加（当初スコープ外のシステムへの対応）
  ✅ 前提条件の変更（「○○は顧客が実施」を「ベンダーが実施」に変更）
  ✅ 成果物の追加（含まないと合意した成果物の追加）
  ✅ 顧客都合によるスケジュール変更（日程が延長・短縮された場合の対応工数）

スコープ変更に当たらない事項の例：
  ❌ 仕様確定前の仕様の詳細化・具体化
  ❌ 軽微なUI調整（ボタンの色・配置など工数が極小のもの）
  ❌ 当初想定内の仕様確認・質問への回答
```

「軽微な変更」の線引きは、プロジェクトごとに合意が必要です。
「○人日以内の作業は追加費用なし・以上は追加見積もり」という閾値を設けることもあります。

#### 要素②：変更管理のプロセス

変更が発生したときの手続きの流れを定義します。

```
変更管理の基本フロー：

STEP1. 変更依頼の受付
  ・誰から：顧客の窓口担当者から
  ・どうやって：変更依頼書（メール・フォームなど）で申請
  ・内容：「何を・なぜ・いつまでに」変更したいかを記載

STEP2. 影響分析
  ・PMがPLと確認：工数・スケジュール・コストへの影響を分析
  ・期間：○営業日以内に回答（例：3〜5営業日）

STEP3. 追加見積もりの提示
  ・追加工数・費用・スケジュールへの影響を文書化して提示
  ・「変更する場合」と「変更しない場合（現状維持）」の両方を示す

STEP4. 顧客の承認
  ・顧客が追加費用・スケジュール変更を確認・承認
  ・承認なしに変更着手しない（口頭承認のみでは着手しない）

STEP5. 変更の実施と記録
  ・承認後に変更作業を着手
  ・変更内容・承認日・費用を変更管理台帳に記録
```

#### 要素③：追加費用・スケジュール変更の基本的な扱い

```
追加費用の扱いの合意例：

「スコープ変更が生じた場合、以下の方針で対応します：

 ① 変更依頼を受けた後、○営業日以内に
   追加工数と費用をお見積もりします

 ② 追加費用はご承認後に確定します。
   承認なしに追加作業に着手することはありません

 ③ 変更による工数増加がスケジュールに影響する場合は、
   スケジュールの変更についても同時にご相談します

 ④ 軽微な変更（○人日以内）については、
   プロジェクト全体の状況を見て吸収を検討します。
   ただし、この範囲を超える変更は追加費用が発生します」
```

### Section 3：変更依頼書（Change Request）の設計

**一言でいうと：変更の記録を残す最小限のフォーマットを作っておくことが、後のトラブルを防ぐ。**

変更管理のプロセスを機能させるには、変更依頼の記録が必要です。
複雑なフォーマットは使われなくなるため、シンプルに保ちます。

#### 変更依頼書の最小フォーマット

```
【変更依頼書（Change Request）】

No.：CR-001
受付日：○月○日
依頼者：（顧客担当者名）

■ 変更の内容
  （何をどう変えたいか）

■ 変更の理由・背景
  （なぜ変更が必要か）

■ 変更希望時期
  （いつまでに対応してほしいか）

---（以下、PM記入欄）---

■ 影響分析
  追加工数：○人日
  費用影響：○万円（追加）
  スケジュール影響：○週間の延長
  変更対象ファイル・仕様書：

■ 判断
  □ 承認（着手します）
  □ 条件付き承認（○○を条件に対応します）
  □ 保留（次回フェーズで対応）
  □ 却下（理由：）

承認日：
承認者：
```

### Section 4：スコープクリープを防ぐ「小さな変更の積み重ね」への対処

**一言でいうと：「ちょっとした修正」を1つひとつ承認するより、積み上げてから可視化して一括確認するほうが現実的。**

実務では、顧客からの「ちょっとした修正」が積み重なって気づいたら大工数になっているケースがあります。

```
よくある「ちょっとした修正」の積み重ね：

  「ここの文言を変えてほしい」→ 0.5人日
  「この項目を追加してほしい」→ 1人日
  「この処理の順番を変えてほしい」→ 1人日
  「エラーメッセージを変えてほしい」→ 0.5人日
  「この画面にボタンを追加してほしい」→ 2人日
  ……
  気づいたら：計○人日（見積もりの○%超）
```

この問題への対処として、以下のアプローチが有効です。

```
対処①：変更バッファを設けて明示する
  「通常の仕様調整・軽微な修正に対応するための
   バッファとして○人日を見積もりに含めています。
   この範囲内の修正は追加費用なしで対応します。
   超過した場合は追加費用が発生します。」
  → バッファを「見える化」することで、顧客も「無尽蔵ではない」と理解する

対処②：変更の累積を定期的に可視化する
  「今月の変更依頼の累計は○人日です。
   残りバッファは○人日です。」
  → 月次定例会等で報告することで、顧客が自発的に変更を絞り込む動機になる

対処③：変更の「着手前承認」を徹底する
  「口頭の依頼は記録として着手しません。
   変更依頼書（メール可）での確認後に着手します。」
  → 「口頭で言ったはずだ」という要求を防ぐ
```

### Section 5：変更ルールを顧客に説明する——受け入れてもらうための伝え方

**一言でいうと：「ルールを守ってください」ではなく「このルールがあると顧客にとってもよいことがある」と伝える。**

変更管理ルールを顧客に説明するときは、顧客のメリットを軸に伝えます。

```
顧客への説明例：

「プロジェクト中に仕様の追加・変更が生じた場合、
 以下のプロセスで対応させていただきます。

 変更が発生した際に影響（工数・費用・スケジュール）を
 事前にお伝えしてから着手します。

 このプロセスには、お客様にとって以下のメリットがあります：

 ① 変更の影響が見える化される
   「これをお願いしたらどうなるか」が先にわかり、
   優先順位の判断がしやすくなります

 ② 計画外の費用・遅延を防げる
   承認前に影響を確認できるため、
   意図しないコスト増加・スケジュール遅延を防げます

 ③ 変更の記録が残る
   プロジェクト全体を通じて何が変わったかが追跡でき、
   後から確認・参照することができます

 このルールは顧客様のプロジェクトを守るための仕組みです。
 ご理解とご協力をお願いします。」
```

## アクティブラーニング

以下の問いについて、自分のPJを思い浮かべながら考えてみてください。

**問い1：**
今担当しているPJに「スコープ変更のルール」はありますか？
顧客と明示的に合意していますか？

**問い2：**
過去のPJで、変更ルールなしに「ちょっとした修正」を積み重ねた結果、工数が崩れた経験はありますか？
そのとき、事前にルールがあれば何が変わっていましたか？

**問い3：**
顧客から変更依頼が来たとき、書面（メール・変更依頼書）で受け付けていますか？
口頭の依頼をそのまま着手して、後から「そんな依頼はしていない」と言われたことはありますか？

## まとめとネクストアクション

### 3つの重要ポイント

1. **変更管理ルールは「問題が起きてから」ではなく「見積もり段階で」合意する**
   変更が起きてから「追加費用が発生します」と言っても、顧客は受け入れにくい。
   「何が変更で・どう対応して・費用はどうなるか」を事前に合意することで、変更が「交渉」ではなく「プロセスの実行」になる。

2. **「小さな変更の積み重ね」への対処には変更バッファの可視化が有効**
   バッファとして○人日を明示し、累計を月次で可視化することで、顧客が変更の「残量」を意識するようになる。
   「無尽蔵に対応してもらえる」という認識を構造的に防ぐ。

3. **変更管理ルールは「顧客のメリット」として伝える**
   「ルールを守ってください」では顧客は義務感を覚える。
   「影響が見える化できる・計画外費用を防げる・記録が残る」というメリットを伝えることで、変更管理の仕組みへの協力を得やすくなる。

> **今担当しているPJの変更管理ルールを確認する。ルールがない場合、「①変更の定義 ②変更時のプロセス ③軽微な変更の閾値」の3点を1枚のメモにまとめ、次の打ち合わせで顧客に提示する。3点を揃えたメモ1枚が変更管理の出発点になる。**
