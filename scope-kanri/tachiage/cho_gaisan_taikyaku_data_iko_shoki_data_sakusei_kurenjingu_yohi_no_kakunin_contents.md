# スコープ管理 > 立ち上げ

## 超概算：【対客】データ移行／初期データ作成／クレンジング要否の確認

---

## 導入

### このスキルを身につけると、何が変わるか

「既存のデータをそのまま移せばいいだけですよね？」
この一言が、プロジェクトを大きく狂わせることがあります。

データ移行は「コピーするだけ」ではありません。
- 20年分の顧客データに、重複・表記ゆれ・欠損が山積みだった
- Excelで管理していたデータがバラバラで、システムに入れられる形ではなかった
- 移行テストをしたら、1割のデータが移行できずに手作業で対応した

データ移行・初期データ作成・クレンジングは、
「機能開発と同じくらい、あるいはそれ以上の工数がかかる」こともある領域です。
超概算フェーズで要否と規模を確認しておくことで：

- 「データを移せばいいだけ」という甘い見積もりを防げる
- クレンジングの担当（顧客側か、ベンダー側か）を早期に合意できる
- データ移行に起因するスケジュール遅延を未然に防げる

---

## 学習目標

このテキストを読み終えると、以下ができるようになります。

1. **データ移行・初期データ作成・クレンジングの違いを説明できる**
2. **顧客からデータの現状と移行要件を引き出す問いかけができる**
3. **データ移行の規模と役割分担を超概算の前提条件として整理できる**

## 本編

---

### Section 1：3つの作業の違いを理解する

**一言でいうと：「既存データを使うか」「ゼロから作るか」「品質を整えるか」の3つです。**

引越しで例えると：
- **データ移行** ＝ 今の家の荷物を新しい家に運ぶ作業
- **初期データ作成** ＝ 新しい家に必要な家具を新たに買い揃える作業
- **クレンジング** ＝ 運ぶ前に不要なものを捨て、荷物を整理・分類する作業

引越し当日に「整理されていない荷物をそのまま運ぶ」と、
新しい家が使い物にならない状態になります。
システムも同様です。

| 作業 | 意味 | 具体例 |
|-----|------|------|
| **データ移行** | 旧システム・既存データを新システムに移す | 旧販売管理の顧客データを新システムへ |
| **初期データ作成** | 新システム稼働に必要なマスタ・設定をゼロから作る | 商品マスタ・コード表の新規作成 |
| **クレンジング** | データの重複・誤り・ゆれを整理・修正する | 「（株）」「株式会社」の表記統一 |

---

### Section 2：データ移行の規模確認

**一言でいうと：「どこから・何件・何テーブル」を確認する。**

データ移行の工数は、移行元の数・件数・複雑さで決まります。

#### 移行元の確認

```
使える質問：
「今のデータはどこで管理されていますか？
 旧システム・Excel・Access・紙・複数の混在、どれですか？」
「移行したいデータの種類（顧客・商品・受注履歴など）を教えてください。」
「何年分のデータを移行する必要がありますか？」
```

**移行元の種類と難易度：**

| 移行元 | 難易度 | 主な課題 |
|------|------|--------|
| 既存システム（DB） | 中〜高 | 旧DB構造の解析・変換が必要 |
| Excel・Access | 中 | ファイルが分散・フォーマットが統一されていない |
| 紙・手書き | 高 | デジタル化から始める必要がある |
| 複数ソースの混在 | 高 | データの名寄せ・突合が必要 |

#### 件数と種類の確認

```
使える質問：
「顧客データは何件くらいありますか？（例：1万件・50万件）」
「受注履歴は何年分・何件移行しますか？
 または直近○年分だけでよいですか？」
「商品・取引先などのマスタデータは何種類・何件ですか？」
```

移行件数が多いほど、移行プログラムの開発・テスト・検証の工数が増えます。
また「全件移行」か「一部移行（直近○年分のみ）」かで工数が大きく変わります。

---

### Section 3：クレンジングの要否確認

**一言でいうと：データの「汚れ」を事前に把握し、誰が清掃するかを決める。**

長年運用されてきたデータには、さまざまな「汚れ」があります。
この汚れを放置したまま移行すると、新システムが正しく動かなくなります。

**よくあるデータの「汚れ」：**

| 汚れの種類 | 具体例 |
|---------|------|
| **重複** | 同じ顧客が別の名前で二重登録されている |
| **表記ゆれ** | 「株式会社ABC」「（株）ABC」「ABC株式会社」が混在 |
| **欠損・空白** | 必須項目が空白のレコードが多数ある |
| **フォーマット不統一** | 日付が「2024/01/01」「20240101」「R6.1.1」と混在 |
| **誤り・古い情報** | 退会済み顧客・廃番商品がアクティブ状態のまま |
| **文字コード問題** | 旧システムの文字が新システムで文字化けする |

```
確認の問いかけ：
「今のデータは、きれいに整理されていると思いますか？
 それとも、ダブりや誤りが混じっていそうですか？」
「同じ顧客が複数の名前で登録されているようなことはありますか？」
「日付・電話番号・住所などの形式は統一されていますか？」
```

多くの場合、顧客は「データの汚れ」を過小評価しています。
「確認してみたら想定以上に汚かった」は、データ移行PJの定番トラブルです。

**クレンジングの担当を早期に合意する：**

クレンジング作業は、業務知識がないと判断できない部分が多いです。
（この顧客は有効か？この商品は廃番か？）

```
担当の選択肢：
① 顧客側がクレンジングしてから渡す
② ベンダー側がクレンジングツールを作り、顧客が内容を確認する
③ ベンダー側が全て担う（業務知識の学習コストが必要で高コスト）
```

「誰がやるか」を曖昧にすると、後から「てっきりやってくれると思っていた」というトラブルになります。

---

### Section 4：初期データ作成の要否確認

**一言でいうと：新システム稼働前に「最初から必要なデータ」を誰が作るかを決める。**

新システムを動かすには、機能を作るだけでなく、
動かすための「最初のデータ」が必要です。

**初期データの例：**

| 初期データの種類 | 具体例 |
|-------------|------|
| **マスタデータ** | 商品マスタ・取引先マスタ・部門マスタ |
| **コード・区分値** | 都道府県コード・ステータス区分・税率テーブル |
| **組織・権限設定** | 部署・役職・アクセス権限の初期設定 |
| **ワークフロー設定** | 承認フローのルート・条件設定 |
| **テンプレート・文言** | メール送信文・帳票のヘッダー情報 |

```
確認の問いかけ：
「新しいシステムで使う商品・取引先などのマスタデータは、
 旧システムから移行しますか？それとも新しく作り直しますか？」
「コードや区分値（ステータス・カテゴリなど）は、
 今と同じものを使いますか？それとも整理して作り直しますか？」
「初期データは誰が用意しますか？（顧客側かベンダー側か）」
```

初期データの作成は、「顧客側で用意する」のが基本です。
しかし「どういう形式で用意すればよいか」はベンダー側が指定する必要があります。
この役割分担を超概算フェーズで合意しておくことで、手戻りを防げます。

---

### Section 5：移行テストと切替方法の確認

**一言でいうと：「移行後にデータが正しいか確認する作業」と「いつ切り替えるか」も費用に影響する。**

データを移行しただけでは終わりません。
「移行後のデータが正しいか」を検証する作業（移行テスト）が必要です。

#### 移行テストの確認

```
確認の問いかけ：
「移行したデータが正しいかどうか、どうやって確認しますか？」
「移行前と移行後のデータを突合（件数・金額の一致確認）する必要はありますか？」
「移行テストは本番前に何回実施しますか？（リハーサルの回数）」
```

移行テストは、件数が多いほど時間がかかります。
「50万件のデータ移行テストを3回実施する」となれば、それだけで数週間かかることもあります。

#### 切替方法の確認

新旧システムの切替には主に2つの方法があります。

| 切替方法 | 内容 | リスク | コスト |
|--------|------|------|------|
| **一括切替** | ある日を境に旧→新へ完全移行 | 高（失敗したら戻れない） | 低 |
| **並行稼働** | しばらくの間、旧システムと新システムを同時に使う | 低（問題があれば旧に戻れる） | 高（二重運用） |

```
確認の問いかけ：
「リリース後、しばらくは旧システムと新システムを並行して動かしますか？
 それとも一斉に切り替えますか？」
「並行稼働が必要な場合、何ヶ月間を想定していますか？」
```

並行稼働が必要な場合は、その期間中の2重入力・照合作業なども工数に含まれます。

---

### Section 6：確認結果の記録方法

**一言でいうと：要否・規模・担当分担をセットで記録する。**

**データ移行確認シート（超概算時点）：**

```
■ データ移行（20XX年XX月XX日時点）

【移行対象データ】
  顧客マスタ    ：約3万件（旧販売管理システムのDB）
  受注履歴      ：直近3年分・約15万件（旧システムのDB）
  商品マスタ    ：約2,000件（Excelで管理中）
  取引先マスタ  ：約500件（Excelで管理中）

【クレンジング】
  要否          ：必要（顧客名の表記ゆれ・重複が多数存在）
  担当          ：顧客側でクレンジングのうえ、CSVで納品
  ベンダー対応  ：クレンジング確認ツールの提供（工数見積もりに含む）

【初期データ作成】
  コード・区分値 ：ベンダー側で初期投入ツールを作成
  権限設定      ：顧客側で設定内容を定義、ベンダーが初期投入

【移行テスト】
  リハーサル回数：2回実施予定
  突合確認      ：件数・金額の一致を顧客担当が確認

【切替方法】
  方式          ：一括切替（並行稼働なし）
  切替時期      ：XX月XX日（土）深夜

■ 前提条件
  - クレンジングは顧客側で実施。ベンダー側は受け入れツールのみ提供
  - 移行データは本番移行の1週間前までに最終版を受領する
  - 上記以外のデータ追加・移行範囲の変更は追加見積もりが必要
```

## まとめとネクストアクション

### 3つの重要ポイント

1. **「データをコピーするだけ」は幻想。クレンジングが最大の工数になることがある**
   データの「汚れ」は見えにくい。早期に現状を確認し、
   クレンジング担当（顧客 or ベンダー）を合意することがトラブル防止の要。

2. **移行対象のデータ件数・種類・移行元の数が工数を決める**
   「全件移行か一部移行か」「Excelからか旧DBからか」で工数が数倍変わる。
   超概算フェーズで規模感の前提を顧客と合意する。

3. **初期データ・移行テスト・切替方法も見積もりに影響する**
   機能開発だけが工数ではない。
   移行テストのリハーサル回数・並行稼働期間も、工数とスケジュールに直結する。
