# スコープ管理 > 立ち上げ

## 超概算：【対客】総合テスト（シナリオテスト）の実施要否／分担の確認

---

## 導入

### このスキルを身につけると、何が変わるか

「テストはベンダーがやるものでしょ？」
「テストはこちら（顧客）でやりますよ、問題ありません」

この認識が食い違ったまま進んだPJは、リリース直前に崩壊します。

- ベンダー側はテストを計画していなかった。顧客が実施するつもりだった
- 顧客側は担当者のリソースがなく、結局ベンダーに丸投げになった
- シナリオテストの期間が短すぎて、業務上の不具合が本番後に発覚した

総合テスト・シナリオテストは、
「誰が・何を・いつ・どれくらいやるか」の合意が最も曖昧になりやすい工程です。
超概算フェーズで要否と分担を確認することで：

- テスト工数を正しく見積もりに含めることができる
- 顧客側のリソース（人・期間）を事前に確保してもらえる
- 「テストで不具合が出ても直してもらえない」というトラブルを防げる

---

## 学習目標

このテキストを読み終えると、以下ができるようになります。

1. **テストの種類と、各テストの目的・実施者の違いを説明できる**
2. **総合テスト・シナリオテストの要否と分担を顧客と合意するための問いかけができる**
3. **テスト計画の前提条件を超概算の見積もりに反映できる**

## 本編

---

### Section 1：テストの種類と担当の全体像

**一言でいうと：テストには段階があり、誰が担うかが工数とスケジュールを左右する。**

システム開発のテストは、一度にまとめて行うのではなく、
段階的に積み上げていくものです。

料理で例えると：
- **単体テスト**＝食材の鮮度を個別に確認する（素材単位）
- **結合テスト**＝炒めた食材どうしがうまく合うか確認する（工程単位）
- **システムテスト**＝料理全体が完成形として成り立つか確認する（料理単位）
- **総合テスト（シナリオテスト）**＝実際に食事として提供し、お客様の食べる体験を通して確認する（体験単位）

**テストの種類と一般的な実施者：**

| テストの種類 | 目的 | 一般的な実施者 |
|-----------|------|------------|
| **単体テスト** | 個々の機能・部品が正しく動くか | ベンダー（開発者） |
| **結合テスト** | 機能間の連携が正しく動くか | ベンダー |
| **システムテスト** | システム全体が設計通りに動くか | ベンダー |
| **総合テスト** | 業務の流れ全体でシステムが使えるか | **顧客 or ベンダー（要合意）** |
| **ユーザー受入テスト（UAT）** | 顧客が「これで使える」と確認するテスト | **顧客**（ベンダーが支援） |

単体〜システムテストはベンダーが実施するのが基本です。
しかし**総合テスト（シナリオテスト）以降は、顧客の参加が必要になります。**

---

### Section 2：総合テスト・シナリオテストとは何か

**一言でいうと：「実際の業務の流れ」で、システムが問題なく使えるかを確認するテスト。**

シナリオテストは「ケース単体の動作確認」ではなく、
「業務の流れを一連で追う」テストです。

**シナリオテストの例（受注管理システムの場合）：**

```
【シナリオ：受注から請求まで】

① 顧客から注文が来る → 受注登録画面で入力
② 在庫を確認する → 在庫管理画面で確認
③ 出荷指示を出す → 出荷指示画面で登録
④ 納品書を印刷する → 帳票出力で確認
⑤ 請求書を発行する → 請求管理画面で発行
⑥ 入金を登録する → 入金管理画面で登録
⑦ 月次売上レポートに反映される → 集計レポートで確認
```

このように「一連の業務の流れ」を通して確認することで、
「各画面は動くが、業務として使えない」という問題を発見できます。

**単体テストでは発見できない不具合の例：**
- 受注登録したデータが、請求画面に正しく連動していない
- 帳票の数字が、受注画面で入力した内容と一致しない
- 月末締め処理を実行すると、翌月の受注データが消える

シナリオテストは**「業務知識がある人」**でないと実施できないため、
顧客側の参加が不可欠です。

---

### Section 3：総合テストの要否・分担確認

**一言でいうと：「誰が・どんなシナリオを・何件・いつ・どれくらいの期間でやるか」を確認する。**

#### ① 実施者の確認

```
使える質問：
「総合テスト（実際の業務の流れでシステムを使ってみるテスト）は、
 御社の担当者様にご参加いただく予定はありますか？」

「テスト担当者として、何名くらいのリソースを確保できますか？」

「テスト期間中（例：2〜4週間）、担当者様は他の業務と兼務ですか？
 テスト専任で動ける方はいますか？」
```

テスト担当者が「兼務で片手間に対応」になると、
テストが長引いてリリースが遅れる原因になります。

#### ② シナリオ数の確認

```
使える質問：
「業務の流れで確認したいシナリオ（パターン）はいくつくらいありそうですか？」
「通常パターンだけでよいですか？
 それとも月末処理・エラー発生時・例外ケースなども確認しますか？」
「テストケース（確認項目）は誰が作りますか？（ベンダー側で用意するか、顧客側で作るか）」
```

シナリオ数の目安：

| システム規模 | シナリオ数の目安 |
|-----------|-------------|
| 小規模（画面10枚以下） | 10〜30シナリオ |
| 中規模（画面10〜30枚） | 30〜100シナリオ |
| 大規模（画面30枚以上） | 100シナリオ以上 |

#### ③ テスト期間の確認

```
使える質問：
「総合テストに使える期間は、どれくらいを想定していますか？」
「テスト中に不具合が見つかった場合、修正〜再テストのサイクルを何回まわせますか？」
「本番リリース希望日から逆算すると、テスト開始はいつが限界ですか？」
```

テスト期間の目安（一般的な参考値）：

| テスト規模 | 目安の期間 |
|---------|---------|
| 小規模 | 1〜2週間 |
| 中規模 | 2〜4週間 |
| 大規模 | 1〜2ヶ月 |

### Section 4：分担パターンとそれぞれの工数への影響

**一言でいうと：「ベンダーがどこまでやるか」によって、見積もりが大きく変わる。**

総合テストの分担は、主に3つのパターンがあります。

**パターン①：顧客がメインで実施（ベンダーは環境準備・不具合対応のみ）**

```
顧客の作業：テストシナリオ実施・不具合報告・再テスト
ベンダーの作業：テスト環境の準備・不具合の修正・対応

→ ベンダーの工数：低〜中
→ 顧客のリソース：中〜高（担当者の確保が必要）
```

**パターン②：ベンダーがテストケース作成し、顧客が実施**

```
顧客の作業：ベンダーが作成したシナリオに沿って実施・確認
ベンダーの作業：テストケース作成・環境準備・不具合修正

→ ベンダーの工数：中
→ 顧客のリソース：中（シナリオに沿って動けばよい）
```

**パターン③：ベンダーがすべて実施（顧客は最終確認のみ）**

```
顧客の作業：最終的な動作確認・承認
ベンダーの作業：テストケース作成・実施・不具合修正・再テスト

→ ベンダーの工数：高
→ 顧客のリソース：低（最終確認のみ）
→ 注意：業務知識がないと判断できない不具合は、顧客に確認が必要
```

超概算フェーズでどのパターンになるかを確認し、
ベンダー側の工数を適切に見積もりに含めます。

---

### Section 5：よくある落とし穴

**一言でいうと：「テストは最後でいい」「リソースは都合をつける」という言葉を信じない。**

#### 落とし穴1：顧客のテストリソースが確保されない

超概算の段階で「テスト担当者を用意します」と言っていたのに、
リリース直前になって「担当者が他の業務で手が離せない」となるケースが多発します。

**対策：** テスト期間と担当者数を具体的に合意し、スケジュールに明記する。
「○月○週から○週間、担当者○名がテストに専念できる」という状態を作ってもらう。

#### 落とし穴2：テストが後回しになり、期間が圧縮される

開発が遅れると、最初にしわ寄せが来るのがテスト期間です。
「リリース日は変えられないので、テストを1週間でやってほしい」となりがちです。

**対策：** テスト期間はバッファを含めて最初から確保する。
テスト期間の圧縮はバグの見落としに直結することを顧客に伝える。

#### 落とし穴3：「不具合が出たら直してもらえる」と思っている

テスト中に見つかった不具合は、すべてベンダーが修正するわけではありません。
「仕様通りに実装されているが、顧客の業務が変わった」場合は追加費用が発生します。

**対策：** 「仕様に基づく不具合は修正対象」「仕様変更は追加費用」という基準を事前に合意する。

---

### Section 6：確認結果の記録方法

**一言でいうと：実施者・シナリオ数・期間・不具合対応の基準をセットで残す。**

**総合テスト確認シート（超概算時点）：**

```
■ 総合テスト計画（20XX年XX月XX日時点）

【実施体制】
  主担当      ：顧客側 3名（テスト期間中は専任で対応）
  ベンダー支援 ：テストケース作成・環境提供・不具合修正対応

【テスト内容】
  対象        ：シナリオテスト（業務フロー全体）
  シナリオ数  ：約40件（通常パターン30件・例外パターン10件）
  テストケース作成：ベンダー側で作成・顧客に確認いただく

【テスト期間】
  総合テスト  ：3週間
  不具合修正  ：1週間（バッファ含む）
  最終確認    ：3日間
  合計        ：約4〜5週間

【不具合対応の基準】
  修正対象    ：設計書・仕様書と異なる動作（ベンダー負担）
  追加費用    ：仕様変更・機能追加・設計書に記載のない要求

【スケジュール】
  テスト開始  ：XX月XX日
  本番リリース ：XX月XX日

■ 前提条件
  - 顧客側のテスト担当者3名を上記期間中に確保いただく
  - テスト期間の短縮は不具合見落としリスクが高まることを合意済み
  - 仕様変更が発生した場合は変更管理プロセスに従い追加見積もりを行う
```

## まとめとネクストアクション

### 3つの重要ポイント

1. **総合テスト・シナリオテストは「誰がやるか」が最も曖昧になりやすい工程**
   単体〜システムテストはベンダーが担うが、シナリオテストは顧客の参加が不可欠。
   超概算フェーズで「顧客が何名・何週間確保できるか」を具体的に合意する。

2. **テスト期間は削ってはいけない。最初から正しく確保する**
   開発が遅れても、テスト期間の圧縮はバグの見落としに直結する。
   スケジュールにテスト期間とバッファを最初から組み込むことがPMの役割。

3. **「不具合＝全部ベンダーが直す」は合意ではなく誤解**
   仕様に基づく不具合はベンダーが修正するが、仕様変更・機能追加は追加費用。
   この基準を超概算フェーズで明文化しておくことで、後からの争いを防ぐ。

### 明日からできるネクストアクション

> **今の担当PJで「総合テスト確認シート」を埋め、顧客と実施体制・期間・基準を合意する。**

| 確認項目 | 内容 | 合意状況 |
|--------|------|--------|
| 実施体制 | 顧客：　名 / ベンダー：　名 | 合意済 / 未確認 |
| シナリオ数 | 約　　件（通常　件・例外　件） | 合意済 / 未確認 |
| テストケース作成 | 顧客 / ベンダー / 共同 | 合意済 / 未確認 |
| テスト期間 | 　　週間（開始：　月　日） | 合意済 / 未確認 |
| 不具合修正の基準 | 仕様不一致：ベンダー / 仕様変更：追加費用 | 合意済 / 未確認 |

このシートを顧客と確認することで、
「テストは誰がやるのか」の認識ズレを早期に解消できます。
