# スコープ管理 > 立ち上げ

## 超概算：【対客】スコープ変更可能性と影響対象の特定／確認

---

## 導入

### このスキルを身につけると、何が変わるか

「あの機能、やっぱり追加してほしい。コストは変わらないよね？」
「業務フローが変わったから、システムも変えてほしい。すぐできるでしょ？」
「法改正が入ったから、年末までに対応してほしい。」

スコープ変更は「もし起きたら」ではなく、「必ず起きる」ものです。
問題は変更が起きることではなく、**変更が起きたときに何も備えていないこと**です。

超概算フェーズで「何がスコープ変更のトリガーになりやすいか」「変更が起きたときに何が影響を受けるか」を顧客と確認しておくことで：
- 変更が起きても冷静に影響範囲を提示できる
- 「コストも納期も変えられない」という無理難題を事前に防げる
- 変更管理プロセスへの顧客の理解と協力を得られる
- PMとして「想定外だった」ではなく「想定していた」対応ができる

---

## 学習目標

このテキストを読み終えると、以下ができるようになります。

1. **スコープ変更が発生しやすいトリガーを特定し、顧客に確認できる**
2. **スコープ変更が「コスト・スケジュール・品質」に与える影響を説明できる**
3. **変更管理プロセスの基本的な考え方を超概算フェーズで顧客と合意できる**

## 本編

---

### Section 1：スコープ変更とは何か

**一言でいうと：最初に合意した「やること・やらないこと」が後から変わることです。**

引越しの見積もりで考えてみましょう。
「荷物は段ボール30箱・大型家具3点」で見積もりを出しました。
引越し当日に「ピアノも運んでほしい」と言われたとします。

これがスコープ変更です。
「ピアノを運ぶ」は最初の合意に含まれていません。
当然、追加のトラックと作業員が必要になり、費用と時間が変わります。

システム開発でのスコープ変更も同じです。

| スコープ変更の種類 | 具体例 |
|--------------|------|
| **機能の追加** | 「検索機能も付けてほしい」 |
| **機能の変更** | 「画面の構成をやっぱり変えたい」 |
| **対象範囲の拡大** | 「当初1部門だったが、全社展開にしたい」 |
| **品質基準の引き上げ** | 「やはり24時間対応にしてほしい」 |
| **スケジュールの前倒し** | 「3ヶ月早めてほしい」 |

いずれも「最初の合意から外れた変更」であり、
何らかの影響（コスト・スケジュール・品質）が生じます。

---

### Section 2：スコープ変更が起きやすいトリガーを特定する

**一言でいうと：「何が確定していないか」がわかれば、変更リスクが見える。**

スコープ変更は突然起きるのではなく、事前に「種」が見えています。
超概算フェーズで「この部分は変わりやすい」という箇所を特定しておきます。

#### よくあるスコープ変更のトリガー：

**① 業務フロー・要件が未確定**

```
確認の問いかけ：
「今回の要件の中で、まだ社内で決まっていない部分はありますか？」
「業務フローが現在検討中・調整中の部分はありますか？」
```

要件が確定していない状態で開発を進めると、後から「やっぱり違う」が必ず来ます。
「未確定の部分を確認した上で見積もりを出している」という前提を明示しておきます。

**② 外部システム・第三者の仕様待ち**

```
確認の問いかけ：
「連携先の外部システムの仕様はすでに確定していますか？」
「今回の要件の中で、他の部門や取引先との調整が必要な部分はありますか？」
```

外部システムの仕様変更は、こちらではコントロールできません。
仕様待ちの部分が変われば、必ずスコープへの影響が出ます。

**③ 経営・組織の変化**

```
確認の問いかけ：
「開発期間中に、組織変更・業務変更・合併などの予定はありますか？」
「今後1〜2年の事業計画で、このシステムへの影響がありそうなことはありますか？」
```

組織変更・事業変更はシステムの要件を大きく変えることがあります。
特に大規模プロジェクトでは、開発中に経営判断が変わるリスクを把握しておきます。

**④ 法改正・制度変更**

```
確認の問いかけ：
「今回のシステムは法律や制度に関連する部分がありますか？
 開発期間中に法改正が予定されているものはありますか？」
```

税制・労務・個人情報保護などの法改正は、
「やらなければならない」対応として突然発生します。
法改正対応は「スコープ変更のオプション」ではなく「必須対応」になるため、
事前にリスクとして認識しておくことが重要です。

**⑤ ステークホルダーの変化**

```
確認の問いかけ：
「今回のプロジェクトの意思決定者（承認権限者）は開発期間中に変わる可能性はありますか？」
「要件を決めている担当者が異動・退職する可能性はありますか？」
```

担当者が変わると、要件の優先度や内容が大きく変わることがあります。
「前任者と決めた要件が引き継がれていない」は開発中盤に頻発するトラブルです。

### Section 3：変更がもたらす影響を理解する

**一言でいうと：スコープ・コスト・スケジュールの3つはトレードオフの関係にある。**

スコープ変更は、必ず以下の3つのいずれか（または複数）に影響します。

```
【プロジェクトの鉄の三角形】

         スコープ
          /  \
         /    \
        /      \
    コスト ── スケジュール
```

「スコープが増える」と、コストかスケジュール（または両方）が変わります。
「コストを増やさずに機能を追加したい」なら、スケジュールが延びます。
「スケジュールも延ばせない」なら、別の機能を削るか、品質を下げるしかありません。

この「3つはトレードオフ」という原則を、超概算フェーズで顧客に伝えておくことが重要です。

**影響の具体例：**

| 変更の内容 | コストへの影響 | スケジュールへの影響 | 品質への影響 |
|---------|-----------|----------------|----------|
| 機能追加（中規模） | 増加 | 延長 | 変わらない |
| スケジュール前倒し | 増加（人員追加） | 短縮 | 低下リスク |
| 品質基準の引き上げ | 増加 | 延長 | 向上 |
| 対象範囲の縮小 | 減少 | 短縮 | 変わらない |

「追加したい」「早めたい」「品質を上げたい」は、
どれかをトレードオフにしなければ実現できないことを、
顧客と共通認識として持っておきます。

---

### Section 4：変更管理プロセスの基本

**一言でいうと：変更が起きたときに「感情論」ではなく「プロセス」で対処するための仕組みです。**

変更管理プロセスとは、スコープ変更の申請・影響評価・承認・実施を
定められた手順で行うことです。

これがないと、何が起きるか：
- 顧客が「口頭で追加をお願いしたからやってくれている」と思い込む
- ベンダーは「正式な変更依頼がないからやらない」と思っている
- 気づいたときには「追加した」「頼んでいない」の水掛け論になる

**変更管理プロセスの基本フロー：**

```
① 変更の申請
   顧客が変更したい内容を書面で申請する
   （口頭・メールの追記ではなく、専用の変更依頼書を使う）

② 影響評価
   ベンダーが変更の影響（工数・コスト・スケジュール）を評価する
   評価結果を顧客に提示する

③ 承認・合意
   顧客が影響を確認した上で、変更の承認または却下を決定する
   承認された場合のみ、変更作業を開始する

④ 実施・記録
   変更作業を実施し、変更の記録を残す
   スコープ合意書・見積もりを更新する
```

**超概算フェーズで合意しておくこと：**

```
使える問いかけ：
「開発中に要件の変更が発生した場合は、
 変更内容と影響（コスト・スケジュール）を書面でご確認いただいた上で
 進める形にしたいと思いますが、よいですか？」

「口頭での変更依頼は受け付けず、書面での申請を基本とすることで
 双方の認識を揃えたいと思います。」
```

「プロセスを決める」ことを「管理が厳しい」と受け取る顧客もいますが、
「変更の記録が残ることで、双方にとって安心できる」という観点で伝えます。

---

### Section 5：影響対象の特定方法

**一言でいうと：変更があった場合に「どこが連鎖的に影響を受けるか」を事前にマッピングする。**

すべての変更が同じ影響を持つわけではありません。
「小さい変更なのに、なぜこんなに工数がかかるのか」という場面では、
連鎖的な影響が発生していることが多いです。

**影響が広がりやすいポイント：**

| 変更の場所 | 連鎖的な影響先 |
|---------|-----------|
| DB（データ構造）の変更 | 関連する全画面・帳票・CSV・連携機能 |
| マスタ（コード体系）の変更 | 全機能・全帳票（データ整合性の確認が必要） |
| 認証・権限の変更 | 全画面（アクセス制御の見直しが必要） |
| 外部連携仕様の変更 | 連携機能全体・テスト計画 |
| スケジュールの前倒し | チーム体制・テスト期間・品質 |

特に「DBの構造変更」は最も影響範囲が広く、
開発後半で発生すると全工程の手戻りが発生します。
超概算フェーズで「DBに影響するような変更が後から来る可能性がないか」を
確認しておくことが重要です。

---

### Section 6：確認結果の記録方法

**一言でいうと：変更リスクの一覧と変更管理プロセスの合意を書面に残す。**

**スコープ変更リスク・変更管理合意（超概算時点）：**

```
■ スコープ変更リスク一覧（20XX年XX月XX日時点）

【変更発生リスクが高い領域】
  ① 在庫管理連携仕様
    リスク    ：連携先ベンダーの仕様確定が遅れる可能性がある
    影響      ：連携機能の設計・開発・テストに影響
    対応方針  ：仕様確定後に当該部分を追加見積もり

  ② 承認フローの設計
    リスク    ：社内の承認ルールが現在検討中で未確定
    影響      ：承認フロー画面・メール通知・権限設定に影響
    対応方針  ：要件定義フェーズ開始前に確定いただくことを条件とする

  ③ 消費税・法改正対応
    リスク    ：開発中に税率変更等の法改正が入る可能性がある
    影響      ：集計・帳票・DB設計に広範な影響
    対応方針  ：法改正対応は追加費用として別途見積もり

【変更管理プロセスの合意】
  変更申請    ：書面（変更依頼書）での申請を基本とする
  影響評価    ：ベンダーが申請受領後5営業日以内に影響を提示
  承認        ：顧客の承認（担当○○様）後に変更作業を開始
  費用        ：承認後に追加費用が確定し、請求に反映

■ 前提条件
  - 上記リスク領域の変更が発生した場合は、変更管理プロセスに従う
  - 口頭・メールの追記による変更依頼は受け付けない
  - 変更の影響評価中は変更前の仕様で開発を継続する
```

## まとめとネクストアクション

### 3つの重要ポイント

1. **スコープ変更は「もし起きたら」ではなく「必ず起きる」。変更トリガーを事前に特定する**
   未確定の要件・外部仕様待ち・法改正リスクを洗い出し、
   「この部分は変更の可能性がある」と顧客と共有しておくことがリスクヘッジになる。

2. **スコープ・コスト・スケジュールはトレードオフ。この原則を超概算フェーズで共有する**
   「追加しても費用は変えない」は無理な要求。
   変更があればどれかが変わるという原則を、プロジェクト開始前に顧客と合意しておく。

3. **変更管理プロセスを最初から決める。「口頭依頼OK」が全ての問題の根源**
   変更は書面で申請・影響評価・承認・実施というプロセスを踏む。
   このプロセスがあることで、感情論ではなく事実ベースの対話ができる。

| 変更リスク領域 | 変更が起きる可能性 | 影響対象 | 対応方針 |
|------------|--------------|--------|--------|
| | 高 / 中 / 低 | | |
| | 高 / 中 / 低 | | |
| | 高 / 中 / 低 | | |

| 変更管理プロセス | 合意内容 | 合意状況 |
|-------------|--------|--------|
| 申請方法 | 書面（変更依頼書） | 合意済 / 未確認 |
| 影響評価の期間 | 　　営業日以内 | 合意済 / 未確認 |
| 承認者 | 　　　　様 | 合意済 / 未確認 |
| 費用の扱い | 承認後に追加費用を確定 | 合意済 / 未確認 |

このシートを顧客と確認することで、
変更が起きても「想定内」として冷静に対処できるPJを作れます。
