# スコープ管理 > 立ち上げ

## 超概算：【対客】画面／帳票／CSV項目等の変動要因の規模確認

---

## 導入

### このスキルを身につけると、何が変わるか

「とりあえず概算を出してほしい」と言われた。
でも何が何枚あるのか、何がどれだけ複雑なのか、誰も教えてくれない。

そのまま出した見積もりは、後から必ず崩れます。

- 「画面がこんなに多いとは思っていなかった」
- 「帳票がこんなに複雑だとは聞いていなかった」
- 「CSV項目が数十項目あるとは…」

超概算の精度を左右するのは、**変動要因の規模**です。
画面数、帳票数、CSV項目数——これらの規模を早期に確認することで、
「ざっくりだが根拠のある見積もり」が作れます。

このスキルを学ぶことで：
- 変動要因（画面・帳票・CSV等）が見積もりにどう影響するか説明できる
- 顧客から規模の情報を引き出す問いかけができる
- 規模の複雑度（シンプル・標準・複雑）を分類できる
- 超概算の前提条件として規模を明記できる

---

## 学習目標

このテキストを読み終えると、以下ができるようになります。

1. **変動要因の概念を顧客にわかりやすく説明できる**
2. **画面・帳票・CSV等の規模確認を顧客との対話で進められる**
3. **規模確認の結果を超概算の前提条件として整理できる**

---

## 本編

---

### Section 1：変動要因とは何か

**一言でいうと：見積もり金額を上下させる「量と複雑さ」のことです。**

システム開発の見積もりは、「何をどれだけ作るか」で決まります。
その「どれだけ」にあたるのが変動要因です。

引越し費用で考えてみましょう。
引越し費用は、荷物の量と運ぶ距離で大きく変わります。
「荷物は普通くらい」では見積もれません。
段ボール何箱か、大型家具は何点かを確認して初めて、概算が出せます。

システム開発も同じです。

| 変動要因 | 意味 | 見積もりへの影響 |
|---------|------|--------------|
| **画面数** | 入力・一覧・詳細などの画面の数 | 多いほど工数が増える |
| **帳票数** | 印刷・PDF出力する書類の数 | 複雑なレイアウトほど工数が増える |
| **CSV項目数** | 取込・出力するCSVの列数・件数 | バリデーション量が増えるほど工数が増える |
| **連携システム数** | 外部システムとのAPI連携の数 | 連携先が増えるほど工数が増える |
| **マスタ数** | コードや区分などの管理テーブルの数 | 多いほど設定・保守工数が増える |

超概算の段階では、これらを**正確に把握する必要はありません。**
「だいたい何個くらいか」「シンプルか複雑か」がわかれば十分です。

---

### Section 2：なぜ超概算フェーズで確認するのか

**一言でいうと：規模の前提が違うだけで、見積もりが数倍変わるからです。**

例えば、画面数だけで考えてみます。

```
【前提：画面数 10画面、すべてシンプルな構成】
 → 開発工数：約100人日（仮）

【実際：画面数 30画面、うち10画面は複雑な条件分岐あり】
 → 開発工数：約350人日（仮）
```

前提と実態が違うだけで、見積もりが3倍以上変わることがあります。

超概算フェーズでの規模確認は、**見積もりの「物差し」を合わせる作業**です。
正確な数字でなくてよい。
「10画面くらい」「30画面以上」という粒度でも、大きな判断材料になります。

`超概算の精度目標：±50%以内。規模の確認なしに出した見積もりは、±200%になることもある。`

---

### Section 3：画面の規模確認

**一言でいうと：画面数と、それぞれの「複雑さ」を確認する。**

#### 画面数の確認

```
使える質問：
「今回のシステムで使う画面を、思いつく限り挙げてもらえますか？」
「一覧画面、入力画面、確認画面、完了画面など、
 業務の流れに沿って洗い出してみましょう。」
```

画面を洗い出したら、以下の3段階に分類します。

| 複雑度 | 基準 | 例 |
|-------|------|-----|
| **シンプル** | 項目が少なく、条件分岐もほぼない | 確認画面、完了画面、マスタ一覧 |
| **標準** | 一般的な入力項目数・バリデーション | 基本的な登録・編集画面 |
| **複雑** | 動的な条件分岐・計算ロジック・複数テーブル連動 | 見積計算画面、承認フロー画面 |

顧客に「複雑度」という言葉は使わなくてよいです。
「この画面は入力項目が多いですか？」「条件によって表示が変わりますか？」と
具体的に聞く方が答えを得やすいです。

#### 確認後の整理例

```
■ 画面一覧（超概算時点）
  シンプル：4画面（ログイン、メニュー、完了、エラー）
  標準    ：8画面（各種登録・編集・一覧画面）
  複雑    ：3画面（見積計算、承認フロー、ダッシュボード）
  合計    ：15画面（概算）
```

---

### Section 4：帳票の規模確認

**一言でいうと：帳票の枚数と、レイアウトの複雑さを確認する。**

帳票（印刷物・PDF）は、見た目が複雑なほど開発工数が跳ね上がります。
「Excelで作ったような複雑なレイアウト」は、
エンジニアにとって非常に手間のかかる作業です。

#### 帳票数の確認

```
使える質問：
「今の業務で印刷したり、PDFで出力している書類は何種類ありますか？」
「受注確認書、納品書、請求書など、どんな帳票が必要ですか？」
「それぞれ、Excelで作るとしたら何ページくらいになりますか？」
```

#### 帳票の複雑度分類

| 複雑度 | 基準 | 例 |
|-------|------|-----|
| **シンプル** | 縦並びの項目のみ、固定レイアウト | 確認書、通知文書 |
| **標準** | 表形式、小計・合計計算あり | 納品書、請求書 |
| **複雑** | 合算・集計・複数ページ・条件による出し分け | 見積書、売上集計表 |

帳票は「既存の書類」がある場合がほとんどです。
「今使っているExcelや紙の書類を見せてもらえますか？」と聞くのが最速です。

---

### Section 5：CSV・データ連携の規模確認

**一言でいうと：CSVの項目数・件数と、取込/出力どちらかを確認する。**

CSVのインポート・エクスポートは、意外と工数がかかります。
特に「取込（インポート）」は、バリデーション処理が多くなるほど複雑です。

#### CSV・データ連携の確認

```
使える質問：
「CSVでの取込・出力は必要ですか？」
「取込の場合、1回あたり何件くらいのデータが来ますか？」
「CSVの列（項目）は何項目くらいありますか？」
「エラーチェック（バリデーション）はどこまで必要ですか？」
「外部システムとのAPI連携（自動でデータをやり取り）は必要ですか？」
```

#### CSV複雑度の分類

| 複雑度 | 基準 |
|-------|------|
| **シンプル** | 出力のみ、項目数10以下、バリデーションなし |
| **標準** | 取込あり、項目数10〜30、基本的なバリデーション |
| **複雑** | 取込あり、項目数30以上、複合バリデーション・エラー処理 |

---

### Section 6：規模確認の進め方と記録の残し方

**一言でいうと：「現状の業務」を起点に聞くと、顧客が答えやすくなる。**

顧客に「画面数を教えてください」と聞いても、
システムの知識がない顧客には答えにくいです。

**「今の業務」から逆算する聞き方**が効果的です。

```
良い聞き方の例：
「今の業務の流れを教えてください。
 その中で、パソコン（またはシステム）を使って操作する場面はどこですか？」

「今は紙やExcelで管理していますか？
 それを画面でできるようにしたい、ということでしょうか？」

「今は何種類の帳票（書類）を使っていますか？
 それをシステムから出力したいですか？」
```

業務の流れから画面・帳票・CSVを一緒に洗い出すことで、
顧客も「こんなものが必要だったのか」と気づくことがあります。

#### 規模確認シートの記録例

```
■ 超概算：規模確認シート（20XX年XX月XX日時点）

【画面】
  合計：約15画面（シンプル4、標準8、複雑3）
  ※ 要件定義フェーズで詳細確定

【帳票】
  合計：約4種類（シンプル1、標準2、複雑1）
  既存サンプル：受注確認書・納品書は紙サンプルあり

【CSV・データ連携】
  取込：商品マスタCSV（項目数：約25項目、件数：月1回500件程度）
  出力：売上レポートCSV（項目数：約15項目）
  外部連携：なし（今回は対象外）

【前提条件】
  - 上記は概算時点の情報。要件定義で変動する可能性あり
  - 規模が20%以上変動した場合は再見積もりを検討する
```

この記録を顧客と共有することで、
「前提が違った」というトラブルを防ぐ根拠になります。

## まとめとネクストアクション

### 3つの重要ポイント

1. **変動要因の規模が「見積もりの精度」を決める**
   画面数・帳票数・CSV項目数が把握できていない見積もりは、
   根拠のない数字になる。超概算でも「前提の規模」を明示することが重要。

2. **「業務の流れ」から逆算して規模を聞き出す**
   顧客に「画面数は？」と直接聞いても答えにくい。
   「今の業務でどこにパソコンを使いますか？」という問いから洗い出す方が効果的。

3. **複雑度の分類が工数を左右する**
   数だけでなく「シンプル・標準・複雑」のどれかを確認する。
   同じ10画面でも、複雑度によって工数が2〜3倍変わることがある。
