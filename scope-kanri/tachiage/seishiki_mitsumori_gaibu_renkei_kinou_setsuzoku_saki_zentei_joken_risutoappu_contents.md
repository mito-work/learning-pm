# スコープ管理 > 立ち上げ

## 正式見積：外部連携機能／接続先に対する前提条件のリストアップ

---

## 導入

### このスキルを身につけると、何が変わるか

「外部APIのテスト環境の提供が遅れ、テスト期間が2週間しか取れなかった」
「接続申請の審査に1ヶ月かかると後から判明し、全体スケジュールがズレた」
「本番稼働直前にAPIの仕様変更が入り、設計を一からやり直すことになった」
「APIドキュメントはあったが実装と仕様が違い、調査に多大な工数がかかった」——

外部連携は、プロジェクト内で最も「自分たちがコントロールできない」領域です。
社内の作業は計画通り進んでも、外部連携先の都合一つでプロジェクト全体が止まります。
このスキルは、**外部連携機能・接続先に特有のリスクを前提条件として正式見積フェーズで明文化し、スケジュール・工数への影響を事前に合意しておく**技術です。

このスキルを学ぶことで：
- 外部連携由来のスケジュール遅延に「根拠のある対処」ができる
- テスト環境提供・接続申請・仕様変更など特有のリスクを事前に把握できる
- 顧客と外部連携先への「確認すべきこと」を見積もり前に洗い出せる
- 「外部の都合で遅れた」を追加費用・スケジュール変更の交渉根拠にできる

---

## 学習目標

このテキストを読み終えると、以下ができるようになります。

1. **外部連携特有の前提条件カテゴリ（技術・申請・仕様・性能）を使ってリストアップできる**
2. **各前提条件について「崩れた場合の影響」をセットで記録できる**
3. **確認先（顧客・外部連携先・PL）ごとに確認事項を整理して確認を進められる**

## 本編

---

### Section 1：外部連携の前提条件がなぜ特別に重要か

**一言でいうと：外部連携先は自分たちが動かせない。だから「動いてくれることを前提にしている」を、全部書き出す必要がある。**

一般的な前提条件（顧客が仕様を期日までに出す・テスト環境が整備されるなど）は、交渉や督促によってある程度コントロールできます。

外部連携の前提条件は異なります。

```
【外部連携特有のコントロール不能なリスク】

  ① 外部連携先の技術的な準備
    → テスト環境の提供 / API仕様書の整備
    → 認証情報（APIキー・証明書）の発行
    → 接続テストの実施許可
    ※ ベンダーや担当者のリソース次第。催促しても動かないことがある

  ② 接続申請・契約プロセス
    → 申請の審査期間（1週間〜数ヶ月まで幅がある）
    → 利用規約・NDA・セキュリティ審査の締結
    ※ 社内決裁・法務確認が必要になるケースあり

  ③ 仕様の安定性
    → プロジェクト期間中にAPIのバージョンアップ・廃止
    → ドキュメントと実装の乖離
    ※ 外部のロードマップ次第で予告なく変わる

  ④ 性能・可用性
    → レスポンス時間・レート制限（APIの呼び出し上限）
    → 障害時の動作・フォールバック仕様
    ※ 事前に確認しないと設計後に発覚する
```

これらは「発生してから対処する」では遅い。
見積もり前に前提条件として明文化し、「崩れた場合の影響」を顧客と合意することが必要です。

---

### Section 2：外部連携の前提条件——4カテゴリでリストアップする

**一言でいうと：「技術・申請・仕様・性能」の4カテゴリで漏れなく洗い出す。**

#### カテゴリ①：技術的な準備の前提条件

```
□ テスト環境
  前提：「外部連携先のテスト環境が○月○日までに提供される」
  影響：「提供が遅れると、テスト期間が圧縮されます。
         テスト完了を条件とした納期に影響が生じます。」

□ APIドキュメント
  前提：「APIの仕様書（最新版）が着手前に提供されており、
         実装と乖離がない」
  影響：「乖離がある場合、調査工数として別途○〜○人日が
         発生します。仕様確認のやり取りが発生すると
         さらに工数が増える可能性があります。」

□ 認証情報の発行
  前提：「APIキー・証明書などの認証情報が開発着手前に取得できる」
  影響：「取得が遅れると、認証が必要な機能の開発・テストが
         着手できず、全体スケジュールが後ろにズレます。」

□ 接続テストの実施許可
  前提：「開発環境から外部連携先テスト環境への接続が許可される」
  影響：「許可が取れない場合、実際の接続テストができず、
         本番稼働後に初めて問題が発覚するリスクがあります。」
```

#### カテゴリ②：接続申請・契約の前提条件

```
□ 接続申請の審査期間
  前提：「接続申請の審査が○週間以内に完了する」
  影響：「審査が長引くと、外部連携機能の開発着手が遅れます。
         審査期間が不明な場合、スケジュールにリスクバッファが
         必要になります。」

□ 利用契約・NDAの締結
  前提：「利用契約・NDAが着手前に締結される
         （顧客側の法務確認を含む）」
  影響：「締結が遅れると、契約条件が確定するまで
         開発に着手できません。」

□ セキュリティ審査
  前提：「外部連携先のセキュリティ要件を確認済みであり、
         当社システムの審査が事前に完了する」
  影響：「審査で追加対応が求められた場合、
         対応工数が追加発生します。」
```

#### カテゴリ③：仕様の安定性に関する前提条件

```
□ API仕様の変更凍結
  前提：「プロジェクト期間中（○月〜○月）、
         外部連携先のAPIバージョンは変更されない」
  影響：「仕様変更が発生した場合、設計・実装のやり直しが
         発生し、追加工数と日程変更が必要になります。」

□ データ仕様の確定
  前提：「連携するデータの項目・形式・桁数は着手前に確定している」
  影響：「確定前に着手すると、後からデータ仕様が変わった場合に
         改修工数が発生します。」

□ エラー処理・例外仕様の定義
  前提：「外部連携先のエラーコード・例外ケースの仕様が
         事前に定義されている」
  影響：「未定義の場合、エラー処理の設計を
         仮定で進めることになり、後の改修リスクがあります。」
```

#### カテゴリ④：性能・可用性に関する前提条件

```
□ レスポンス時間・レート制限
  前提：「APIのレスポンス時間（目標：○秒以内）と
         レート制限（○回/分）の仕様が把握できている」
  影響：「把握できない場合、性能設計の前提がなく、
         本番後に性能問題が発覚するリスクがあります。」

□ 障害時の動作（フォールバック）
  前提：「外部連携先が障害のとき、
         システムがどう動くかの仕様が定義されている」
  影響：「未定義の場合、障害時の動作設計ができず、
         本番後に障害の影響範囲が拡大するリスクがあります。」
```

### Section 3：確認先を整理する——誰に何を確認するか

**一言でいうと：外部連携の前提条件確認は「顧客」「外部連携先」「PL」の3者に分けて進める。**

外部連携の前提条件は、確認先が複数あります。
PMが誰に何を確認するかを整理してから動くことで、確認の効率が上がります。

```
【確認先の整理】

◆ 顧客に確認するもの
  ・接続申請の手続き状況（いつ申請するか・審査状況）
  ・外部連携先との利用契約・NDAの締結状況
  ・認証情報（APIキー等）の取得手続きを顧客が主導する場合の進捗
  ・外部連携先の担当者の連絡先・窓口の紹介

◆ 外部連携先に確認するもの（顧客経由での紹介後）
  ・テスト環境の提供可否・提供時期
  ・APIドキュメントの入手経路・最新版の確認
  ・APIバージョンアップの予定（プロジェクト期間中の変更有無）
  ・レスポンス時間・レート制限の仕様
  ・接続テストの実施条件

◆ PLに確認するもの（技術的な観点）
  ・APIドキュメントを見た上での「実現可能性の確認」
  ・前提条件が崩れた場合の工数への影響の見積もり
  ・テスト環境なしで開発を進めた場合のリスク評価
```

外部連携先への直接確認は、顧客に窓口を紹介してもらってから行うことが基本です。
「ベンダーが勝手に外部連携先に連絡している」という状況は顧客の信頼を損なうことがあります。

---

### Section 4：外部連携特有の失敗パターンと対処

**一言でいうと：「よくある失敗」を知ることが、同じ轍を踏まないための最短経路。**

外部連携の前提条件でよく起きる失敗とその対処を押さえます。

| 失敗パターン | 原因 | 対処（前提条件として書く内容） |
|-----------|-----|--------------------------|
| テスト環境の提供が遅れる | 提供時期を確認しなかった | 「テスト環境は○月○日までに提供される。遅れた場合、テスト期間が圧縮される」 |
| APIドキュメントと実装が違う | 仕様書の信頼性を確認しなかった | 「ドキュメントと実装の整合性を着手前に確認する。乖離がある場合○人日追加」 |
| 接続申請に1ヶ月以上かかった | 審査期間を事前に確認しなかった | 「接続申請の審査は○週間以内に完了する。遅れた場合スケジュールに影響が出る」 |
| 本番前にAPIが仕様変更された | 変更凍結を取り決めなかった | 「プロジェクト期間中はAPIバージョンを変更しない旨を外部連携先に確認する」 |
| レート制限で性能要件を満たせない | 事前に制限を確認しなかった | 「レート制限（○回/分）の仕様を着手前に確認し、性能設計の前提とする」 |

---

### Section 5：前提条件を顧客と合意する

**一言でいうと：外部連携の前提条件は、顧客が「中間者」として外部連携先を動かしてくれることへの依存を含む。顧客の協力を明確に依頼する。**

外部連携の前提条件の多くは、**顧客が外部連携先に対して働きかけてくれることを前提にしています。**
この依存関係を顧客と明確に合意することが重要です。

```
顧客への説明例：

「今回の外部連携について、以下の点を
 前提条件として整理しました。

 特に下記については、顧客様から外部連携先への
 ご確認・ご手配をお願いしたい事項です。

 ① テスト環境の提供依頼（○月○日までに）
 ② APIドキュメントの入手（着手前に）
 ③ 接続申請の手続き開始（○月○日までに）

 これらが予定通り進まない場合、開発着手・テストの
 スケジュールに影響が出ます。

 進捗状況を○月○日の打ち合わせで確認させてください。
 その時点で遅れが確認された場合は、スケジュールの
 見直しをご相談させていただきます。」
```

「顧客が動いてくれることへの依存」を曖昧にしておくと、遅延が発生したときに「誰のせいか」という不毛なトラブルになります。
「顧客側でやっていただくこと」を具体的に書いて合意することが、後の対話をシンプルにします。

## まとめとネクストアクション

### 3つの重要ポイント

1. **外部連携の前提条件は「技術・申請・仕様・性能」の4カテゴリで漏れなく洗い出す**
   外部連携は自分たちがコントロールできない領域が多い。
   「当然そうだろう」という仮定を全部書き出すことが、スケジュール遅延の根拠作りになる。

2. **確認先を「顧客・外部連携先・PL」の3者に分けて整理してから動く**
   外部連携先への直接確認は顧客に窓口を紹介してもらってから行う。
   誰が何を確認するかが曖昧なまま進むと、確認漏れが発生する。

3. **「顧客が外部連携先を動かしてくれること」への依存を明確に合意する**
   顧客の協力が前提になる事項（テスト環境の依頼・接続申請の手配）を具体的に書いて合意する。
   「誰が動くのか」が明確でないと、遅延が起きたときに誰の責任かがわからなくなる。
