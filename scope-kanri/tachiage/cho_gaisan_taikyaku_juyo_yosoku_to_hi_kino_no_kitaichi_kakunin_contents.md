# スコープ管理 > 立ち上げ

## 超概算：【対客】需要予測と非機能の期待値確認

---

## 導入

### このスキルを身につけると、何が変わるか

「とにかく速くて、絶対落ちないシステムにしてほしい」
この言葉をそのまま受け取ると、見積もりが崩壊します。

「速い」とは何秒以内のことか。
「絶対落ちない」とは年間何時間の停止まで許容されるのか。
誰が、どれくらいの頻度で、どれだけのデータ量で使うのか。

これらが曖昧なまま超概算を出すと：
- インフラコストを大幅に見誤る
- 後から「性能が足りない」「落ちすぎる」と言われる
- アーキテクチャの根本見直しが発生する

需要予測（利用規模の想定）と非機能要件（品質の期待値）の確認は、
「機能を作る」以外のコストを見極めるための必須作業です。

このスキルを学ぶことで：
- 需要予測（ユーザー数・アクセス数・データ量）を顧客から引き出せる
- 非機能要件（性能・可用性・セキュリティ等）の期待値を整理できる
- 「なんとなく高品質」ではなく「数字で語れる前提条件」が作れる

---

## 学習目標

このテキストを読み終えると、以下ができるようになります。

1. **需要予測の主要な確認項目（ユーザー数・アクセス量・データ量）を説明できる**
2. **非機能要件の5分類を使って、顧客の期待値を引き出す問いかけができる**
3. **確認結果を超概算の前提条件として整理し、記録できる**

## 本編

---

### Section 1：需要予測とは何か

**一言でいうと：「誰が・何人が・どれくらいの頻度で・どれだけのデータを扱うか」の見積もりです。**

橋の設計で考えてみましょう。
1日10台の車が通る橋と、1日10万台が通る橋では、
設計・素材・コストがまったく異なります。
「とりあえず橋を作って」では、後から壊れることになります。

システムも同じです。
10人が使うシステムと、10万人が同時に使うシステムでは、
必要なサーバーの性能・数・コストが桁違いに変わります。

**需要予測の主な確認項目：**

| 確認項目 | 意味 | 具体例 |
|--------|------|------|
| **総ユーザー数** | システムを使う人の総数 | 社員200人・顧客1万人 |
| **同時接続ユーザー数** | 同時にシステムを使う人の最大数 | ピーク時50人同時 |
| **1日のアクセス数** | 1日に発生するリクエストの件数 | 1日500件の注文処理 |
| **ピーク時のアクセス数** | 最も集中する時間帯の処理件数 | 月末に1時間で300件集中 |
| **データ保存量** | 蓄積するデータの総量 | 3年で500万件のレコード |
| **将来の成長率** | 1〜3年後の利用規模の見込み | 年30%のユーザー増加 |

---

### Section 2：非機能要件とは何か

**一言でいうと：「何ができるか（機能）」ではなく「どれだけ良いか（品質）」の要求です。**

レストランで例えると：
- **機能要件** ＝ メニューの内容（何を食べられるか）
- **非機能要件** ＝ 提供速度・衛生レベル・営業時間・席数（どれだけ良いサービスか）

同じメニューでも、「5分で出てくる」「3時間待ち」では価値が全然違います。
システムも同様で、「同じ機能」でも品質の基準によってコストが大きく変わります。

非機能要件は主に5つに分類されます。

| 分類 | 一言で言うと | 代表的な指標 |
|-----|-----------|-----------|
| **性能** | 速さ・さばける量 | 応答時間・スループット |
| **可用性** | 使えている率・止まらなさ | 稼働率・復旧時間 |
| **セキュリティ** | 安全さ・守られ方 | 認証方式・暗号化要件 |
| **拡張性** | 将来の成長への対応力 | ユーザー増加への対応 |
| **運用・保守性** | 管理しやすさ・直しやすさ | 監視方法・バックアップ頻度 |

---

### Section 3：性能の期待値確認

**一言でいうと：「何秒以内に返ってほしいか」を数字で確認する。**

「速いシステムにしてほしい」は誰でも言います。
しかし「速い」の定義は人によって異なります。

```
確認の問いかけ：
「画面が表示されるまで、何秒以内であれば許容範囲ですか？」
「データを検索して結果が出るまで、何秒くらいを想定していますか？」
「一番使われる時間帯（ピーク時間）はいつごろですか？」
```

**性能の目安（Webシステムの一般的な基準）：**

| 応答時間 | ユーザーの感覚 | 対応コスト |
|--------|------------|---------|
| 1秒以内 | 快適・ストレスなし | 標準的な設計で対応可能 |
| 3秒以内 | 許容範囲 | 標準的な設計で対応可能 |
| 5秒以内 | やや不満 | 最適化が必要な場合あり |
| 10秒以上 | 不満・離脱 | 大幅な設計見直しが必要 |

「3秒以内」を要件にする場合と「0.5秒以内」を要件にする場合では、
インフラ費用・設計コストが数倍変わることがあります。

---

### Section 4：可用性の期待値確認

**一言でいうと：「どれだけ止まらないか」を稼働率と復旧時間で確認する。**

「絶対に止まらないシステムにしてほしい」は、コストが青天井になります。
99.999%の稼働率（年間5分以内の停止）を実現するには、
99%（年間88時間の停止）の場合に比べて、インフラ費用が10倍以上になることもあります。

```
確認の問いかけ：
「システムが止まると業務にどんな影響がありますか？」
「メンテナンスのための計画停止は受け入れられますか？（深夜・週末など）」
「もし止まった場合、何時間以内に復旧する必要がありますか？」
「24時間365日の利用が必要ですか？それとも業務時間内のみで十分ですか？」
```

**稼働率の目安：**

| 稼働率 | 年間の停止時間（目安） | 用途の例 |
|------|-----------------|--------|
| 99% | 約88時間 | 社内業務システム（計画停止あり） |
| 99.9% | 約9時間 | 一般的なBtoBサービス |
| 99.99% | 約53分 | ECサイト・決済システム |
| 99.999% | 約5分 | 金融・医療など停止が致命的なもの |

業務時間内だけ使う社内システムであれば、
夜間・休日のメンテナンス時間を設けることで、コストを大幅に抑えられます。

---

### Section 5：セキュリティ・運用の期待値確認

**一言でいうと：「何を守るか」と「誰がどう管理するか」を確認する。**

#### セキュリティ

セキュリティの要求水準は、扱うデータの性質によって決まります。

```
確認の問いかけ：
「このシステムで扱うデータには、個人情報・機密情報が含まれますか？」
「ログイン時の認証は、ID・パスワードだけで良いですか？
 それとも二段階認証や社内認証との連携が必要ですか？」
「システムへのアクセスログを記録・保存する必要はありますか？」
「セキュリティに関する社内規程や準拠すべき基準（ISMSなど）はありますか？」
```

個人情報や機密情報を扱う場合は、
暗号化・アクセス制御・ログ管理などの実装が必要になり、工数が増えます。

#### 運用・保守

```
確認の問いかけ：
「システムのバックアップはどれくらいの頻度で必要ですか？」
「障害が起きた場合、誰が最初に対応しますか？（社内担当か、ベンダーか）」
「システムの監視（サーバーが落ちたら通知するなど）は必要ですか？」
「リリース後の問い合わせ・サポート対応は、誰がどのように行いますか？」
```

### Section 6：確認結果の記録方法

**一言でいうと：数字で語れる前提条件として残す。「速くする」ではなく「3秒以内」と書く。**

**需要予測・非機能要件確認シート（超概算時点）：**

```
■ 需要予測（20XX年XX月XX日時点）

  総ユーザー数        ：約200名（社員のみ）
  同時接続ユーザー数  ：最大30名（ピーク時）
  1日のアクセス件数   ：約500件（受注処理）
  ピーク集中          ：月末の3営業日に全体の40%が集中
  データ保存量        ：初年度 約10万件、3年後 約50万件を想定
  将来の成長          ：ユーザー数は年10%増の見込み

■ 非機能要件（超概算時点の期待値）

  【性能】
    通常操作の応答時間：3秒以内
    一覧検索の応答時間：5秒以内（データ量が多い場合）

  【可用性】
    目標稼働率        ：99%（計画停止は深夜・休日に限定）
    障害時の復旧目標  ：翌営業日中に復旧
    利用時間          ：平日 8:00〜20:00（時間外はメンテナンス可）

  【セキュリティ】
    個人情報          ：あり（顧客氏名・連絡先）
    認証方式          ：ID・パスワード（二段階認証は今回対象外）
    アクセスログ保存  ：必要（1年間保存）

  【運用・保守】
    バックアップ      ：日次（1世代）
    障害対応          ：ベンダーへ連絡、翌営業日対応
    監視              ：死活監視あり（停止時にメール通知）

■ 前提条件
  - 上記は超概算時点の情報。要件定義で変動する可能性あり
  - 上記以上の品質（高稼働率・高セキュリティ等）が必要な場合は追加見積もりが必要
```

## まとめとネクストアクション

### 3つの重要ポイント

1. **需要予測の数字が、インフラ設計とコストを左右する**
   ユーザー数・同時接続数・データ量が変わると、必要なサーバー構成が変わる。
   「だいたい何人くらい使うか」という粒度でも、早めに確認することが重要。

2. **非機能要件は「数字で合意する」ことで初めて有効になる**
   「速い」「落ちない」「安全」は要件ではなく希望。
   「3秒以内」「稼働率99%」「日次バックアップ」と数字に変えることで、
   見積もりの根拠になり、後からのトラブルを防ぐ。

3. **高い非機能要件はコストが跳ね上がる。顧客に選択肢を示す**
   99%と99.99%の稼働率は、コストが10倍以上変わることがある。
   「どの水準が必要か」を顧客と一緒に判断するのがPMの役割。
